### 0.3 要決定の一覧（人間が決める。設計役は候補・推奨・影響を書くが決めない）

1 問 1 論点で、推奨を先頭に置いた。詳しい根拠は「節」の列の節にある。**どの候補も、成績を見て作っていない**。

### 2.1 全体の流れと PR の分け方

```
本書の承認・要決定の決定
  → 手順 1 事前の記録（PR-1: 元の実験の事前登録） → 人間が merge
  → 手順 2 小さな探索（main から元の実験を実行。台帳に開始・結末の行）
  → 手順 3 原因分析（D14-3 の担当。再現は並行。D14-10）
  → 手順 4 変更の記録（PR-2: 元の実験の実行記録＋改善後の実験の事前登録） → 人間が merge
  → 手順 5 再評価（main から改善後の実験を実行）
  → 手順 6 一巡の報告（PR-3: 改善後の実験の実行記録＋報告の版管理に置く部分） → 人間が終了を判定し merge
```

- PR の分け方は仮置き 2。各 PR は `docs/pr_review_policy.md` のレビュー（Codex、利用上限なら Claude 代替、安全弁 3 周）を通し、merge は人間が決める。
- **台帳の行を含む PR（PR-2・PR-3）**: D09 §10.10 は「追記の後のコミットと push は、実験設定のファイルと同じく人間が行う」と定める。順 2〜4 では、実験設定のファイルは作業役がコミット・push した PR を人間が merge してきた。しかし台帳については D09 §10.10 が「人間が行う」と明記しており、**人間による merge はこの規則を満たさない**（PR #99 のレビュー 1 周目の指摘）。そこで **D14-11** で、(a) 承認済みの規則のまま人間がコミット・push するか、(b) D09 §10.10 を改訂して作業役のコミット・push と人間の merge にするかを決める。推奨は (a)（承認済み設計を変えない。人間の手作業は一巡で 2 回のコミット・push）。(a) の手順: 実装役は実行の後、台帳を追記した作業ツリーを変えずに止めて司令塔へ報告し、人間がその作業ツリーで `research/trial_ledger.jsonl` をコミット・push する。その後、実装役・設計役が同じブランチに残りのファイル（実行記録・次の事前登録）を足して PR を作る。(b) を選ぶなら、D09 §10.10 の該当の文を「2026-10-22 の人間の決定 D14-11 による改訂」として本 PR で直し、最初の実験の前に承認を得る（D09 の改訂なしに作業役が台帳をコミットしない）。
- 台帳の行には判定の値（4 値・2 軸・保留の印）が入る（D09 §10.10、PR #98 の仮置き 55）。成績の数値は入らない【事実】（`TrialLedgerEntry`・`VariantLedgerResult` の項目）。司令塔は台帳の差分を開かない（D14-4 の (a) を選んだ場合。(b) なら判定の値は読んでよい）。

3. 取引が多いと想定され、証拠の要件（検証の合計 8 件。D13-11）で構造的に止まりにくい。

## 4. 格子の大きさと軸（要決定 D14-2）

### 4.1 候補を決める根拠【導出】＋【提案】

- **上限より十分小さい**: 試行の上限は 1 実験 100（Q7）。候補はその 1 割未満（4〜9）。
- **選定の偏り**: 選定は選定区間（2 年）の年率化シャープレシオの最大化（Q25）。試行が多いほど、選定区間で偶然よかった試行を選ぶ効きが大きくなり、検証区間での落ち込みの原因が「規則の弱さ」か「選び方の偏り」か分けにくくなる。少数なら原因分析で軸ごとに追える。
- **軸ごとの向きを読める最小**: 軸 2 本 × 値 2 なら各軸の「上げると良くなるか悪くなるか」を読める。値 3 の軸を 1 本入れると、中間がよいかも読める。
- **時間**: 第8.2節の表。1 実験が夜間 1 回（約 8〜13 時間）に収まる大きさを目安にした。
- **値の選び方**: 戦略の固定値（A・B の値）を中心に、半分と倍を置く。結果を見て値を選ばない。値は書いた順が試行番号と同点の解き方を決めるので、事前の記録で固定する（D09 §5.2）。

| `HYPOTHESIS`（仮説の変更） | 許さない | 許さない | 許す（新しい実験名。仮置き 8） |
| 1 回に使う種類の数 | 1 つ | 1 つ | 1 つ |

- **どの候補でも許さないもの**: `POLICY_REVISION`（評価基準の改訂。全実験の物差しが変わる。D09 §10.11）、`DATA`（データの版の変更。新しい snapshot は順 5 の外）、新しい部品（D05 の設計が要る）、比較の前提の変更（読込で拒否される）、日足 60 本より長い履歴窓（研究ポリシーの新しい版が要る）、時刻の規則・無記録の扱いの変更（D12-89）。必要になったら第9節のとおり止める。`RETRY` は改善ではない（途中停止の再実行だけ。仮置き 11）。
- 推奨 (a) の理由: 1 種類に限ると、結果の差を 1 つの変更に結びつけて説明できる（終了条件）。格子の変更だけ (b) では、H1 のように「条件を足す」改善が書けない。仮説の変更 (c) は「改善」より「別の研究」に近く、一巡の説明が弱くなる。

### 6.2 再評価の回数の上限（D14-6）

| 候補 | 内容 | 影響 |
|---|---|---|
| (a) 1 回【推奨】 | 一巡 = 元の実験 1 本＋改善後 1 本 | 計算は 2 実験分。同じ検証区間を見る回数は 2 回（台帳に数えられる） |
| (b) 最大 2 回 | 改善後をもう一度直してよい | 計算は最大 3 実験分。見る回数が 3 回 |
| (c) 上限を置かず、毎回人間が決める | ― | 終わりが事前に決まらない |

- 推奨 (a) の理由: 順 5 の目的は「一巡を記録から説明できる」ことで、改善の成功ではない。見る回数を増やすほど、同じ区間への適合が進む（D09 §10.10・D13 §7.3）。2 巡目以降が要るなら、順 5 の終了後に人間が改めて決める。

### 6.3 2 回目以降の再評価の手順（D14-6 で (b)・(c) を選んだ場合）【提案】

再評価 1 回ごとに、手順 3〜5 を同じ規則で繰り返す。版を k とすると（元の実験が k = 1）:

1. 手順 3: 版 k の結果の原因分析（担当は D14-3。読む観点は版 k の事前の記録に書いた一覧のまま）。
2. 手順 4: **「版 k の実行記録（台帳の行の担当は D14-11）＋版 k+1 の事前登録（実験設定 `version: k+1`、系譜 `derived_from` = 版 k の実行、変更の種類 1 つ、理由の文）」の PR を 1 本作り、人間が merge する**。版 k+1 の系譜は版 k の台帳の行を読込で確かめるので、同じ PR に置く（仮置き 2 と同じ理由）。
3. 手順 5: merge 後の main から版 k+1 を走らせる（結果を見る前に変更が main に固定されている）。
4. 上限（D14-6）に達するか、人間が「これで終える」と決めたら、最後の版の実行記録と一巡の報告（第7.1節の表を、元と最後の版に加えて途中の版も並べる形）を最後の PR に置く。

- 確認項目 E1・E2・E5（第7.2節）は、すべての版について確かめる（E2 は各版の系譜が直前の版を指すこと）。
- (c)（上限なし）では、続けるかを人間が版ごとに決める。後続の PR の本数は「再評価の回数 + 2」になる。

終了条件【原文】「改善理由と結果の差を記録から説明できる」（D12 §0.1.31）。**成績がよくなったかは終了条件に入れない**（悪化・変化なしでも、理由と差を記録から説明できれば満たす）。

確認項目【提案】:

| 番号 | 確認項目 | 数値を見ずに機械的に確かめられるか |
|---|---|---|
| E1 | 元と改善後の実験の事前の記録が、それぞれの実行より前に main にある（記録票の `git_commit` が事前登録の PR の merge 後のコミットで、`git_dirty` が false） | できる |

## 8. 実行環境と所要時間（要決定 D14-9・D14-10）

### 8.1 run の本数【導出】

1 回の実行で両組を評価する（D13-15）。1 つの組の中で、fold 5 つの選定区間（728 日）の run を全試行 N について、検証区間の run（独立口座。選ばれた試行だけ）を fold ごとに 1 本、連続口座の経路の区間の run を最大 5 本（同じ試行が続く区間は 1 本にまとまる。D13-22）走らせる（D09 §5.4、D13 §4.6）。

- run の本数（1 実験）= 2 組 ×（5N + 5 + 最大 5）
- 模擬する日数（1 実験）= 2 組 ×（5 × N × 728 + 検証の合計 1,743 + 経路 1,743）日（検証の合計は D13 §5.1 の 287 + 4 × 364）

### 8.2 所要時間の見積り【導出、仮定付き】

**仮定**（仮置き 12）: run の時間は模擬する日数に比例する。速さは順 3 の実測から、検証戦略 A 並み = 約 0.60 秒/日（1,527 秒 ÷ 2,553 日。両組の平均）、B 並み = 約 1.32 秒/日（3,359 秒 ÷ 2,553 日）。run ごとの固定の時間（snapshot の読み込みなど）は測っていない。固定の時間が run 1 本あたり t 秒あれば、下の値に「run の本数 × t」を足す（例: t = 60 秒なら 4 試行で +1 時間、6 試行で +1.3 時間）。評価・レポートの時間は run に比べて小さいと仮定した。

| 試行数 N | run の本数 | 模擬する日数 | A 並み（H1） | B 並み（H2・H3） |
|---|---|---|---|---|
| 4 | 最大 60 | 36,092 | 約 6.0 時間 | 約 13.2 時間 |
| 6 | 最大 80 | 50,652 | 約 8.4 時間 | 約 18.5 時間 |
| 9 | 最大 110 | 72,492 | 約 12.0 時間 | 約 26.5 時間 |
| 12 | 最大 140 | 94,332 | 約 15.7 時間 | 約 34.5 時間 |

- **一巡の計算**（D14-6 (a) の 2 実験）: 推奨の組み合わせ（H1・6 試行）で約 17 時間（夜間 2 回）。H2・H3（4 試行）で約 26 時間。D14-10 (a) の再現を足すと、元の実験 1 本分の約 8〜9 割（再現は原因分析と並行に走らせるので、待ち時間には効かない）。
- **一巡の全体**（人間の待ちを含む目安）: 計算に加え、PR 3 本のレビュー（各 1〜3 時間）と原因分析（D14-3 による）で、H1 なら 3〜5 日。
- **メモリ**: 1 プロセスの最大メモリは約 4.5 GB（順 3）。実験と再現を同時に走らせると約 9 GB。D09 §5.4 で 1 実験の中は並列に走らせない。

順 5 での当て方【導出】:
