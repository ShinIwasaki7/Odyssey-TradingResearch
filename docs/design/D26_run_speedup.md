## 3. 改善 2: 標準と候補の組を並列に走らせる【提案】（D26-1 (a)・D26-2 (a)・D26-3 (a)・D26-4 (a) の推奨で書く）

### 3.1 なぜ組ごとか【導出】

- 標準の組と候補の組は、snapshot が違うので同じ `RunId` を持たない（`RunId` は run の設定のダイジェストを材料にし、run の設定は snapshot を持つ。ADR-0006）。2 つの組が同じ snapshot を指す探索の実験は、読込で必ず拒否される（`app/config/experiment_v2.py` の検査「両組は別の snapshot を指す（用途によらない）」、実装 PR の仮置き 54。研究ポリシーの用途が `STANDARD` のときは D13-16 (a) も同じことを求める）。したがって評価の使い回し（`cache`）は組をまたいで当たらない（`execute_search` のコメント「同じ `RunId` の評価は組をまたいで共有する」は、当たる場合に共有するという意味で、両組の `RunId` が違う以上は当たらない）。組どうしの依存は、両組の全 fold と経路が終わった後の「組の判定・集約表・結末記録・台帳の結末の行」だけである（`execute_search`）。

- 並べるのは 2 本だけなので、メモリ 16 GB・4 コアの Mac で動く見込みがある（第3.3節）。fold の中の試行を並べる形（D26-1 (b)）は 4 本以上を並べないと効かず、この Mac ではメモリが足りない見込みが高い。

### 3.2 動き（仮置き 4・6）

1. 親プロセスは今と同じ並び（D09 §10.7）で、事前検査 → 既存の成果物の確認（読むだけ）→ 記録票の保存（事前検査の合否によらず保存し、同じ版の旧い記録は退避する。D09 §11.3）→ 台帳の開始の行 → 束縛の記録までを行う。
2. 親は組ごとに子プロセスを 1 つずつ起こす（計 2 つ）。子は自分の組の読み取り面を組み立て、**今と同じ順序で** fold の単位と経路の区間を走らせ、開始記録・試行記録・選定記録・経路の記録を今と同じファイルに書く（組ごとにディレクトリが分かれている: `search/standard/`・`search/candidate/`）。
3. 子は結果（選定・試行記録・指標・経路の要約・事後検査の結果）を戻り値で親へ返す。
4. 親は両方の子が終わってから、今と同じ順（標準 → 候補）で集約表を書き、結末記録 → 台帳の結末の行 → レポートを書く。
5. 並列か順番かは記録票に入れない。`launch.json`（包みが run の前に書く）には要求した方式だけを書き、空きメモリの確認で順番へ切り替えたかは表示にだけ出す（仮置き 6。結果を変えないので識別子の材料にしない）。
6. D26-3 (a) のとき、`experiment reproduce` も同じ形にする: 親が再現の準備を今と同じに行い、組ごとの子が自分の組の単位・選定・経路の区間を今と同じ順で走らせ直して照合し、照合の行（今の再現の行と同じもの）を親へ返す。親は両方がそろってから、今と同じ順で再現の記録（`reproduction.json`）を書き、終了コード（D07 §21.2。不一致なら今と同じ値）を決める。状態×出来事表は第3.4節と同じ形（終端の書き込みが再現の記録になる）。細部は実装 PR

### 3.3 メモリ（仮置き 5）

- 版 1 の最大メモリは 7.1 GB で、両組の読み取り面を 1 プロセスが持った結果である可能性が高いが、確かめていない。手順 0 で「組 1 つだけを持つプロセスの最大メモリ」を測る。
- 起動前に空きメモリを確かめ、「組 1 つの最大メモリ × 2」に足りなければ今の順番で走らせ、その旨を表示する。測った値は設定の既定値として実装 PR に書く（実行ごとの値ではない）。
- 測った結果、2 本でも 16 GB に収まらないと分かった場合は、実装に進まず人間に報告する（メモリを減らす変更は本書の範囲の外）。
- 空きメモリの確認は、記録票の保存より前（何も書く前）に 1 回だけ行う。足りずに今の順番へ切り替えても、書いたものは無い。

**手順 0 の結果（2026-11-16）**: 組 1 つだけを持つプロセスの最大メモリは約 4.4〜4.6 GiB（第1.4節の 4 本。区間の長さでほとんど変わらない）。子 2 つで約 9.3 GiB。

- **親は子を起こす前に、読んだ足を手放す**【既決】（2026-11-16 の人間の決定「親が先に手放す（推奨）」。第0.5節）: 今の準備（`_prepare_search`）は両組の snapshot の足を読む。親がそれを持ったまま子を 2 つ起こすと、合計は約 16 GiB（親 約 6.6 GiB（版 1・版 2 の最大メモリ）+ 子 約 9.3 GiB）になり、この Mac（16 GB）に収まらない。親は SP（束縛の記録まで）を終えた後、子を起こす前に、両組の読み込んだ足・照合の写し・それらを指す読み口への参照を手放す。結果は変わらない（子は自分の組の読み取り面を組み立て直す。第3.2節の 2）。
- 【提案】PR-B で、手放した後の親の最大メモリを測る（Python は手放したメモリをすぐには OS に返さないことがある）。親と子 2 つの合計が 16 GB の中で余裕を持てない（目安: 合計 13 GiB を超える）と分かったら、実装を止めて人間に報告する（上の「16 GB に収まらないと分かった場合」と同じ扱い）。
- 空きメモリの安全弁の値は「組 1 つの最大メモリ（約 4.6 GiB）× 2 + 手放した後の親の最大メモリ」とし、数は PR-B で測って決める（仮置き 5 のとおり実装 PR）。これらの値は D25 に渡す（第3.8節の 5）。

### 3.8 順 11 の設計（D23・D24（案）・D25（案））との関係【既決】＋【提案】

順 11 の計画書 D23（PR #174 で承認済み）と実行器の D25（案。PR #178）は「実験どうしは最大 2 本。1 実験の中は並列にしない（既決）」（D23 §4.2 の段 3・§4.5、D25 §2.5 の残す既決の表）と書き、研究ポリシー第 5 版の D24（案。PR #177）は経路の後に組ごとの局面の成果物を足す。本書の改善 2（1 実験の中の組ごとの並列）とそのまま組み合わせると食い違うので、次のとおりにする。
