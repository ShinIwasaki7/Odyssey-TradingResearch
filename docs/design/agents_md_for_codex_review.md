## 3. AGENTS.md の設計方針

### 3.1 役割分担（重複を作らない）

PR レビュー方針は 2026-09-23 に「レビューの規則は本書だけを直す」と決めた。4 文書に同じ規則を写して収束しなかった反省である。AGENTS.md はこれに従い、**手順を一切書かない**。

| 文書 | 決めること | AGENTS.md との関係 |
|---|---|---|
| PR レビュー方針 | 依頼の仕方、対象範囲の決め方、3 分類と P0〜P2、巡数、終了条件、merge 前提 | AGENTS.md は §3・§3.1 を**参照するだけ**（Codex が指摘に付ける優先度の定義として） |
| D01 | 依存規則・層・ポート・外部ライブラリの配置 | AGENTS.md は「import-linter の外側で確かめること」だけ書き、規則本体は D01 §2.2・§4・§8 を参照 |
| D02〜D08 | 各型・表・手順 | AGENTS.md は「設計文書の該当節を引用して不一致を述べよ」と要求する。個々の型は書かない |
| **AGENTS.md（新設）** | **Codex（と設計適合レビューを行う Claude）が何を・どの形で指摘するか** | 両レーン共通の「レビュー観点の正本」 |

境界の定義: **手順**（レビューの要否、対象範囲の決め方、対象内／対象外／不採用の分類、優先度の定義、巡数、終了条件、merge 前提）は方針文書だけが持ち、AGENTS.md は参照する。**出力の形**（範囲の中だけを指摘する、失敗シナリオと根拠節を添える、同型をまとめる、要決定候補の印）と**観点**（Code Review Rules の各分類）は AGENTS.md が持つ。方針文書はこれらを写さない。

### 3.2 両レーンで同じ規則を使う

Codex は 2026-09-23 に「リポジトリ用の環境を作成してください」と返して一時利用できず、Sonnet の設計適合レビューで代替していた（本 PR で 2026-09-24 に復旧を確認）。AGENTS.md の `## Code Review Rules` を **Claude の設計適合レビュー（方針 §5）でも読ませる**ことで、Codex が使えない期間も同じ観点で検査でき、両レーンの観点が食い違わない。共有するのは**観点**（各分類の規則）と失敗シナリオ・根拠節の書き方であり、「範囲外を報告しない」は Codex の出力形式の制約に由来する Codex 専用の規則である。Claude レーンは方針 §3.1・§5 のとおり対象外・不採用も優先度なしで記録し、範囲外の重大事項はこの経路で拾う（Q6 (a) の前提）。方針 §5 に「観点は AGENTS.md を参照」の 1 行を足す改訂を、AGENTS.md 追加の PR に含める。

### 3.3 置き場・言語・大きさ

| 項目 | 推奨 | 代替案 |
|---|---|---|
| 置き場 | **ルートに 1 本** | パッケージ別に `src/odyssey_fx/<pkg>/AGENTS.md` を足す（近いものが優先される）。今は全体が約 13 KB で足りるため不要。ある節が 3 KB を超えたら分割を検討 |
| 言語 | **日本語本文＋英語の固定見出し**（`## Code Review Rules`、`###` 小見出しに英語の型名） | 全文英語。Codex は日本語を読めるので、リポジトリの他文書と揃える方が保守しやすい |
| 大きさ | **16 KB 以下**を維持（上限 32 KiB の半分。現状約 13 KB） | — |
| 更新の契機 | **同じ型の指摘が 2 本以上の PR で再発したとき**に規則を 1 つ足す。規則には出典 PR 番号を残す | 各 PR ごとに足す（膨らむ） |

### 3.4 書き方の規則（公式の推奨 §1.1 に従う）

- 構成は公式の 3 節: `## Working agreements`（設計が正本・前提を決めない・merge は人間、の約束）、`## Repository expectations`（配置・コマンド・**完了の定義**・PR の期待）、`## Code Review Rules`（`###` で分類）。
- 各レビュー規則は「**指摘すべき振る舞い → 安全な側の書き方または例外 → 根拠の設計節**」の順で 1〜3 行。公式の言い方では「flag する振る舞いと、安全な経路や例外を説明する」。
- 規則は再発した型だけ載せる（出典 PR 番号を付ける）。理屈上ありうるだけの事項は載せない。
- ruff / mypy / lint-imports / pytest が止めるものは書かない（公式: 整形・lint は CI に任せる）。
- 範囲外・不採用の**判定**は Codex に求めない（判定は方針 §3.1 で作業役が行う）。Codex には範囲の中だけを指摘させる（Q6）。
- 16 KB を超えそうになったら、話題ごとの文書への参照に置き換えるか、パッケージ別の AGENTS.md に分ける（公式の分割の勧め）。

## Code Review Rules

### Scope and reporting format

この節は Codex の**出力の形**（何を・どう書くか）だけを定める。範囲の決め方・分類・巡数などの**手順**は方針 §3・§3.1・§4 が正本で、ここには写さない。

- 指摘は PR 本文の「レビュー対象範囲」の**中に限る**。**Codex は範囲外の事項を報告しない**（決定 Q6。Codex の出力は優先度付き指摘しか持てないため）。Claude の設計適合レビュー（方針 §5）はこの行の対象外で、対象外・不採用も優先度なしで記録する（方針 §3.1・§5）。
- 各指摘に **具体的な失敗シナリオ**を添える。形は 2 通りあり、どちらも有効: (a) 入力→誤った出力、(b) **入力／出来事→振る舞いが未定義**（状態×出来事の空欄など。期待動作を創作せず、未定義のまま何が起きるか・何に影響するかを書く）。設計適合の指摘（「設計と違う」「設計に無い」）には **根拠となる設計文書の節**（例: `D06 §4.2 手順 6`）も添え、根拠節を示せない設計適合の指摘は P2 とする。**再現可能な実装バグ（通常入力で例外・誤った値）は設計節の有無に関わらず P1** である（方針 §3）。
- 優先度（P0 / P1 / P2）の定義は `docs/pr_review_policy.md` §3 の表を読んで付ける。ここには写さない。
- 同じ型の指摘が複数箇所にあるときは、代表 1 件に他の箇所を列挙してまとめる。
- 承認済みの ADR・設計文書の決定に反する提案はしない。設計側に直すべき点があるなら、**本文の先頭に「要決定候補」と書く。優先度は方針 §3 のとおり付け、この印で下げない**（設計判断の要否と優先度は独立。P0/P1 からも要決定は生じる。方針 §4.3）。

### Conformance to the approved design (A)

- 設計文書が定める **記録の表・列・主キー**（判断履歴の表は D06 §9.2。段階2 で 15 表、段階3 で 19 表。run manifest は D06 §9.3、result.json は D06 §9.4、評価 5 表と評価 manifest は D07 §8）がすべて書かれるか。**0 行でも列とその型が残る**か（PR #19）。
- manifest・ダイジェスト・根拠記録に、設計が列挙する項目（市場／評価／口座 snapshot、能力検査結果、換算経路、下位足の参照）がすべて入るか（PR #19）。
- 設計のフェーズ順（D06 §4.1 の rank 順・§4.2 の手順番号）どおりに処理されるか（例: 足欠損検査は期限切れ処理より前）（PR #19）。
- コンパイル後に宣言の制約（warmup 等の時刻制約、有効性束縛）が失われないか（PR #18）。
- 実装が設計に無い振る舞いを決めていたら、PR 本文の仮置き一覧に載っているかを確かめ、無ければ P1 で「仮置き未記載」と指摘する。
- 段階を閉じる PR（PR 本文が「段階 N の完了」を掲げるもの）では、**段階の完了条件**（全体計画書 §8.2）が受入テスト（`tests/acceptance/`、D08）で 1 件ずつ示されているか。示されていない条件は P1。

### Determinism and reproducibility (F)

- **ダイジェスト／ハッシュの入力**が、設計文書の入力一覧と一致するか。新しいフィールドの取りこぼし、タプル・集合の順序未正規化、格納順依存を疑う（PR #14・#16・#19・#20）。
- 処理点 `ProcessingPoint` の組 `(time, phase.rank, sequence)` が run 内で一意か（D02 §3.3。`sequence` は判断時刻ごと・フェーズごとに 0 から採番されるので、数値単独の重複は正常）。同じ時刻・同じフェーズで組が衝突する経路（RUN_END、約定後の評価）を疑う（PR #19）。
- domain / application が実時計・乱数・環境変数を読んでいないか（D01 §2.2 規則 2）。
- 主キーの重複が黙って後勝ちにならないか。重複判定が型変換後の値で行われるか（PR #20）。

### Lookahead and time (P0)

- 判断時点で公開されていない情報（`available_at` より後の足、未承認 manifest、未記録 partition）を参照していないか（PR #7）。
- 公開遅延・DST 境界・週末／祝日の扱いが D03 の規則と一致するか。エントリー用の遅延を決済要求に流用していないか（PR #19）。

### Types, invariants and numerics (E)

- `Price`/`Quantity`/`Money`・台帳は Decimal、Feature は float。`Decimal(float)` と、グローバルな Decimal context への依存を禁じる（ADR-0012、D02）。
- 通貨・単位が異なる値の演算が素通りしないか（手数料通貨、口座通貨と決済通貨）（PR #19）。
- `frozen=True` の dataclass の中身（list / dict）が可変のまま公開されていないか（PR #6）。
- 売買方向で参照価格（bid / ask）とスプレッドの適用が対称か。二重加算が無いか（PR #19）。
- 検証の正規表現が `fullmatch` か。`$` は末尾改行を許す（PR #6）。

### Missing data, failures and overwrites (J)

- 構造エラーは例外で止め、入力欠損は `MissingInputPolicy` で扱う。**例外を欠損に読み替えない**（D01 §2.2 規則 5）。
- 表・必須列の欠落は、**検査結果の表に観測値として残す**（D07 §4.3・§10.2 が定める範囲）。例外で診断が消えて評価が「完了」にならないか（PR #20）。値の解釈失敗（null・型不一致）を同じ検査へ寄せる扱いは現時点では仮置き（`evaluate_run.py`）であり、**対応する D07（と D06）の改訂が承認・導入されるまでこの規則の対象にしない**（R5 は承認済みだが未実施）。
- 既存の成果物を**検査せずに上書きしていないか**。既定は「存在すれば失敗」。**確定済み snapshot は常に失敗**（D03 §3.7.1）。**run 成果物 `runs/<run_id>/` は明示の置換指示（`replace=True`）があり、旧 manifest を残す場合だけ置換できる**（ADR-0006）。この正当な置換経路を違反として報告しない（PR #10・#19）。
- ID 不一致・能力検査の失敗が、書き込みの**前**に検出されるか（PR #19・#20）。

### Architecture beyond import-linter (D)

- DataFrame・`numpy.ndarray` 等の外部ライブラリ型が domain / application の引数・戻り値・**状態**・記録に出ていないか（D01 §2.2 規則 1）。状態付き部品（`strategy.catalog`）が内部状態に `numpy.ndarray` を持つのも違反（D01 §5.1）。
- ポートは利用側の application が `Protocol` で定義し、実装者はそれを import せず構造的に満たすか（D01 §4）。**例外**: 実際の利用側が application より下の層なら、構造をその層で定義し application が同じ名前で再公開する（D01 §4 v2.4。`backtest.engine.loop` の `PublicationFeed` / `ExecutionSeries` / `IntrabarSeries` / `Calendar` が該当）。この形を「application に定義されていない」と指摘しない。
- `adapters` / `application` の型を `__init__.py` で再エクスポートしていないか（D01 §8）。
- Pydantic モデルが `app.config` の外へ流出していないか（D01 §2.2 規則 6）。

### Tests (G)

この節は**実装 PR だけ**に適用する（設計文書 PR には適用しない。設計→合意→実装の順序のため、承認前の設計にテストは存在しない）。

- **その PR が実装する**設計の規則（状態遷移・不変条件・手順）に対応するテストが `tests/` の該当層（D01 §9、D08）にあるか。PR の範囲外の規則や、D08 §13 が後続作業として挙げる既知の未整備テストは指摘しない。
- golden / property テストが**実際に値を比較している**か。比較を省略して通しているテストを指摘する（PR #20）。
- 受入テストが人工データで受入れ→run→評価を 1 本通しているか（D08）。

### Design-document PRs

状態×出来事表と値の伝播の規則は、**状態機械や実行時の値の伝播を定める節を持つ文書だけ**に適用する（該当例: D03 §3.7.1 の snapshot の段階、D04〜D07、紙上トレース。非該当例: D01・D02・D08）。文書が §1.2 に「状態×出来事表: 該当なし（理由）」と書いていれば、その表を要求しない。

- §1.2 境界表（決めること／委ねること／受け取ること）と本文が一致するか。表の外の事項を本文が決めていないか。
- 複数部品をまたぐ値（機会 ID・区間・建玉 ID・run_id）の**伝播規則と記録先**が書かれているか（PR #14〜#16）。
