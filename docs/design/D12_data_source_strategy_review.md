### 1.4 今の土台（HistData の 1 分足）の事実（研究期間、時刻の列だけ）

案 R で HistData を単一の提供元にする場合と、案 M の土台の両方に関わるので、手元の HistData の 1 分足（`data/raw/histdata/<ペア>/HISTDATA_COM_ASCII_<ペア>_M1<年>/DAT_ASCII_<ペア>_M1_<年>.csv`）を、**各行の先頭の時刻の欄だけ**読んで数えた（価格の列は読んでいない）。v0.2 案では、取引カレンダー `fx_ny17` の週の中の 1 分ごとに数え、長さを問わずすべての空白を数えた（第8.2節。v0.1 案の「24 時間以上の空白を数えない」集計は撤回した）。

- 【事実】2023 年は 8 ペアすべてで、**2 月〜7 月に 1 時間前後の空白が多数**ある。週の中の分の欠けは 2023 年が 13.7〜14.4%、2017〜2022 年は 0.47〜2.75%（ラベルをニューヨークの現地時刻として読んだ場合。第5.2節、付録 D-4）。USDJPY の 2023 年 3 月（2023-03-05 22:00Z〜03-31 21:00Z）は 29.52%（付録 D-2）。
- これは旧基盤が 2023-01-29〜07-30 の週に Dukascopy 由来の足を混ぜた期間（監査 §2.3）と重なる。**HistData を単一の提供元にすると、2023 年 2〜7 月は必要な足が欠け、実行できない見込みが高い**（第4.1節の Q6）。
- **時刻の基準が公表仕様と全週では合わない**: 公表仕様は EST 固定（夏時間なし）だが、そのとおりに UTC に直すと米国の夏時間の週ごとに週の始めの 60 分が欠け、金曜の閉場の後に約 60 分がはみ出す。ラベルをニューヨークの現地時刻として読むと 2017〜2018 年は合うが、2019 年以降は合わない週がある（第8.2節、付録 D-4。監査 §2.2 の推定と同じ傾向）。
- 2020-11-30 と 2021-05-31（どちらも月曜）に 19〜20 時間の空白がある（8 ペアとも。付録 C-1・D-4）。この 2 か所は既存の補充で Dukascopy の tick から埋めた区間である【事実】`docs/data/refill_trial_2026-10-01.md` §3 の計画 A・B。休場かどうかの判定は本書ではしていない。

2. **再現性**: 元ファイルのハッシュ・取得日時・取得の道具の版・集約規則の版を manifest に残し、同じ元ファイルから同じ snapshot が作れること。提供元が過去データを差し替える可能性に備え、元ファイルは非公開の場所に保存する（第7節）。

## 4. 初期版を「品質基準を満たす連続期間だけ実行する」構成に絞る場合の設計変更案と PR #80 の扱い

### 4.1 品質条件【提案】（要決定 D12-4。v0.2 で改めた）

**基本の方針**（人間の指示「品質条件は、基準を満たす期間を長くするために緩めない。初期版は必要な入力が欠ける期間では実行しない方針を基本とする。」）:

1. **初期版は、戦略が必要とする入力が 1 本でも欠ける期間では実行しない**。「必要な入力」は、戦略の宣言が読む全時間足の足（例: 15 分足・1 時間足と、1 時間足から作る日足）と、各 run の開始より前のウォームアップの足（第4.2節）である。
2. **品質条件は、連続期間の長さを見て変えない**。条件を変えるのは、時刻の基準や価格種別などの事実が新たに分かったときだけで、変えるときは新しい版として理由を記録する。長さを理由にした許容幅の追加・閾値の緩和はしない。
3. **補正や条件の緩和で採用しない**（人間の指示）。元データに違反（例: ask < bid）があり原因が分からない提供元は、違反を直したり除いたりして使わない。原因と影響が分かるまで採用しない（第8.1節）。

**必須条件（1 件でも違反があれば、その足を含む期間では実行しない）**

| # | 項目 | 測り方 |
|---|---|---|
| Q1 | 時刻の基準が文書と元ファイルで一致する | 提供元の公表仕様（UTC か、夏時間の扱い、足の始点か終点か）と、週の最初と最後のデータの位置（ニューヨーク日曜 17:00〜金曜 17:00 の週）が合う。合わない週・判定できない週は違反。**HistData は公表仕様（EST 固定）どおりでない週がある**（第8.2節）ので、この条件を満たさない週がある |
| Q2 | 価格種別が 1 つに揃う | 系列の全期間で同じ価格種別（例: bid）。提供元の文書と元ファイルの列で識別できること |
| Q3 | 重複が無い | 同じ時刻の足の重複 0 件（tick の提供元は、同じ時刻の tick の扱いを文書か元ファイルで確かめる。OANDA のサンプルには同じ内容の行の連続がある。付録 D-1） |
| Q4 | 価格の大小関係 | 高値 ≥ 始値・終値 ≥ 安値。bid と ask を両方持つ場合は ask ≥ bid（始値・高値・安値・終値のすべて、全件） |
| Q5 | 出所が 1 つ | その期間のすべての足が、同じ提供元・同じ取得形式の元ファイルから来ている（manifest の記録で確かめる） |
| Q6 | 必要な足が作れる | 戦略が読む全時間足の足が、その区間に元データ（tick または 1 分足）を 1 件以上持ち、作れること。1 本でも作れなければ、その足を必要とする期間では実行しない（休場の宣言の中を除く） |
| Q7 | 休場との整合 | カレンダーの休場の宣言の中にデータがある件数が 0 件。ある場合は、休場の宣言か元データのどちらかを調べ、解けるまでその期間では実行しない |

**記録するが、実行の可否には使わない値（診断の値）**: 1 分ごとの欠けの割合、週の中の最長の空白、tick の件数の分布、同じ分の提供元間の価格差。これらは提供元の比較（第5節・第8.2節）と、足の作り方の説明に使う。**実行の可否の条件に足すかは人間が決める**（足すときは、期間の長さを見る前に決め、緩めない）。

v0.1 案からの変更: v0.1 案は程度の基準（欠落率・最長の空白など）の閾値を「分布表を見て人間が決める」としていた。人間の指示に合わせ、実行の可否は必須条件と「必要な足が作れるか」だけで決め、程度の値は診断に回した。

### 4.2 連続期間の決め方【提案】（要決定 D12-5。v0.2 で改めた）

人間の指示: 「連続期間は、戦略が必要とする全時間足とウォームアップを合わせて算出する。最長区間が短い場合は、研究に十分かを別に判断する。」

**入力**（戦略の成績は使わない）:

1. **戦略が必要とする時間足**: 研究の対象とする全戦略の宣言（`configs/strategies/*.yaml`）が読む系列の集合。例: 検証戦略 B は USDJPY の 15 分足・1 時間足・日足（`1d_ny17`。1 時間足から作る）を読む【事実】`configs/strategies/strategy_b_v1.yaml`。日足は 1 時間足から作り、構成する 1 時間足が 1 本でも欠ければ作られない（D09 §17.8.3）。
2. **ウォームアップの長さ**: 全戦略の履歴窓の最大（D09 §17.8.5 の段 3-2 の決定 c「全戦略の履歴窓の最大から機械的に決める」と同じ）。今の 2 つの検証戦略では、検証戦略 B の日足の EMA の 60 本が最大【事実】D09 §17.8.5。

**手順**:

1. 系列ごと（ペア）に、必要な全時間足の足について第4.1節の必須条件 Q1〜Q7 を判定する。
2. 必要な足が 1 本でも欠ける（または違反する）時刻で、期間を切る。休場の宣言の中は切らない（休場の宣言は根拠のあるものだけ。D11 §2 の休場の定義と D03 §3.4.2 の根拠の規則）。
3. 切った各区間の始めから、ウォームアップに要る足（例: 完全な日足 60 本）を数え、その終わりを「実行できる区間の始まり」とする（D09 §17.8.5 の手順 4 と同じ数え方）。
4. 実行できる区間の始まりと終わりを、D09 §17.8.5 の規則（土曜 12:00Z に揃える）で揃え、最長の区間を出す。複数の区間はすべて一覧にする。
5. 戦略が増えて必要な時間足や履歴窓の最大が変わったら、同じ手順で算出し直し、新しい版として記録する（D09 §17.8.5 の版の規則と同じ）。

**研究に十分かの判断**（要決定 D12-13）: 手順 4 で出た最長の区間が短い場合（例: D09 §17.8.5 の安全弁「2 年未満、または 2018 年の 1 年に収まる」に当たる場合）は、その区間を登録せず、**研究に十分かを人間が別に判断する**。判断の材料は、区間の長さ・含む年と相場の時期・区間の数であり、戦略の成績は使わない。条件を緩めて区間を伸ばすことは選択肢に入れない（第4.1節の 2）。

**複数のペアをまたぐ研究**: 複数のペアを同時に読む戦略が加わったら、そのペアすべての必要な足で手順 1〜4 を行う（ペアごとの区間の共通部分になる）。

今の暫定の評価範囲（826 日、2020-03-21〜2022-06-25。D09 §17.8.5）は旧 snapshot の値として記録に残し、新しい snapshot の連続期間で置き換えるかを人間が決める（要決定 D12-12）。

|---|---|---|
| 列 | `DateTime,BidOpen,BidHigh,BidLow,BidClose,AskOpen,AskHigh,AskLow,AskClose`。出来高の列は無い | 付録 A-3 |
| 時刻 | README は UTC。週の最初と最後の足の位置はニューヨーク 17:00 に合う。同じ UTC の分で HistData・OANDA と bid の終値を比べると、ずらし 0 分のときに差が最小（中央値 0.10 pip。±1 分で 0.50 pip、±60 分で 4.00 pip）。**時刻のずれは原因ではない** | 付録 A-3・D-2 |
| 集約の仕様（元レコードから） | **始値は常に直前の足の終値と同じ**（直前の足がある足のすべて。2019 年の週 11 で 7,187 本、2023 年の週 11 で 7,154 本。bid・ask とも）。始値はその分の最初の気配ではない。始値の逆転の件数が終値の逆転の件数と毎週同じなのはこのため | 付録 D-3 |
| 逆転の範囲 | 始値・高値・安値・終値の 4 つすべてに逆転がある（例: 2019 年の週 12 は終値 61・高値 75・安値 77 本）。高値・安値の逆転は、同じ時刻の bid と ask から作った足では起きない（ask の高値は、bid が高値を付けた時の ask 以上のはずなので）。**bid の足と ask の足が、同じ気配の組から作られていない**ことを示す | 付録 D-3 |
| 大きさ・時間帯 | 逆転の大きさは中央値 0.1 pip、最大 1.6 pip。時間帯は週によって散らばる（2019 年の週 12 は UTC 21 時台に 30 本で最多） | 付録 D-3 |
| 年による違い | 各年の週 11 の USDJPY で、逆転のある足: 2017 年 154・2018 年 522・2019 年 116・2020 年 225・2021 年 265・**2022 年 0・2023 年 0** 本。2022 年以後で集約の方法が変わった可能性がある（【未確認】。週 11 だけの観察） | 付録 D-3 |
| 他社の同じ分 | 2019 年の週 9〜13 に FXCM で逆転した足のうち、OANDA のサンプルに同じ UTC の分がある 618 本で、OANDA の tick の ask − bid は一度も負にならなかった（その分の最小のスプレッドが負の分 0） | 付録 D-3 |
| 公表されている仕様 | README: "Data points are indicative and based on the lowest spreads available exclusively on Active Trader accounts"。集約の方法（どの気配の bid と ask を組み合わせるか）の記述は見つからない | 付録 A-3 |

**原因の仮説（どれも【未確認】）**: (1) 「最も狭いスプレッド」に基づくと書かれているので、bid と ask を別々の気配の出し手から取って組み合わせ、交差（ask < bid）が起きた。(2) bid の足と ask の足を別々の流れから集約し、時刻のずれた気配が混ざった。確かめるには FXCM の tick（ログインかメールでの依頼が要る。問い合わせに当たるので人間の判断）か、集約の仕様の文書が要る。

**研究への影響**:

1. 第4.1節の必須条件 Q4（ask ≥ bid）に、2017〜2021 年の観察した週はすべて違反する。条件を緩めなければ、FXCM の 2017〜2021 年は実行できる期間にならない見込み（全週は未確認）。
2. bid だけを使う戦略でも、bid の足が「どの気配の bid か」が分からないので、時刻・価格種別の根拠（Q1・Q2）を満たすとは言えない。
3. ask を執行の費用（スプレッド）の根拠に使えない。
4. 始値が「その分の最初の気配」ではないので、tick から作る足（始値はその区間の最初の気配）とは足の意味が違う。FXCM を採るなら、足の定義をこの仕様に合わせて文書にする必要がある。

### 8.2 「各社の空白を、同じUTC区間と取引カレンダーで比較する。24時間以上の空白も、根拠なく集計対象外にしない。」

**結論: 同じ UTC 区間・同じ取引カレンダーで比べ直した。2019 年 3 月は OANDA の欠けが 30,120 分のうち 1 分で最も少ない。2023 年 3 月は HistData の欠けが 29.52%、FXCM は 0.69%。v0.1 案の「24 時間以上の空白を数えない」集計は撤回し、休場の宣言に重なる空白も数えた上で印を付けた**。

比べ方（付録 D-2）: 取引カレンダー `fx_ny17` の週（ニューヨーク日曜 17:00〜金曜 17:00）の中の 1 分ごとに、各社のデータ（1 分足、OANDA は tick を 1 分に集めたもの）があるかを数えた。空白は長さを問わずすべて数えた。比べた 2 つの区間には、カレンダー版 2 の休場の宣言は無い。

| UTC 区間 | 期待する分 | OANDA（tick） | FXCM（1 分足） | HistData（1 分足、公表仕様の EST 固定で UTC に直す） |
|---|---|---|---|---|
| 2019-03-01 00:00Z〜03-29 21:00Z | 30,120 | 欠け **1 分**（0.00%）。15 分以上の空白 0 | 欠け 96 分（0.32%）。15 分以上 0、最長 11 分 | 欠け 96 分（0.32%）。15 分以上 1（03-10 21:00Z から 60 分）|
| 2023-03-05 22:00Z〜03-31 21:00Z | 28,800 | 未取得 | 欠け 199 分（0.69%）。15 分以上 1（17 分） | 欠け **8,502 分（29.52%）**。15 分以上 124、最長 240 分 |

**HistData の年ごとの表（2017〜2023、8 ペア、取引カレンダーの週の中。時刻の列だけ）**は付録 D-4 に置いた。要点:

- 公表仕様の EST 固定で UTC に直すと、米国の夏時間の週ごとに、週の始めの 60 分が欠け、金曜 17:00（ニューヨーク）の後に約 60 分のデータがはみ出す（USDJPY の 2019 年ではみ出しは 1,799 行、すべて金曜の 17 時台）。ラベルをニューヨークの現地時刻（夏時間あり）として読むと、2017〜2018 年ははみ出し 0 行で合うが、2019 年以降は年 55〜240 行がはみ出す。**HistData の時刻は、公表仕様にもどちらの単一の規則にも、全週では合わない**（監査 §2.2 の推定と同じ傾向）。第4.1節の必須条件 Q1 に違反する週がある。
- 24 時間以上の空白: ニューヨークの現地時刻で読んだ場合、8 ペアとも 2017 年に 1 件（USDJPY は 2017-12-24T22:00Z から 1,440 分。カレンダー版 2 のクリスマスの宣言と重なる）。休場の宣言に重なる 15 分以上の空白は年 0〜3 件で、数えた上で印を付けた（付録 D-4 の列 `gaps_overlapping_v2_closure`）。宣言に重ならない長い空白もある（例: USDJPY 2020-11-30T05:00Z から 1,140 分、2021-05-31T04:00Z から 1,200 分、2023-04-07T00:00Z から 1,380 分）。
- 2023 年は 8 ペアとも欠けが 13.7〜14.4%（ニューヨーク現地時刻で読んだ場合）。

**v0.1 案の表の扱い**: v0.1 案の第1.4節・第5.2節の表（隣の行との差が 24 時間以上を数えない集計）は、人間の指示により撤回し、上の比べ方に置き換えた（第1.4節・第5.2節）。

### 8.4 「品質条件は、基準を満たす期間を長くするために緩めない。初期版は必要な入力が欠ける期間では実行しない方針を基本とする。」

**結論: 第4.1節を改めた**。実行の可否は必須条件 Q1〜Q7（「必要な足が作れる」を含む）だけで決め、1 本でも欠ける・1 件でも違反する期間では実行しない。条件は期間の長さを見て変えない。分単位の欠けの割合などの程度の値は、実行の可否に使わない診断の値にした。

### 8.5 「連続期間は、戦略が必要とする全時間足とウォームアップを合わせて算出する。最長区間が短い場合は、研究に十分かを別に判断する。」

**結論: 第4.2節を改めた**。必要な時間足は戦略の宣言から、ウォームアップの長さは全戦略の履歴窓の最大（D09 §17.8.5 の決定 c）から取り、全時間足の必要な足がそろう区間からウォームアップを引いて最長の区間を出す。最長の区間が短いときは登録せず、研究に十分かを新しい要決定 D12-13 で人間が判断する。
