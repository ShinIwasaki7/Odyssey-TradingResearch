# 新 FX 研究基盤：戦略部品・バックテスト・評価の設計と構築計画

作成日: 2026-09-17  
更新日: 2026-09-18  
状態: 会話で合意した設計方針と、次の設計作業への引き継ぎ。詳細仕様・実装完了を意味しない。

## 1. 目的と読み方

新しいリポジトリに、FX 戦略を役割ごとの部品として定義し、再現可能なバックテストと評価を行う基盤を一から構築する。本書だけを読んだ別セッションでも、合意済みの前提を繰り返し議論せず、未決定の契約設計から作業を続けられるようにする。

基本方針は次のとおり。

1. 戦略アーキテクチャ・バックテスト基盤・評価基盤の3つの契約を先に設計する。
2. 「戦略定義 → バックテスト → 単一実行の評価」が通る最小構成を作る。
3. MTF（マルチタイムフレーム）と後続確認を使う戦略で部品境界を検証する。
4. その後、探索・時系列評価・注文や建玉の能力を広げる。

以下の「合意済み」は会話で採用された方針。「推奨」「案」「要決定」は、実装前に具体化する事項である。「確定」と記載した型名・フィールド・責務を正本とし、補助型の内部フィールドや設定例は明記された範囲を除き詳細設計の対象とする。本書は旧リポジトリのファイル・コード・設計資料へのアクセスを必要としない。

## 2. 合意済みの前提と対象範囲

- 対象は **FX トレードのみ**。他資産への一般化は目的にしない。
- 実装言語はPythonを想定する。具体的なライブラリは未決定。
- 使用データは、旧FX研究基盤で使用していた既存データを再利用する。データの内容と受入れ条件は第3節に記載する。
- 戦略コードだけでなく、バックテスト基盤と評価基盤も刷新する。
- 旧基盤との API 互換・クラス構造・評価方式の継承を前提にしない。
- 戦略を Feature / MarketState / Trigger / ExecutionFilter / Order / Protection / Exit などに分解する方針を維持する。
- 各部品は **入力データ・評価タイミング・出力**を明示する。
- 戦略の役割は `StrategyDefinition` の名前付きフィールドで指定し、内部計算は型付き部品の接続で表す。`ComponentInstance` に `role` を持たせない。
- 1つの役割に1つの時間足を固定しない。1部品が複数時間足を参照できる。
- 利用可能時刻による先読み防止、情報を持つ取引機会、条件・イベントの合成を採用する。
- 注文意図と約定処理、注文・約定・建玉・資金管理の責務を分離する。
- 初期の研究ポリシーは **共通の1種類**。将来複数に増やせる参照構造を持つ。
- 計算資源節約を主目的とする厳しい条件数・時間足数・探索パラメータ数の上限は、初期には設けない。
- 再現性・先読み防止・事前固定・探索履歴の記録は維持する。計算量への寛容さと評価規律は別である。

本書は新基盤の設計であり、旧基盤の仕様を変更するものではない。ライブ発注・本番移行・既存戦略の自動移植は初期の対象外。

## 3. 再利用する FX データの前提

### 3.1 引き継ぐデータの内容

| 項目 | 現状と新基盤への含意 |
|---|---|
| 保存形式 | 通貨ペア・時間足ごとの結合済みCSV。時刻と始値・高値・安値・終値・volumeを持つ |
| 読み込み | 既存の結合済み1時間足CSVが主な入力。旧基盤には元データから生成する経路もあるが、新基盤でどちらを採用するかはデータ受入れ時に固定する |
| 時間足 | 1h から4h・1dを生成。15mは対応する merged ファイルがある場合に読み込む。1hから15mを復元しているわけではない |
| 上位足 | 4h・1dはニューヨーク現地時刻の17時を基準に集約。夏冬時間で UTC 境界が変わる |
| 時刻 | tz-aware UTC。既存足は開始ラベルを用いる。集約足のラベルは実装上、バケット内の最初の観測時刻 |
| 価格系列 | 主にbid（売却側の提示価格）基準のOHLC。HistData由来のデータとDukascopyによる補完がある。TradingView由来のデータを結合する経路も存在していたため、採用ファイルごとに出所と価格基準を確認する |
| volume | HistData 由来は実質0とされる。0を真の市場出来高と解釈しない |
| 期間 | 既存データの概ねの範囲は2016〜2025年。実際の対象ペア・期間・欠損・出所は採用スナップショットごとに検査する |
| 補助データ | 政策金利などの別系列・opt-in 経路が存在する。初期の必須入力にはしない。使用時は利用可能時刻と鮮度を別途定義する |

旧基盤の棚卸しでは、AUDJPY、AUDUSD、EURGBP、EURJPY、EURUSD、GBPJPY、GBPUSD、USDCAD、USDCHF、USDJPYがデータ保有対象として挙げられていた。ただし、全CSVの品質・期間・価格基準を監査済みという意味ではなく、初版で全ペアを評価対象にする決定でもない。新基盤は引き渡されたデータを検査し、利用可能なペア・期間・時間足を確定する。通貨ペアの表記はUSDJPYのように区切り文字なしで統一する。

### 3.2 足生成と入力データの意味

入力CSVの論理項目は時刻、`open`、`high`、`low`、`close`、`volume`である。出所を表す付加情報が含まれる場合は、価格計算の入力と分離して履歴に保存する。実際の列名・時刻の書式・欠損表現は受入れ時に確認し、新基盤の内部形式へ明示的に変換する。

1時間足から上位足を生成するときは、ニューヨーク現地時刻で区間を定義する。日足は17時から翌日17時、4時間足は17時・21時・翌1時・5時・9時・13時を起点とする。各区間の始値は最初の観測の始値、高値は最大値、安値は最小値、終値は最後の観測の終値、volumeは合計値とする。夏時間・冬時間を含むタイムゾーン規則で境界をUTCへ変換し、日足を常に固定24時間の加算だけで生成しない。

区間開始時刻と最初の観測時刻は分けて扱う。途中欠損や区間末尾の欠損を無視して完全な足とみなさず、不完全足を採用・除外する規則を決める。元のOHLCと変換後のOHLCを照合し、解釈の変更を追跡できるようにする。

旧データではHistData由来の時刻にニューヨーク現地時刻からUTCへの変換が行われ、Dukascopy由来の時刻は元からUTCとして扱われていた。新基盤は変換済みCSVをUTCとして受け取るか、元データの時刻規約に従って変換するかを入力単位で固定する。どちらか不明な入力を時刻の見た目だけで推測して読み込まない。

### 3.3 新基盤のデータ受入れで設計する事項

- 原データを上書きせず、読み取り専用のデータ供給または複製とスナップショット manifest で固定する。
- manifest にファイル digest、出所、銘柄、価格基準、期間、行数、時間帯・足境界・欠損処理・変換コードの版を記録する。
- UTC へ変換済みのファイルに元データ用の時差補正を再適用しない。
- 既存の集約方法を検証用に再現した後、新しい足生成規則へ変更する場合は別バージョンとする。
- `bar_start`、`bar_end`、`available_at` を明示する。欠損で最初の観測が遅れた場合、既存 index だけから本来の足境界を無条件に推定しない。
- DST、週末、短いセッション、不完全足、重複、欠損、銘柄間の時刻ずれを検査する。
- 15mより細かい市場データの存在を前提にしない。5mやtickを使う戦略・執行モデルは、別途データがなければ実行不可。
- bid OHLC だけから実測 ask や tick 内経路を復元したことにしない。必要な spread や足内経路はモデル上の仮定として記録する。
- 政策金利差をブローカーの実際の swap と同一視しない。

旧基盤では2016〜2023年を研究期間、2024〜2025年を最終評価専用の封印期間としていた。データ移管時には実際の閲覧・使用履歴も引き継ぐ。リポジトリを新設しても、既に観測した期間が未観測holdoutに戻るわけではない。従来の封印期間を設計作業や動作確認のために開かず、新基盤の分割・アクセス規則を明示する。新基盤でも同じ期間分割を恒久採用するかは未決定である。

## 4. 戦略を役割ごとの部品で定義する

### 4.1 役割と出力の意味

| 部品 | 責務 | 出力の例 |
|---|---|---|
| Feature | 判断に使う観測値を計算する | EMA、ATR、確定高値、セッション状態 |
| MarketState | 取引を許可する継続状態を判定する | 方向別の取引許可状態 |
| Trigger | 新しい取引機会を検出する | ID・方向・時刻・根拠水準を持つ取引機会 |
| ExecutionFilter | 発生済みの取引機会について、後続の確認を行う | 確認成立、未成立とその根拠 |
| Order | 注文の種類・価格条件・有効条件などの意図を作る | 注文要求 |
| Protection | 初期の損切り水準などを決める | 絶対価格のストップ水準 |
| Exit | 保有後の決済や保護水準変更を判断する | 決済要求、ストップ更新要求 |

ATR倍率やpipsは計算の入力にできるが、注文・保護水準の境界では解決済みの絶対価格を明示する。TimeExit は期間による Exit として位置付ける。戦略の名前付きフィールドと必須性は第4.3.5節を正本とする。内部の部品数は旧基盤の上限を自動継承しない。

資金管理は戦略の優位性探索から分離する。Protection が決める「損切り位置」と、資金管理が決める「その距離に対して持てる数量」は別責務である。

### 4.2 Trigger と ExecutionFilter

Trigger は「機会の発生」、ExecutionFilter は「その機会を記憶したうえで、後から発注条件が整ったかの確認」である。

例: 1hで高値突破を検出し、同時刻に確定した15m足、またはその後の15m確定時に確認条件が成立した場合だけ発注する。後続確認時に1hの突破がもう一度発生する必要はない。Trigger がなければ、確認条件だけ成立しても発注しない。

- 高値突破ですぐ発注: Trigger のみ。ExecutionFilter 不要。
- 上昇トレンド中の高値突破で発注: MarketState + Trigger。後続確認がなければ ExecutionFilter 不要。
- 高値突破後、期限内の確認を待つ: Trigger + ExecutionFilter + 待機ポリシー。

確認条件と、待機期限・取り消し・再発火の扱いは分離する。TriggerがTに発生した場合、同じTに確定して利用可能になった足でExecutionFilterが確認してよい。最低1本の待機は必須にしない。「後続」は取引機会の発生後という因果順序であり、必ず後の時刻や次の足を意味するわけではない。Tで確認できれば発注判断へ進み、未確認なら待機方針に従って後の評価機会を待つ。MarketStateとの差は、取引機会に紐付いた確認・記憶・期限管理を行う点にある。

### 4.3 各部品の契約

各部品に最低限、以下を宣言する。

| 項目 | 設計する内容 |
|---|---|
| 入力 | データ系列・銘柄・時間足・Feature・取引機会・建玉情報への型付き参照 |
| 評価タイミング | 特定の足確定、約定通知、その他の許可されたイベント |
| 出力 | 状態・イベント・注文要求などの型、方向、単位 |
| パラメータ | 型・範囲・固定値・探索対象の区別 |
| 状態 | 部品固有の履歴、初期化・リセット・保存方法。グローバルな共有状態を持たない |
| 時刻の制約 | 利用可能時刻、鮮度、ウォームアップ、欠損時の動作 |
| 同一性 | ID・version・実装 digest・依存部品の版 |

同じ役割でも異なる時間足を参照できる。1部品が日足高値と15m終値を同時に読むことも可能。ただし読み出せるのは、判断時点で利用可能な情報に限る。

ここでの「契約」は、上表の7項目をひとまとめにしたものを指す。日足高値と15m終値を使う部品は、2つの契約ではなく、1つの契約の中に2つの入力スロットを持つ。「同時に読む」は1回の評価で両方を参照する意味であり、両方が同じ時刻に更新される必要はない。

入力は数値だけでなく、市場状態・取引機会・建玉情報などの型付きデータを含む。評価タイミングは単なる数値ではなく、「対象銘柄の15分足が確定したとき」などのイベント条件で表す。

パラメータは出力とは別の設定である。例えば最小突破幅2 pipsは実行前に与える設定であり、入力の価格と組み合わせて判定に使う。出力には説明や後続処理のため、適用した閾値価格を記録できるが、それによってパラメータの定義場所が出力へ移るわけではない。

### 4.3.1 役割に応じた出力型（名称・責務を確定）

出力は役割に応じた型で管理する。すべてを数値・真偽値・自由形式の辞書に統一しない。継続して参照できる観測値/状態と、一度発生したイベント、実行を依頼する要求を区別する。未入力・計算不能・未発火も、価格0や条件Falseへの暗黙変換で表現しない。

以下の型名と責務を採用する。各出力型の内部フィールドは今後具体化する。

| 部品 | 出力型 | 意味 |
|---|---|---|
| Feature | `Observation[T]` | 型Tの観測値と市場の対象区間・鮮度。共通の利用可能時刻等は外側のOutputRecordで管理する |
| MarketState | `MarketPermission` | 方向別の取引許可状態。口座リスク審査とは別 |
| Trigger | `Opportunity` | ID・方向・時刻・根拠情報を持つ取引機会 |
| ExecutionFilter | `ConfirmationResult` | 対象の取引機会を識別した確認結果 |
| Order | `OrderIntent` | 数量決定前の注文意図。資金管理の承認後に数量付き注文として受け付ける |
| Protection | `ProtectionLevels` | 初期SLを担当。TPと約定後の管理はExitの責務 |
| Exit | `ManagementAction` | 決済・保護水準更新等の型付き要求。具体的な要求種別は要設計 |

`Observation[T]`は型Tの値を包む表記である。出力なしを空イベント列で表すか等の実行API、状態の有効期限、共通メタデータの構造は別途決める。内部の条件判定には、役割用の出力とは別に `ConditionState` を設ける。複数の条件を合成し、明示的な変換で `MarketPermission` を作る。すべての内部計算部品に戦略上の役割を付ける必要はない。

### 4.3.2 部品の契約と、戦略内での使用箇所（採用）

再利用可能な部品の契約と、その部品を戦略内で具体的に使用する設定を分ける。以下の3つの型名と責務を採用する。これらは宣言を表すデータクラスとして設計し、計算を実行する抽象クラスそのものとは区別する。実装側の共通インターフェースは別途設計する。

| 型名 | 責務 |
|---|---|
| `ComponentContract` | 入力スロットと型、評価イベントの条件、出力型、パラメータ仕様、状態仕様、時刻制約、部品の同一性を宣言する |
| `ComponentInstance` | 戦略内の使用箇所にIDを付け、部品の契約を参照し、入力元・具体的パラメータ・許可された評価タイミングを指定する。`role` と実行中の状態は含めない |
| `StrategyDefinition` | 使用する部品の一覧、各役割を担当する出力への名前付き参照、待機等の戦略全体の方針をまとめる |

契約側が型や許可条件を定め、使用箇所側がそれを満たす具体値を選ぶ。契約が評価タイミングを固定する部品では、使用箇所から自由に上書きしない。各使用箇所の実行状態は、実行ごとに別に生成・保存する。

例: 汎用の価格突破Triggerの契約は、`reference_level`と`current_price`という価格入力を要求する。戦略内の使用箇所は、前者に日足高値、後者に15m終値を接続し、突破幅2 pipsと15m確定時の評価を指定する。同じ契約を別の時間足構成に使う場合も、独立した使用箇所と状態を持つ。

依存関係は「上流部品の使用箇所IDと出力名 → 下流部品の入力スロット」で明示する。部品の実装が、特定の上流部品を直接呼び出す形にはしない。実行前に接続先の存在・型・単位・銘柄の整合性と循環の有無を検査し、実行時には利用可能時刻と鮮度を検査する。

依存関係は何を読むかを定め、評価タイミングはいつ動くかを定める。上流が更新されたことだけで下流を自動評価するとは限らない。イベント入力の配送・保存・重複処理防止は、最新値を読む観測入力とは分けて設計する。

### 4.3.3 役割は戦略の名前付きフィールドで指定する（採用）

`StrategyDefinition` は1つの戦略構成を表し、複数の `ComponentInstance` を保持する。役割のフィールドは部品を重複して埋め込むのではなく、部品の使用箇所IDと出力名を参照する。

```text
StrategyDefinition
  components
    daily_trend       : 日足の上昇トレンド判定
    low_volatility    : 低ボラティリティ判定
    london_session    : ロンドン時間判定
    context_condition : AND(daily_trend, OR(low_volatility, london_session))
    entry_permission  : 条件を方向別の取引許可に変換
    breakout          : 高値突破の検出
    entry_order       : 注文意図の生成
    initial_stop      : 初期ストップの計算
    primary_exit      : 決済判断

  market_state      → entry_permission の出力
  trigger           → breakout の出力
  execution_filter  → なし
  order             → entry_order の出力
  protection        → initial_stop の出力
  exit              → primary_exit の出力
```

`market_state` 等の名前付きフィールドから役割を判別するため、使用箇所側の `role` や契約側の `supported_roles` による二重指定は採用しない。コンパイル時に接続先の出力型が役割の要求を満たすか検査する。例えば `trigger` は取引機会を、`order` は注文意図を要求し、両者を誤接続した場合は拒否する。

役割フィールドが1つであることは、条件やイベントが1個しか使えないことを意味しない。複雑な条件や複数のイベントは、その参照先で型付きの合成部品として表す。条件とイベントを暗黙に混ぜず、条件によるイベントの通過判定等も意味の明確な操作とする。

同じ部品出力を複数箇所で参照することと、同じ契約から複数の使用箇所を作ることは区別する。前者は同じ計算結果の共有、後者は別の設定・独立した実行状態を持つ。イベント出力を複数箇所で購読する際の配送規則は別途定義する。

### 4.3.4 クラスのフィールドと拡張の境界（方針は採用）

3クラスは、スキーマのバージョンごとに共通フィールドを固定し、その中に入る部品固有の内容を可変にする方針を採用する。トップレベルのフィールド名・型・必須性は第4.3.5節で確定し、補助型の内部構造は別途具体化する。部品ごとにPythonオブジェクトへ任意属性を追加する方法では拡張しない。

| クラス | 共通フィールド | 部品・戦略ごとに変わる内容 |
|---|---|---|
| `ComponentContract` | `component_id`、`version`、`implementation_ref`、`inputs`、`outputs`、`parameters`、`evaluation_spec`、`state_spec`、`temporal_constraints` | 名前付き入出力の数・型、パラメータの名前・型・範囲、許可イベント、状態の構造等 |
| `ComponentInstance` | `instance_id`、`contract_ref`、`inputs`、`parameters`、`evaluation` | 参照する契約、入力の接続先、具体的なパラメータ値、許可条件内での評価イベント指定 |
| `StrategyDefinition` | `strategy_id`、`version`、`components`、`market_state`、`trigger`、`execution_filter`、`order`、`protection`、`exit`、`entry_policy`、`opportunity_validity`、`opportunity_concurrency` | 使用する部品数、接続グラフ、各役割の参照先、確認待ち等の方針 |

例えばEMAと価格突破はどちらも `parameters` を持つが、内容はEMAなら期間、価格突破なら最小突破幅になる。契約側の `parameters` は各設定の仕様、使用箇所側の `parameters` はその仕様を満たす値である。可変の名前付きコレクションを使う場合も自由形式の任意データとはせず、未宣言キーや型・範囲の不一致を拒否する。

入力スロットの追加やパラメータ追加は、その部品の契約の変更として管理し、通常は3クラス自体のフィールド追加を必要としない。一方、新しい戦略上の役割や評価機構の追加など、共通モデルの意味が変わる場合はスキーマ変更として扱う。保存形式のスキーマ版と、個々の部品・戦略の版は区別する。スキーマ版の保存場所は要決定。

Pythonの型注釈だけに依存せず、構築・読込・コンパイル時に検証する。宣言データは検証後に変更しない方針とし、入れ子の設定も実行中に書き換えない。実行中の状態は別の実行コンテキストに保持する。データクラス、検証ライブラリ、実装用インターフェースの具体的な選択は未決定。

### 4.3.5 3クラスのフィールドと型（正本・2026-09-18確定）

以下のトップレベルのフィールド構成・型・必須性と補助型の責務を正本として採用する。`state_spec` と `temporal_constraints` は削除せず、`ComponentContract` のトップレベルに保持する。補助型の内部フィールドや実装方式まで確定したことを意味しない。型表記はPythonを想定する。`Mapping` は名前付きの対応表、`tuple[T, ...]` は型Tの可変個数の列、`T | None` は省略可能を表す。宣言内のコレクションは検証後に凍結する。

**ComponentContract：何を受け取り、どの条件で評価し、何を返せるか**

| フィールド | 型 | 意味 |
|---|---|---|
| `component_id` | `str` | 部品の識別子。表示名とは分離する |
| `version` | `int` | 部品の意味を識別する正の整数版 |
| `implementation_ref` | `ImplementationRef` | 登録済み実装のIDと内容ハッシュ。実行関数そのものは保存しない |
| `inputs` | `Mapping[str, InputSpec]` | 入力名から、必要な型・入力数・時点参照条件への対応 |
| `outputs` | `Mapping[str, OutputSpec]` | 出力名から、値の型・観測/イベント/要求の区別への対応 |
| `parameters` | `Mapping[str, ParameterSpec]` | パラメータ名から、型・単位・許容範囲等への対応 |
| `evaluation_spec` | `EvaluationSpec` | 許可する評価イベントと、固定条件または選択可能範囲 |
| `state_spec` | `StateSpec \| None` | 内部状態の型・初期化・リセット規則。状態を持たない部品はNone |
| `temporal_constraints` | `TemporalConstraints` | ウォームアップなど、部品全体の時刻に関する制約 |

入力ごとの読み取り条件・鮮度・観測履歴の必要量は `InputSpec`、入力を跨ぐ制約等は `TemporalConstraints` に置き、同じ規則を両方に重複定義しない。`InputBinding` は接続先だけを持ち、読み取り条件を上書きしない。`OutputSpec` は出力の仕様であり、実行結果の `Opportunity` 等の値そのものではない。

**ComponentInstance：戦略内での具体的な使用設定**

| フィールド | 型 | 意味 |
|---|---|---|
| `instance_id` | `str` | 同一戦略内で一意な使用箇所ID |
| `contract_ref` | `ContractRef` | 部品ID・版・契約の内容ハッシュで契約を固定する |
| `inputs` | `Mapping[str, InputBinding]` | 入力スロット名から、具体的な参照元への対応 |
| `parameters` | `Mapping[str, ParameterValue]` | 契約に従った具体値。探索範囲ではない |
| `evaluation` | `EvaluationSchedule` | 実際に評価を起動するイベント条件 |

`role`・出力型の再宣言・実行中の状態は持たせない。入力名・パラメータ名・値・評価タイミングを契約と照合する。契約で固定されている評価条件は変更できない。省略時の既定値を許可する場合でも、実行前には有効値を確定して記録する。

**StrategyDefinition：部品をつないだ戦略全体**

| フィールド | 型 | 意味 |
|---|---|---|
| `strategy_id` | `str` | 戦略の識別子 |
| `version` | `int` | 保存する戦略定義の正の整数版 |
| `components` | `tuple[ComponentInstance, ...]` | 部品の使用設定。並び順で実行順序を指定しない |
| `market_state` | `OutputRef \| None` | 市場状態による取引許可の参照。Noneはこの制約を使わない |
| `trigger` | `OutputRef` | 取引機会を出す出力の参照 |
| `execution_filter` | `OutputRef \| None` | 発火後の確認結果の参照。Noneは後続確認なし |
| `order` | `OutputRef` | 注文意図の参照 |
| `protection` | `OutputRef` | 初期の保護水準の参照。初版は必須 |
| `exit` | `OutputRef` | 保有管理要求の参照。複数ルールは明示的に合成する |
| `entry_policy` | `EntryPolicy` | 即時発注/確認待ち、期限、失効、再発火の扱い |
| `opportunity_validity` | `OpportunityValiditySpec` | 確認待ち中に固定する条件と継続成立を要求する条件の分類。必須、暗黙の既定値なし（2026-09-20 確定、ADR-0031） |
| `opportunity_concurrency` | `OpportunityConcurrencySpec` | 複数の有効な取引機会の関係と `on_order_accepted`。必須、暗黙の既定値なし（2026-09-20 確定、ADR-0032） |

末尾2フィールドは 2026-09-20 の追加であり、2026-09-18 に確定した他のフィールドの意味を変更しない。取引機会のライフサイクル規則を宣言に現すために必須化したもので、詳細は第4.5節を正本とする。

各 `OutputRef` が存在し、役割の要求型を満たすことをコンパイル時に検査する。例えば `trigger` に `OrderIntent` を接続することは拒否する。`execution_filter` の有無と `entry_policy` のモードも照合する。`opportunity_validity` の各 `ValidityBinding` が指す出力の存在と型、`opportunity_concurrency` の `on_order_accepted` の整合も同時に検査する。Protectionは初期SL、ExitはTPと保有後の管理を担当する。詳細な出力項目は第4.7節の責務分担に沿って具体化する。

定義の内容ハッシュは部品参照・接続・パラメータ等から決定論的に算出する。探索で作った異なるパラメータ割当を、同じ `strategy_id/version` だから同一実行として扱わない。人間が管理する戦略の版と、各評価の解決済み設定の識別を分ける。研究ポリシー・口座・リスク方針・データsnapshot・探索空間は実験側の設定であり、このクラスへ混在させない。

**補助型の境界（責務を確定、内部構造は詳細設計対象）**

- `InputSpec` / `OutputSpec` は、価格・比率・条件状態・取引機会などの型を、保存可能な型識別子とスキーマで指定する。Pythonの任意クラス名を動的に読み込む方式にはしない。
- `OutputRef` は `instance_id` と `output_name` を持ち、部品の特定の出力を指す。
- `InputBinding` は、部品出力への `OutputRef`、市場データへの `MarketDataRef`、現在評価中の建玉等への `RuntimeInputRef` を区別する。後者はエンジンが供給する許可された時点情報であり、共有された可変台帳への直接アクセスではない。
- AND等の可変個数入力には、`InputSpec` で入力数を宣言し、`InputBinding` に型付き参照の列を渡せるようにする。単一入力と複数入力を区別して検証する。詳細な表現は次に決める。
- `ParameterValue` の初期型は `bool | int | float | str`。浮動小数点は有限値に限定し、boolと整数も区別して検証する。pips等の単位は `ParameterSpec` に明記する。列挙値は許可値で検証し、無制限な任意オブジェクトは受け付けない。価格計算全体の数値精度の選択とは別である。
- `EvaluationSchedule` は足確定や約定通知などの型付きイベント条件を保持する。同時刻の実行優先順位を自由な整数で部品ごとに指定する方式にはしない。順序は因果関係とエンジンの契約から決定する。
- `EntryPolicy` はモード別の型を組み合わせる。即時発注なのに確認期限が設定される等の無意味な組合せを避ける。各モードのフィールドは別途設計する。

3クラスの主要フィールドは確定した。入力・出力・接続の詳細は第4.3.8節以降で具体化し、パラメータと評価タイミング、状態と時刻制約、待機ポリシーの順に詳細を決める。

### 4.3.6 仕様・参照・実行結果の区別（確定）

`InputSpec` は入力の受け口の仕様、`OutputSpec` は出力の出し口の仕様、`OutputRef` は特定の出力への接続先である。いずれも実際の計算結果を保持するものではない。

例として「日足終値がEMAより上なら買いを許可する」場合、次の計算と接続を行う。

```text
日足終値 → EMA計算 → EMAの価格観測値
日足終値とEMA → 価格比較 → ConditionState
ConditionState → 方向別の許可への変換 → MarketPermission
StrategyDefinition.market_state → 最後の出力をOutputRefで指定
```

比較部品の契約には、価格型を要求する2つの `InputSpec` と、条件状態型を宣言する `OutputSpec` を定義する。使用設定では、入力スロットに日足終値の参照とEMA部品の出力への `OutputRef` を接続する。

`OutputRef` は `instance_id` と `output_name` を指定するだけであり、型変換・計算・条件判定を行わない。`market_state` に参照を置くだけで真偽値が取引許可型へ変換されることはなく、必要な変換は部品が明示的に行う。エンジンはその参照先の利用可能な出力を戦略の役割として消費する。

上記の分解は必須の細かさではない。日足終値とEMAを受け取り、直接 `MarketPermission` を返す部品を実装してもよい。外部へ見せる型付き契約は維持し、単純な計算に不要な変換部品を要求しない。

### 4.3.7 状態仕様と時刻制約を保持する理由・配置（確定）

`state_spec` と `temporal_constraints` をトップレベルから外す案は採用しない。両フィールドの責務を以下に限定し、仕様の重複を避ける。

**state_spec**

例: 「Aの発生後5本以内にBが発生したら取引機会を出す」部品は、Aの発生を待機状態として記憶し、Bの成立・期限到達で解除する。`StateSpec` は、この内部状態の型と初期化・リセット規則を宣言する。実行時のAの発生時刻や待機状態の値は契約に入れず、実行ごと・使用箇所ごとの状態として保持する。

Python実装側は状態を専用の型で管理し、契約からその状態型の定義を参照・検証できるようにする。契約と実装に同じ状態構造を独立に手書きして二重管理することは避ける。状態の初期化・リセットを実装と照合する方法、保存・復元の詳細は次の設計対象とする。状態を持たない部品は `state_spec=None`。

**temporal_constraints**

入力1つに閉じない、部品全体の時刻条件を宣言する。例えば、2系列の変化量を比較する部品で「両系列の対象区間が一致すること」を要求する場合、個々の入力が確定済みでもそれだけでは十分ではない。このような入力間の時刻整合性や、内部状態を準備する部品全体のウォームアップ条件を保持する。

| 規則 | 正本となる配置 |
|---|---|
| 判断時点より未来の情報を読ませない | データ参照基盤の共通契約。部品から緩和不可 |
| 各入力の鮮度・必要履歴・欠損時の扱い | `InputSpec`。接続先だけを持つ `InputBinding` には置かない |
| 入力を跨ぐ時刻整合性・部品全体の準備条件 | `temporal_constraints` |
| どのイベントで部品を評価するか | `evaluation_spec` と `evaluation` |
| 順序イベントの「5本以内」等 | 当該部品のパラメータと状態遷移の意味 |
| Trigger後の確認待ち期限・失効 | `entry_policy` |
| 確認待ち中に固定する条件／継続成立を要求する条件 | `opportunity_validity`（ADR-0031） |
| 複数の有効な取引機会の関係・`on_order_accepted` | `opportunity_concurrency`（ADR-0032） |

日足高値と15m終値の参照に「対象時刻の一致」を一律には要求しない。時刻整合性は必要な部品のみが宣言する。追加制約がない部品も `TemporalConstraints` は保持し、追加条件なしを明示する。具体的な制約の型・検査方法は詳細設計で決める。

### 4.3.8 入力・出力・接続先の詳細設計

**合意済み事項**

- `InputSpec` が読み取り条件を持ち、`InputBinding` は接続先だけを持つ。
- `InputSourceRef` の区分は `OutputRef`、`MarketDataRef`、`RuntimeInputRef` の3種類とする。
- 市場データは `MarketDataRef` で直接入力へ接続できる。終値を読み出すだけの専用部品は必須にしない。
- EMA等の計算が必要なところから部品として扱い、基本的なインジケータを部品カタログへ追加していく。収録する具体的な指標と計算規則は別途決める。

**フィールドの詳細案（確認中）**

| 型 | フィールドと型 | 責務 |
|---|---|---|
| `InputSpec` | `data_type: DataTypeRef`、`kind: PortKind`、`arity: InputArity`、`read_spec: InputReadSpec` | 必要な値の型・流れ方・接続数・読み取り条件 |
| `OutputSpec` | `data_type: DataTypeRef`、`kind: PortKind` | 返す値の型と流れ方。実行時の値は含まない |
| `InputBinding` | `sources: tuple[InputSourceRef, ...]` | 単一または複数の具体的な接続先 |

入力名・出力名は契約のmappingのキーに持ち、Spec内に重複させない。`InputArity` は最小・最大接続数を持つ。接続元がないことと、接続元の実行時データが欠損していることは別に扱う。

例: EMA部品の入力は `MarketDataRef` で指定した日足終値。価格比較部品の入力は日足終値への `MarketDataRef` と、EMA部品の出力への `OutputRef`。両方を価格型として検証し、対象銘柄・単位も照合する。AND部品には複数の条件出力への参照を渡す。部品実装がinput bindingを無視して市場データ全体へアクセスすることは許可しない。

### 4.3.9 区分値の整理（2026-09-18確定）

本節の区分値・型名・責務、および固定enumにしない対象を採用する。各補助型の内部フィールドは次の詳細設計対象とする。

区分値は、小さなenumで表す分類と、区分ごとに必要なフィールドが異なる型付きunionを区別する。unionの保存形式には区分タグを持たせる。Python側で型とenumを独立に二重指定して矛盾を許す設計にはしない。

| 対象 | 型・区分 | 意味 |
|---|---|---|
| 参照元 | `InputSourceRef = OutputRef / MarketDataRef / RuntimeInputRef` | 部品出力、市場データ、実行コンテキストの3区分 |
| データの流れ方 | `PortKind`: `VALUE`、`EVENT`、`COMMAND` | 更新まで繰り返し参照する値、一度発生した事実/機会、処理を依頼する要求 |
| 市場データ項目 | `MarketDataField`: `OPEN`、`HIGH`、`LOW`、`CLOSE`、`VOLUME` | 既存OHLCVの列。OPEN指定でも未完了barへのアクセス権を意味しない |
| 値の読み方 | `LatestAvailable`、`HistoryWindow` | 判断時点で利用可能な最新値、利用可能な履歴区間 |
| イベントの読み方 | `DeliveredEvent` | 今回評価に配送されたイベント。最新イベントを毎回再利用しない |
| 実行コンテキストの読み方 | `CurrentContext` | 現在処理中の取引機会・建玉等の時点情報 |
| 必要入力が欠損/鮮度切れの場合 | `MissingInputPolicy`の動作区分: `SKIP_EVALUATION`、`ERROR`、`WAIT_FOR_INPUT`、`USE_PREVIOUS` | 見送り・失敗に加え、明示した待機・過去値使用を設計する。後二者の詳細は第4.3.13節の案。無断補完はしない |
| 履歴窓の表現 | `BarsWindow`、`DurationWindow` | 指定系列の本数、経過時間。双方の必要フィールドを分ける |
| 評価を起動するイベント | `OnBarClose`、`OnInputEvent` | 指定銘柄・時間足の確定、指定入力へのイベント配送。具体的な対象も宣言する |

`EvaluationSchedule` は必要に応じて複数の起動条件を宣言できる。例えば後続確認を行う処理では、取引機会の配送と、その後の15m足確定を区別して受け取れる構造とする。どの起動条件でどの入力を必須とするか、複数条件が同時刻に成立した場合の配送・評価回数、確認待ち状態の管理主体は次の詳細設計で明示する。戦略判断の因果順序と同時刻確認の許可は第4.3.11節で確定する。これらは区分値の確定だけで決まったものとは扱わない。

`InputReadSpec` は上表の読み方別の型を組み合わせる。全読み方が全 `PortKind`・参照元に適用できるわけではない。例えばVALUEにDeliveredEvent、EVENTにLatestAvailableは拒否する。COMMANDの通常の消費者は注文/保有管理エンジンであり、観測値として何度も再実行しない。コマンドを加工する部品を許す場合の配送規則は別途具体化する。

欠損扱いは、必要な値が得られない場合に適用する。Triggerが発火せずイベントが発生しないことは通常動作であり、欠損エラーではない。SKIP_EVALUATIONはFalseや価格0を出力することではない。既存出力の有効性・鮮度の扱いも明示し、停止した部品の古い値が無期限に有効にならないようにする。構造エラーや部品実装の例外は欠損として握り潰さない。

バー数窓は読み取る系列のbar数であり、戦略全体の評価回数ではない。例えば日足20本と15分足20本は異なる。必要履歴がパラメータに依存する場合は、そのパラメータへの明示的な参照で実行前に解決し、InputBindingへ読み取り規則を移さない。EMA等の再帰計算では、必要本数・初期化・更新方法を合わせて定義する必要があり、毎回直近N本から再計算することを一律に要求しない。

初期の戦略部品は確定済みbarを参照する。OHLCデータのOPEN列を選んだことだけで、同じbarのHIGH/LOW/CLOSEまで始値時点で見える構造にしない。約定エンジンによる始値処理は戦略部品の確定足参照と別のイベント順序契約で扱う。

**enumにしないもの**

- `DataTypeRef` は登録済みデータ型の参照。新しい指標の構造的な出力型を追加できるよう、Price等を1つの巨大な固定enumに閉じ込めない。登録・版固定・接続検証は必要。
- 銘柄は銘柄定義のID、部品は契約のIDを使う。対応データや実装の存在は別途検証する。
- 時間足は長さとセッション/集約規則を表す定義の参照とする。15m/1h等の固定enumだけで表現力を制限しない。実際に用意できる足だけ実行可能。
- 接続数・期間・閾値は型と範囲を持つ数値。値ごとのenumは作らない。

`RuntimeInputRef` の対象区分、状態リセット、入力間の時刻整合性、確認待ちの失効/再発火、注文/管理要求の種別は、各型のライフサイクルを具体化する際に決める。現段階で全将来機能を列挙して予約しない。

### 4.3.10 InputReadSpecのフィールドと鮮度・必要本数（確定）

最新値・履歴には鮮度と不足時の設定を持たせ、配送イベント・実行コンテキストには不要な設定を持たせない。固定本数の窓は指定本数を厳守し、`min_samples` はフィールドから削除する。部分履歴を許可する旧案は不採用とする。

| 読み取り型 | フィールド構成 |
|---|---|
| `LatestAvailable` | `max_age: timedelta \| None`、`on_missing: MissingInputPolicy` |
| `HistoryWindow` | `window: BarsWindow \| DurationWindow`、`max_age: timedelta \| None`、`on_missing: MissingInputPolicy` |
| `DeliveredEvent` | 初期は追加フィールドなし。配送されたイベントを受け取る |
| `CurrentContext` | 初期は追加フィールドなし。今回処理中の対象を受け取る |

**固定本数の窓は必要本数を厳守する**

- `BarsWindow.count` は必要本数を表す正の整数。20本平均は有効な20本が揃った場合だけ計算する。
- 19本しかない場合、無効値を含む場合、必要な足が欠落している場合は `on_missing` に従う。期間を短縮した平均へ暗黙に変更しない。
- 先に対象窓を決め、その内部のデータを検査する。欠損を削除して窓外の古い足を繰り上げたり、補間で必要本数を満たしたことにしたりしない。
- 正常な休場時間には足を要求しない。足が存在すべき時間帯の欠落は、採用した取引セッションと足生成規則を使って検査する。
- 数えるのは対象系列の異なる足であり、戦略の評価回数や入力接続数ではない。同じ値の正常な別の足は別観測として扱い、重複行は本数に加算しない。
- 複数系列の履歴では各系列について必要本数を満たす必要がある。別系列の本数を合算しない。系列間の整列条件も別途検査する。
- countが期間パラメータに依存する場合は、その参照を実行前に具体値へ解決する。入力接続側に別の期間設定を設けない。
- 必要本数が揃っても、再帰指標の初期化など部品全体のウォームアップ条件は別途満たす必要がある。

**足データの標準の鮮度判定**

- 判断時点で「期待される最新の確定足」が存在し、利用可能で有効かを確認する。単純な経過時間だけで更新遅延を判定しない。
- 期待する足は、銘柄/データの取引セッション、タイムゾーン、夏冬時間、休場規則、足の集約規則に基づいて決める。単に土日を一律に除外する方式にはしない。
- 市場再開直後に、直近の確定日足が前営業日のものであることは正常になり得る。一方、新しい15m足が確定するはずの時点でそれがない場合は、古い15m足を最新として黙って使わず、不足として扱う。
- 最新値の存在だけでは履歴途中の欠落を保証できないため、必要な履歴窓内の完全性も検査する。
- この標準判定は `max_age=None` でも実施する。週末を許容するために平日の更新遅延まで長く許す設計にはしない。
- 同時刻の足確定・入力公開・部品評価の順序、利用可能になるまでの既知の遅延をどのように契約へ反映するかは、時刻処理の詳細設計で明示する。

**max_ageは必要な入力だけに付ける追加制約**

- 非負の `timedelta` または `None`。Noneは追加の経過時間制限なしであり、標準の鮮度判定を無効にしない。
- 指定する場合、`判断時刻 − 鮮度基準時刻 <= max_age` を追加で要求する。上限と同値は許可し、0は基準時刻と同時点のみ許可する。
- 追加制約の経過時間はUTCで計算し、週末・休場時間も含む。週末を含めて情報の古さを制限したい入力に明示的に使用する。足データ全体の標準制約として強制しない。
- 確定足では鮮度基準を `bar_end` とする。利用可能時刻は「その時点で知れるか」の検査に使い、古い足が遅れて到着したから新鮮になったとは扱わない。
- 日足EMAは最後に反映した確定日足の終了時刻を鮮度の基準とする。同じ入力での再計算によって鮮度を更新しない。ウォームアップ履歴の最古時刻を基準にするわけでもない。
- HistoryWindowの追加鮮度制約は履歴末尾の市場時点に適用し、窓内の全データに一律適用して過去の履歴を切り詰めない。
- Featureが反映すべき入力の更新状況・複数系列Featureの鮮度伝播は契約として詳細化する。新しい計算時刻で古い入力や未更新の出力を隠さない。

**不足時の処理と理由を分ける**

| 状況 | 処理 | 記録する理由 |
|---|---|---|
| データ開始時に必要な履歴がまだない | on_missingに従う | ウォームアップ不足 |
| 存在すべき足がない、値が無効 | on_missingに従う | 入力データ欠損/無効 |
| 期待される最新確定足が利用できない | on_missingに従う | 最新足の未取得/更新遅延 |
| 明示したmax_ageを超える | on_missingに従う | 追加鮮度制約違反 |

理由名は説明上の分類であり、診断コードの具体的なenumは別途設計する。正常な休場自体は欠損ではない。SKIP_EVALUATIONで価格0や条件Falseを生成しない。過去出力を新たに生成・発火したように扱わない。構造エラー・実装例外は入力不足として握り潰さない。

**時間幅の窓に残る詳細設計**

`DurationWindow` は時間幅を指定し、その範囲内で存在すべきデータが揃っているかをセッションに基づいて判定する。最小件数による部分履歴許可は設けない。休場を含むため期間内の件数は変わり得る。区間の端点、データ開始前を含む場合、全期間が休場で空になる場合の扱いは次に具体化する。空の履歴から指標を暗黙に計算することは許可しない。

### 4.3.11 同時刻の情報反映とExecutionFilter確認（確定）

判断時刻Tでは、利用可能時刻がT以下の情報を使う。日足と15m足がともにTで利用可能になる場合は、両方を反映してFeatureとMarketStateを更新し、更新後のMarketStateを使ってTriggerによる取引機会の取引可否を判定する。

戦略判断の因果順序は次のとおり。

1. Tまでに利用可能な確定足を公開する。
2. 今回の評価に必要なFeatureとMarketStateを、宣言された評価条件・依存関係に従って更新する。
3. Triggerを評価し、更新後のMarketStateで取引可否を判断する。
4. 許可された取引機会についてExecutionFilterを評価する。同じTに確定して利用可能な足を使ってよい。
5. 確認成立なら注文意図の生成へ進む。未成立なら待機・期限・失効の方針に従う。

この順序は日足を常に先に処理する規則ではなく、情報の可用性と依存関係を守るための規則である。登録順・データ読込順によって判断が変わってはならない。足の終了時刻がTでも利用可能時刻がTより後なら、その情報は使えない。

ExecutionFilterの同時刻確認を許可することは、すべての足確定で無条件に全フィルターを起動する意味ではない。宣言された評価スケジュールと必要な入力を満たすことが前提である。開始足確認を許可する設定では同時刻の足確定と取引機会の配送を処理できるようにし、足確定を先に処理したという実装上の都合だけで確認を次足まで遅らせない。戦略ごとの開始足確認設定は第4.3.13節で具体化する。

例: Tで1hの突破が確定し、同じTで15mの確認条件も成立していれば、Tの判断処理で発注判断まで進める。15mの確認条件が未成立なら、その機会を保持し、方針に従って後の確認を待つ。必ず1本待つという制約は設けない。

同時刻に複数の起動条件が成立した場合の配送・評価回数は詳細設計対象だが、同じ取引機会に対する確認成立で注文意図を意図せず重複生成しないことを保証する。

この決定は注文の約定価格・約定時点の決定とは別である。Tで確認できても、その足の過去の始値や足内価格で遡って約定させない。終値約定・次足始値約定等の選択はOrderと執行モデルで別途定義する。既存建玉の決済、保留注文の約定、期限切れと確認の競合を含む全体のイベント順序は引き続き詳細設計対象とする。

### 4.3.12 具体的な時刻表による情報公開・評価の正面案（確認中）

第4.3.11節の更新後MarketStateと同時刻確認は確定事項。同時刻の公開をまとめること、機会を識別した重複防止を採用する。順序は時間足の大小でなく依存グラフから導く。系列ごとの公開予定・遅延、開始足確認の明示設定、欠損時の選択肢による補足を第4.3.13節に記す。

**例の前提**

- USDJPY、冬時間のある営業日の22:00 UTCをTとする。ニューヨーク現地17時に対応し、日足・1h足・15m足が確定する例。
- 価格は説明用の仮の値であり、実データや収益性の検証ではない。
- 基本ケースではbar_endとavailable_atが一致する。足の区間は開始を含み終了を含まない。未確定のOHLCは戦略部品に公開しない。
- Featureは各入力足の確定時に更新する。MarketStateは確定日足終値と日足EMAを比較する。
- Triggerは1h確定時に突破を検出する。突破基準は当該1h足を除く過去20本の高値であり、評価時に使う参照区間を明示する。
- ExecutionFilterは取引機会の配送と15m足確定を起動条件とし、対象機会がある場合に確定15m終値と15mEMAを比較する。取引機会がない場合には確認・注文を生成しない。
- 待機中のMarketState再検査、失効、保有建玉との競合はこの例では発生しない前提とし、別途設計する。

**Tで公開する市場データ**

| 系列 | 対象区間 | 公開時刻 |
|---|---|---|
| 日足 | 前営業セッションの17時から当日17時まで（この例では前日22:00〜当日22:00 UTC） | T |
| 1h | 21:00〜22:00 UTC | T |
| 15m | 21:45〜22:00 UTC | T |

**T内の評価段階**

| 段階 | 実行内容 | 使える情報 |
|---|---|---|
| P0 | 同じavailable_at=Tの市場データをまとめて公開 | 上記3系列とそれ以前の利用可能データ。T後に終わる足は不可 |
| P1 | 起動対象のFeatureを依存順に更新 | 最新公開データ、明示された過去区間、必要な内部状態 |
| P2 | MarketStateを更新 | Tの日足終値とTの日足EMA等 |
| P3 | Triggerを評価し、更新後MarketStateで取引可否を判定 | Tの1h終値、当該足を除く基準水準、P2の取引許可 |
| P4 | 新規/待機中の対象機会についてExecutionFilterを評価 | P3で生成された機会、Tの15m終値、P1の15mEMA等 |
| P5 | 確認済み機会から注文意図を生成 | 確認結果とその根拠。数量・Protection等は別途定義する契約に従う |

P0〜P5は因果順序であり、22:00:00から人工的に1秒ずつ進める意味ではない。部品出力が同じTを持っていても、後段の出力を前段で使うことはできない。実行記録には時刻に加えて因果順序を追跡できる情報を残す。

P1は全Featureの無条件再計算を意味しない。宣言された起動条件と依存関係に従い、起動対象の上流計算完了後に下流を評価する。同時刻に必要な上流の更新が失敗した場合、前回出力を新しい出力として扱わず入力の不足時規則に従う。明示的に過去値を読む入力は、その宣言した区間を維持する。

**数値例**

- Tの日足終値151.10、更新後の日足EMA150.80なら買い許可。
- Tの1h終値151.10、当該足を除く過去20本高値151.00。前回の状態等も突破条件を満たしている前提で、買い機会O1を生成。
- Tの15m終値151.10、更新後の15mEMA151.05なら、O1を同じTで確認し注文意図I1へ進む。
- 15mEMAが151.15ならTでは未確認。T+15分の確定足で条件が成立すれば、失効していないO1を確認する。1h Triggerの再発火は不要。

**同じ時刻の評価要求をまとめる案**

取引機会の配送と15m足確定が同時に起きても、同じ機会に対する同じ論理確認を二重実行しない。P3までの必要な情報を揃えた後にP4で評価要求を集約し、機会IDごとに確認結果を確定する。異なる機会は別対象として識別する。任意の異なるイベントを時刻が同じという理由だけで一つに潰さない。再発火と複数機会の扱いは第4.5節で確定した（2026-09-20 確定、ADR-0032）。ランタイムは複数の有効な取引機会を同時に保持できなければならず、固定の並行上限を設けるのではなく `OpportunityConcurrencySpec` の宣言に従う。

**情報公開が遅れる場合の案**

日足だけavailable_at=T+2秒なら、Tの判断でその日足・派生Featureを読むことはできない。期待される最新日足が未取得の場合は、その入力のon_missingに従う。最新を要求する宣言で前営業日の日足へ黙って戻らない。

T+2秒では新しい情報公開として処理する。bar_end=Tは対象区間の情報として保持する。SKIP_EVALUATIONの場合、Tで見送ったすべてのTriggerを自動再実行しない。新たな起動条件に該当する場合のみ別の評価を行う。WAIT_FOR_INPUTを明示した場合は、保持した評価要求を入力到着時に再開する。どの場合も実際の判断はT+2秒以降であり、Tの判断・注文履歴を後から書き換えない。具体的なポリシー案は第4.3.13節を参照。

**本節で決めないこと**

Tの注文意図が、そのTで終わる足の終値で約定するか、次足の始値で約定するかは未決定。同じ時刻ラベルでも約定モデルの因果順序と価格条件が必要である。次足の完成済みOHLCや過去の足内経路を使って有利な約定を選ばない。既存注文・建玉の処理、期限切れと確認の優先順位も次の設計対象とする。

### 4.3.13 公開予定・依存グラフ・確認開始・遅延シナリオ

**採用する設計方針**

- 系列ごとに足の境界・整列・セッションと公開予定を定義する。期待される確定足の判定と欠損検査はこの定義を使う。
- 取引カレンダー、タイムゾーン、日足の区切り、足の整列起点は設定とする。ニューヨーク17時の日足区切りは冬時間22:00 UTC、夏時間21:00 UTCに対応する。固定UTC時刻をコードに埋め込まない。
- 同時刻に実際に公開される入力をまとめた後、Featureを含む部品の依存グラフから評価順を機械的に導く。日足→1h→15mという固定優先順は採用しない。
- 15m EMAを参照する日足レベルのMarketStateも表現可能とする。両者が起動対象ならEMAを先に計算し、状態判定はその結果を読む。必要な更新が発生しない場合の利用可否は出力の時刻・鮮度契約で判断する。
- グラフに、部品の明示入力接続と、MarketState適用・取引機会生成・確認・注文生成等のエンジン上の因果依存を含める。循環は検出して拒否する。実行順序を得るためだけに時間足から依存関係を推測しない。
- 開始足の確認を許可するかは、戦略構成内で明示的に設定する。同時刻確認を基盤が対応可能にすることと、全戦略にそれを強制することを分ける。
- 欠損時の見送り・保留待機・明示的な過去値使用を選択可能な方針として設計し、失敗終了も維持する。
- バックテストで系列ごとの公開遅延シナリオを注入可能にする。ライブ遅延でのみ発火する未検証の特別経路にしない。

**系列スケジュールの具体化案（型名・フィールドは確認中）**

足区間を決める定義、通常いつ利用可能になるはずかを決める公開予定、今回のシミュレーションで実際にいつ公開するかを決める遅延シナリオを分離する。例えばbar_end=T、通常の公開予定T、注入後のavailable_at=T+2秒とする。異常遅延を通常の公開予定へ書き換えて、欠損判定から隠さない。

同時刻にデータを揃えるとは、今回のavailable_atが等しい入力をまとめて公開することである。予定はTでも到着がT+2秒のデータまで無条件に待つことではない。不足した系列はon_missingで扱う。足区間の終了通知と実際のデータ公開通知をエンジン内部で区別し、欠損しても到着を待たずに予定時点の検査を起動できるようにする。OnBarCloseをどちらの通知へ結び付けるか、通常公開遅延がある系列の起動時点は次の詳細設計で固定する。

**開始足確認の具体化案**

ExecutionFilter部品の契約に `include_start_bar: bool` を宣言し、その使用箇所のparametersで明示する。Trueなら取引機会の開始足で確認可能、Falseなら次の対象確認足からとする。入力が利用可能であることは両方で必要。共通の確認制御処理がこの宣言を検証・適用し、EntryPolicyには同じ設定を重複して置かない。

確認の開始足は、機会が実際に生成されたdecision_time時点で利用可能な最新の確認対象足を基準に識別し、そのIDを記録する。通常の最新足検査と不足時規則は引き続き適用し、欠損によって古い足へ黙って戻らない。include_start_barはその開始足を含めるかを決める。同時刻というだけで異なる機会や異なる出力を同一視しない。追い越しによる確認足の更新は第4.3.14節で区別する。

**on_missingの具体化案**

| 動作区分 | 動作 | 必要な追加条件 |
|---|---|---|
| `SKIP_EVALUATION` | 今回の評価を見送り、暗黙の再試行をしない | 理由と対象評価を記録 |
| `ERROR` | 実行を失敗終了 | 原因を記録。実装例外を欠損へ読み替えない |
| `WAIT_FOR_INPUT` | 対象評価を保留し、必要な入力到着時に再開 | 有限の待機期限、期限切れ処理、対象入力区間、再開時の評価時刻 |
| `USE_PREVIOUS` | 指定上限内の過去の有効値を明示的に使用 | 遡れる足数/経過時間、実際に使った観測の記録、許可する欠損理由 |

追加条件が異なるため、MissingInputPolicyは動作タグごとの型付き設定として具体化する案とする。区分だけを指定して無期限に待つ・任意に古い値を使うことは許さない。読み取り条件なのでInputSpec側に置き、InputBindingには置かない。

WAIT_FOR_INPUTは評価要求と入力の対象区間を保持する。待機中に次の足が来たからといって元の要求を別の市場局面へ暗黙に変更しない。再開時刻までに利用可能な情報だけを使用し、過去時刻へ注文を遡らせない。対象市場区間と実判断時刻を分けて記録する。市場由来のMarketStateは固定した対象区間、口座等の現在状態は再開時点に束縛する（第4.3.14節）。複数入力の同時保留、期限切れの優先順位の詳細は引き続き設計対象。

USE_PREVIOUSは、最新の確定足を要求する標準動作への明示的な例外である。初期案ではLatestAvailableだけに許可し、固定本数のHistoryWindowの穴埋めには使わない。20本の窓の欠損を21本目の古い足で補うことは引き続き禁止する。追加制約max_age、未来参照禁止、その他の型/単位条件も緩和しない。用途は許可した未取得・公開遅延等に限定し、破損データや計算例外まで一律に過去値で隠さない。

**バックテストの公開遅延シナリオ**

遅延モデルは部品パラメータでなく、実験のデータ公開設定に置く。系列ごとの固定遅延、指定足への遅延注入、将来必要ならseed固定の確率的遅延を表現し、シナリオの版・設定・実現した公開時刻列を保存する。OHLC値や足の対象区間は変えず、available_atと配送順序を変える。派生Featureは必要入力が公開される前に可視化しない。

最初に検証するケースは、遅延なし、日足のみ2秒遅延、待機期限を超える遅延、次足まで到着しない場合。SKIP/WAIT/USE_PREVIOUS/ERRORと開始足確認設定を適用し、使用した観測・評価時刻・確認結果・注文数の差を追跡できるようにする。同じシナリオの再実行は同じ結果とする。

### 4.3.14 WAIT_FOR_INPUT：問いの固定と再開時の状態

**採用する原則**

固定するのは「問い」であり、市場入力の値そのものではない。待機記録は対象足と入力区間を保持し、再開時はその区間を読み直す。現在状態は再開時のdecision_timeで取得する。既に終端状態となった評価や、待機と無関係な独立部品を自動で再評価しない。

| 入力の時間的な束縛 | 対象例 | 再開時の扱い |
|---|---|---|
| 対象区間に束縛 | 足、EMA、過去N本、これらから求める市場状態 | 最初の評価要求で解決した対象足/入力区間を読む。再開時の最新市場区間へずらさない |
| 現在状態に束縛 | 建玉、エンジンが管理する未約定注文・利用可能なリスク枠 | 再開時のdecision_timeで読み直す。ただし初版の戦略部品には未約定注文を公開しない |

これは参照元3区分とは別の軸である。例えばOutputRefで取得するEMAも市場区間に束縛する。具体的な入力ポートの束縛フィールド・型名は次の詳細設計で決め、InputBindingに読み取り条件を混在させない。

LatestAvailableもWAITに入った後で再開時の最新足を選び直す意味にはしない。最初の対象足と系列の公開規則から必要な観測区間を解決し、不足した区間の到着を待つ。HistoryWindowも同じ基準から窓を固定する。区間指定に当該足を含むか除くかを明示し、突破判定が当該足自身の高値を基準にしてしまうことを避ける。

**待機記録**

- 評価要求ID、対象の部品使用箇所ID、実験/戦略/契約/パラメータの固定参照。
- 対象足の系列IDと区間、解決済み入力区間、および不足している入力の識別情報。
- 既に受け取った取引機会があれば、そのIDと不変の内容（signal_interval、方向、突破水準等）。まだ生成されていない機会を仮に作らない。
- 待機開始時刻、有限の期限、期限切れ時の動作、on_supersededの設定。

取引機会は過去に発生したイベントなので、受信済みの内容を固定することと、市場値を再開時に区間指定で読み直すことは両立する。

**再開契機と処理**

1. 宣言した不足入力に対応する市場データまたは上流出力が到着した場合のみ、その待機要求を再開候補にする。
2. 期限、追い越し、受信済み機会の失効を検査する。受信済み機会については、`OpportunityValiditySpec` で `REQUIRE_UNTIL_ORDER_REQUEST` に分類された条件も読み直し、成立しなくなっていれば `MARKET_STATE_INVALIDATED` で終端にする（第4.5節、2026-09-20 確定、ADR-0031）。複数不足が残る場合は記録を更新して待機を継続し、部分入力で実評価を始めない。
3. 対象区間を変えず市場入力を読み直す。現在状態入力は今回のdecision_timeで取得し、鮮度・型・必要本数を検査する。
4. 条件を満たせば評価し、結果を下流へ配送する。要求IDによる重複処理防止を維持する。
5. 注文要求に実際のdecision_timeを刻み、対象足の終了時刻へ遡らせない。

別系列の無関係な足の到着は再開理由にしない。期限・追い越し・機会失効の検査は実評価とは別のライフサイクル処理として起動できる。元の入力集合に対する再開以外に新たな評価を行う場合は、別の評価要求として識別する。

**待機の伝播**

MarketStateが待機するとき、必要な同区間の出力に依存するTrigger等も未解決依存として保持できる。ただし全下流を無条件にWAITへ変換するわけではなく、解決済みの各入力ポリシーと戦略の実行契約が待機を認める場合に限る。SKIPやERRORで決着した要求を上流到着で復活させない。取引機会生成前の確認/注文は、機会生成後に起動する下流処理として区別する。独立した15m EMA等は通常どおり更新する。

**supersession（追い越し）＝ `REQUEST_SUPERSEDED`**

ここでいう追い越しは**評価要求**に対するものであり、第4.5節で取引機会の終端として定義した `SUPERSEDED`（新しいTriggerを優先する設定、ADR-0032）とは対象が異なる。両者を同じ語で呼ぶと判断履歴（trace）と理由コードで読み分けられないため、**評価要求側の追い越しを `REQUEST_SUPERSEDED` と呼ぶ**（2026-09-20 改訂、ADR-0032）。取引機会側の `SUPERSEDED` は変更しない。改名は語彙のみで、本節で確定済みの追い越しの意味・検査時点・`on_superseded` の扱いは変えない。

同じ評価対象系列の新しい足が公開済みになった場合、期限とは別の失効/遷移理由として追い越しを検査する。WAIT設定のon_supersededに有効方針を明示し、部品/用途別の既定を実験固定時に解決・記録する。役割はStrategyDefinitionの配置から分かり、ComponentInstanceへroleを復活させない。Feature/MarketState等の既定の詳細は別途設計する。

- Triggerの標準方針: 古い対象足が追い越されたら、その待機評価を失効させる。古い突破を後から新たに実行しない。
- 確認の標準方針: 対象確認足が追い越されても、上流の取引機会そのものはこの理由だけでは失効させない。確認の対象足を進める。

**整合性のための実装提案（確認対象）**: 確認足を進める際は、古い評価要求をsupersededとして閉じ、同じ機会IDに対して新しい対象足の評価要求を作る。古い問いの対象区間を上書きしない。機会の当初の開始足IDは保存し、include_start_barによる判定基準を毎回リセットしない。期限も黙って延長しない。これにより「問いは固定」と「確認は後の足へ進める」を両立する。新要求の発行は通常の確認足イベント/宣言済み遷移に従い、無関係な入力到着による旧要求の再開とは区別する。

**22:00の日足が22:00:02に届く例**

| 時刻 | 処理 |
|---|---|
| 22:00 | MarketStateが対象日足の未公開でWAIT。依存する当該区間の処理を保留。独立した15m EMAは更新 |
| 22:00:02 | 日足公開を契機にMarketStateを再開し、固定した区間の市場入力を読む |
| 同時刻の依存順処理 | 21:00〜22:00の1hを対象にTriggerを評価。追い越しがなければO1を生成し、decision_time=22:00:02を記録 |
| 同時刻の確認 | O1生成時点で利用可能な最新の確認足である22:00確定の15m足を開始足として識別。include_start_bar=Trueなら確認可能、Falseなら次の対象足へ |
| 同時刻の注文判断 | 再開時の建玉・未約定注文・リスク枠を使って発注可否を判断。許可ならI1を生成し、22:00へ遡及しない |

リスク枠が他戦略の建玉等で埋まっていれば、過去に余裕があっても現在の発注を拒否する。検出された機会という事実を消すこととは区別し、リスク拒否として記録する。拒否した発注試行と再審査の扱いは以下の確定規則に従う。リスク審査と注文受付間の競合を防ぐ予約/処理順序は口座基盤の設計対象。

**リスク拒否後の発注試行と再審査（確定）**

- リスク拒否となった発注試行は終了する。後からリスク枠が空いたこと、次の足が確定したこと、同じ取引機会の通知が再配送されたことだけでは再発注しない。
- 初期の標準動作は再審査なし。同じ取引機会から暗黙に別の発注試行を生成することも禁止する。機会が発生した事実と拒否履歴は保存する。
- 再審査は実験前に明示的に設定した場合だけ許可する。終了済みの試行を復活させず、元の機会IDと拒否した試行IDへ関連付けた新しい試行として識別する。
- 明示設定による再審査でも、その実時刻の口座・建玉・未約定注文・リスク枠と、機会の有効性を検査する。過去の審査結果を使い回さず、機会の期限を暗黙に延長しない。
- 再審査設定の型・配置、起動条件、回数上限、期限、確認結果の再利用条件は次の詳細設計対象とする。設定の存在だけで無制限の再試行を許可しない。初版で再審査機能が未実装なら、その設定は明示的に拒否する。

**同じ問いが同じ市場値を返すための条件**

対象区間だけでなく、データsnapshot・訂正履歴・Feature実装・パラメータ・初期化規則を固定する。区間が同じでも、後から訂正されたデータを無条件に読み込めば答えは変わる。固定snapshotの遅延シナリオでは値を変えず、公開時刻だけを変える。訂正を扱う場合は別の明示的な版/公開イベントとして設計する。

EMA等の状態付きFeatureは対象区間に対応する履歴出力を参照または再現し、現在の最新キャッシュを過去区間の答えとして使わない。過去区間の再計算で通常更新中の状態を巻き戻さない。

待機開始・不足入力到着・再開・期限切れ・追い越し・機会失効・リスク拒否を記録する。各再開には対象区間、使用観測/Feature出力の識別子、実際の読取時刻、decision_time、因果順序を含める。同じシナリオの再実行で照合できるようにする。

### 4.3.15 実行時の出力データ（3層構成・フィールドを確定）

共通の出力記録 `OutputRecord`、市場の観測を表す `Observation`、役割ごとの内容型を分ける構成を採用する。

- `OutputRecord[T]`: エンジンが付ける出力の同一性、評価との関連、実判断時刻、利用可能時刻、因果順序と、内容Tを保持する。
- `Observation[T]`: 市場の観測値Tに、対象・対象区間・鮮度基準を付ける。
- 内容型: `ConditionState`、`MarketPermission`、`Opportunity`、`ConfirmationResult`等が役割に固有の情報を保持する。

市場の状態は `OutputRecord[Observation[MarketPermission]]`、取引機会は `OutputRecord[Opportunity]` とする。イベントまで一律にObservationで包む必要はない。実行時の出力と、その仕様を宣言するOutputSpecを区別する。

部品は内容を計算し、エンジンが共通の識別・時刻情報を付ける。部品が独自に発生時刻や実行履歴を書き換えない。入力不足・評価見送りは正常なFalse等の出力に変換せず、評価記録として残す。

**確定したフィールド（2026-09-18）**

| 型 | フィールド |
|---|---|
| `OutputRecord[T]` | `output_id`、`evaluation_id`、`producer`、`decision_time`、`available_at`、`sequence`、`payload: T` |
| `Observation[T]` | `value: T`、`subject`、`observation_interval`、`freshness_time` |
| `ConditionState` | `satisfied: bool` |
| `MarketPermission` | `allow_long: bool`、`allow_short: bool` |
| `Opportunity` | `opportunity_id`、`symbol`、`direction`、`signal_interval`、`reference_values` |
| `ConfirmationResult` | `opportunity_id`、`confirmation_interval`、`confirmed: bool` |

上記6型のフィールド名と責務を確定する。IDの具体的な表現、対象・区間等の補助型の内部構造、細部の検証規則は引き続き詳細設計対象とする。これらの残項目を理由に、確定したフィールド構成を未承認として扱わない。

例: 22:00に終了した日足からEMAを22:00:02に計算した場合、decision_timeと、計算遅延がなければavailable_atは22:00:02。Observationの対象は当該日足、freshness_timeは22:00。EMAの計算に使った履歴全体はevaluation_idから追跡し、observation_intervalを全計算履歴の区間と混同しない。

Opportunityのreference_valuesは、突破水準等を契約で名前と型を宣言して保持する。機会の内容は不変とし、失効・確認待ち・発注試行は別のライフサイクル記録で管理する。ConfirmationResultのFalseは条件未成立であり、入力不足・期限切れ・追い越しと区別する。

次は注文・Protection・Exit・資金管理の接続、単一バックテストと評価の境界の順に進める。共通記録とpayloadの型検査、補助型の内部構造、宣言した参照値のスキーマ、確認結果の配送と重複防止の詳細も、必要な箇所で具体化する。

### 4.4 時間足の用途名を必須構造にしない

`context`（環境認識）、`signal`（機会検出）、`execution`（執行）、`management`（保有管理）は、時間足の用途を説明するための名前であり、部品そのものではない。

新基盤ではこれらと MarketState / Trigger 等を固定対応させない。必要なら説明用の別名やテンプレートにはできるが、入力参照や評価スケジュールの唯一の指定方法にはしない。

特に、Exit の計算が1hごとでも、既に置かれたストップの約定判定を1hごとに限定する必要はない。**戦略判断の頻度と、約定処理に使用する市場データの粒度を分離する。**

### 4.5 情報を持つ取引機会

Trigger の出力は単なる真偽値ではなく、少なくとも ID・発生/利用可能時刻・方向・対象銘柄・根拠情報を持てる構造にする。

例: 「レンジ突破後にリテストを待つ」場合、突破時のレンジ上限を保存し、ExecutionFilter がその水準を参照する。最新のレンジ上限に暗黙に置き換えない。

取引機会の状態と注文・建玉の状態は分離する。

**確認待ち中の条件の再検査（2026-09-20 確定、ADR-0031）**

> 確認待ちのOpportunityが参照する条件は、発生時に固定する条件と、待機中に継続して成立を要求する条件に明示的に分類する。分類はOpportunityValiditySpecとしてStrategyDefinitionに必須指定し、暗黙の既定値を設けない。
>
> SNAPSHOT_AT_OPPORTUNITYに指定された条件は、Opportunity生成時のOutputRecordを固定し、その後の更新によって再評価しない。
>
> REQUIRE_UNTIL_ORDER_REQUESTに指定された条件は、確認評価のたび、およびOrderRequest生成直前に、そのdecision_timeで利用可能な最新の出力を読み直す。条件が成立しなくなったOpportunityはMARKET_STATE_INVALIDATEDで終端とし、条件が再び成立しても復活させない。新たな取引には新しいTriggerとOpportunityを必要とする。
>
> 再検査によって、Opportunityに固定された方向、signal interval、突破水準、参照値、Trigger時点の根拠を変更してはならない。再検査するのはOpportunityの現在の有効性であり、過去のTriggerを現在値で再計算することではない。
>
> 再検査対象の入力が欠損している場合は、そのValidityBindingに宣言されたMissingInputPolicyを適用する。欠損を不成立や直前値へ暗黙変換してはならない。待機する場合もOpportunity本来の期限は延長しない。

**再発火と複数Opportunity（2026-09-20 確定、ADR-0032）**

> Triggerの各発火は、それぞれ固有のopportunity_idを持つ不変のOpportunityを生成する。同方向・逆方向という理由だけで、ランタイムが既存Opportunityを暗黙に破棄、更新または統合してはならない。
>
> 複数Opportunityの関係はOpportunityConcurrencySpecとしてStrategyDefinitionに必須指定する。ランタイムは複数の有効なOpportunityを同時に保持できなければならない。
>
> 既存Opportunityの内容を新しいTriggerの内容で上書きする「置換」は禁止する。新しいTriggerを優先する設定であっても、既存OpportunityをSUPERSEDEDで終端にし、新しいopportunity_idを持つOpportunityを生成する。
>
> 同一event_idの再配送は冪等性検査で除外し、新しいOpportunityを生成しない。異なるTriggerイベントは、方向・価格・内容が同じでも別の市場事実として記録する。条件が連続してtrueであることによる毎足の再発火は、Trigger部品の遷移検出および再武装規則で制御する。
>
> 各Opportunityは独立した確認開始区間、期限、ValiditySpec、確認履歴を持つ。あるOpportunityの確認、失効、無効化または発注試行によって、別のOpportunityを暗黙に変更してはならない。
>
> 複数のOpportunityが同時にOrderRequestへ到達した場合は、決定論的な受付順とRiskPolicyで審査する。ある注文が受け付けられたことを理由に他のOpportunityを終了する場合は、on_order_acceptedへその規則を明示する。

**取引機会のライフサイクル状態（2026-09-20 確定、ADR-0031・ADR-0032）**

上記2決定が導入する終端状態を含め、取引機会の状態を次のとおりとする。注文状態（第4.7.13節の PENDING / FILLED / CANCELED / EXPIRED）とは別の状態機械であり、混同しない。

| 状態 | 意味 |
|---|---|
| `ACTIVE` | 生成済みで、確認待ちまたは発注試行が可能 |
| `CONFIRMED` | 後続確認が成立し、`OrderRequest` へ進んだ |
| `EXPIRED` | `entry_policy` の期限に到達して終端 |
| `MARKET_STATE_INVALIDATED` | `REQUIRE_UNTIL_ORDER_REQUEST` の条件が成立しなくなって終端（ADR-0031）。復活させない |
| `SUPERSEDED` | 新しいTriggerを優先する設定により終端（ADR-0032）。内容の上書きではなく終端＋新規生成 |
| `CLOSED_BY_ORDER_ACCEPTANCE` | 別の注文が受け付けられたことを理由に終端（ADR-0032）。`OpportunityConcurrencySpec` の `on_order_accepted` に規則を明示した場合に限る。規則がなければ暗黙に終端させない |

受付起因の終了には専用の終端状態を使う（2026-09-20 確定、ADR-0032）。`SUPERSEDED` の意味を受付起因の終了まで広げることはしない。両者を1つの状態にまとめると、判断履歴（trace）で「新しい Trigger に置き換わった機会」と「他の注文が通ったので終わった機会」を集計上区別できなくなるためである。

`SUPERSEDED` は取引機会の終端であり、第4.3.14節の評価要求に対する追い越し（`REQUEST_SUPERSEDED`）とは対象が異なる。

要決定として残るのは、発火時に凍結する値と随時更新する値の具体的な列挙（`Opportunity.reference_values` のスキーマ宣言と合わせて D04 で確定する）。

### 4.6 条件・イベントの合成

共通操作として、条件の AND/OR、状態の遷移検出、N本継続、Aの後N本以内のB、発生後の確認待ちを段階的に用意する。状態とイベントを暗黙変換しない。

依存関係は型付きグラフで表し、組合せ循環は拒否する。履歴や順序を持つ部品の内部状態は別途明示する。任意コードを記述できる巨大な独自言語や、無制限の汎用状態機械エディターは初期には作らない。

### 4.7 注文・Protection・Exit・資金管理の接続

#### 4.7.1 合意した責務と初版の範囲

| 担当 | 責務 |
|---|---|
| Order | 数量決定前の注文意図。銘柄・方向・注文種別・価格条件・有効期限を指定 |
| Protection | 初期SLを定義する。価格水準と約定価格からの距離を混同しない |
| 資金管理 | RiskPolicyと現在の口座状態から数量・発注可否を決める。戦略外に置く |
| 約定モデル | 実際の約定価格・数量・費用と、SL/TPへの到達を処理する |
| Exit | 初期TP、約定後のトレーリング、全数量の決済要求等を生成 |

機会ID、発注試行ID、受け付けた注文IDは別に持つ。注文、約定、建玉、リスク予約も別管理とし、初版が1建玉でもこの境界を設ける。戦略内の管理要求の競合と、市場での約定競合を分ける。

初版の方向は単一ペア・成行・同時1建玉・初期SL必須・固定RRのTP・全数量決済。指値・部分約定・増し玉・部分決済は後から追加する。未対応の設定は拒否する。

#### 4.7.2 RiskPolicyの配置（確定）

口座単位のRiskPolicyをエンジン側に置き、実験がその版と設定を固定する。StrategyDefinitionにポリシー本体を持たせない。資金管理はそのポリシーを解釈・適用する機能、口座/予約台帳は現在状態とする。

将来の戦略別配分も、エンジン側の戦略ID別予算として表現し、口座全体の上限内で適用する。戦略ごとに独立したリスク枠を作って共有口座の総量制約を回避しない。初版は1つの口座ポリシーで十分である。ResearchPolicyは研究の規律、RiskPolicyは資金制約であり別物。

#### 4.7.3 SL・数量・約定ずれ・丸め（具体化案）

初版は注文受付前に解決した絶対価格のSLを凍結する。ブレイク足安値等の直接の水準だけでなく、「発注判断時の参照価格 − その時点のATR×2」を絶対価格へ解決して凍結する方式も表現できる。ただしこれは「実約定価格 − ATR×2」とは別の意味である。

実約定価格を起点にした距離型SLは、距離・ATRの観測時点・換算規則を事前固定し、約定時に絶対価格へ解決する別のProtection型を要する。初版では未対応として拒否し、価格水準型へ暗黙変換しない。追加時には予約計算、約定時初期化、gap処理を合わせて設計する。

注文受付時に数量を確定し、実約定価格を見て受付済み数量を遡及変更しない。固定RRのTPは実約定価格と実際の初期SLから算定する。算定不能・不正なSL等への対応も執行契約に置く。

推奨する丸め手順:

1. 銘柄の価格刻みでSLを解決・丸めする。買いSLは下側、売りSLは上側へ丸める案とし、意図より近いSLへ黙って変更しない。
2. 丸め後SL、事前の参照価格、許容する不利な約定ずれ、費用・口座通貨換算を使って数量上限を計算する。
3. 数量は数量刻みで切り下げる。最小数量未満は拒否し、切り上げてリスク上限を超えさせない。
4. 丸め後の数量・価格でリスク、証拠金、レバレッジ等を再検査する。
5. TPの丸めは、買いなら下側・売りなら上側へ寄せ、利益を上方に丸めない案。entryとの位置関係を再検査し、丸め後の実RRを記録する。SLとTPの丸め方向は単に同じ規則を使うのではなく目的を区別する。

参照価格に対する許容不利約定幅を注文受付前に固定する。上限は成行約定の保証ではない。上限外の成行約定が起きた場合、約定をなかったことにせず、実約定と超過理由を記録して緊急決済要求を生成する案。決済もその時点以降の執行モデルに従い、同値・無損失での撤退を保証しない。実行可能な価格制限付き注文で事前に拒否できる場合は、別の注文意味論として定義する。

#### 4.7.4 リスク予約と建玉への移行

ユーザー提示の基準距離×数量を基礎とし、初版では以下の保守的な予約を推奨する。

```text
予約額 = 許容不利約定価格から丸め後SLまでの損失幅
         × 数量 × 口座通貨への換算率
         ＋ ポリシーで定義した費用予算
```

SLへのgap等により実損失が予約額を超える可能性はあり、予約を最大損失保証として扱わない。換算価格の時点と費用の範囲も記録する。

予約は注文IDに紐付け、受付と同じ不可分な処理で確保する。取消・拒否・失効が確定すれば解放する。約定なら予約を単純にコピー/解放するのではなく、実約定価格で再計測したリスクを記録し、建玉の割当へ不可分に移す。取消要求を送っただけでは解放しない。未実装の部分約定では残注文と建玉への分割が必要になるため、初版には混在させない。

以下を別の値として保持する。

- 注文時の予約額。
- 約定直後/現在のSLに基づく計測リスク。
- 新規発注可否に使う消費済みリスク枠。

初版では受付時に確定した消費済み枠を決済まで保持し、約定価格・トレーリング・残高変化で再計算しない。約定時の実リスクと予約額との差は別の計測値として記録する。超過時は元の割当を上書きせず、違反として記録して約定ずれ・口座保護規則に応じた緊急処理を行う。固定割当の集計だけで実リスク監視を代替しない。ポジション終了をもって枠を解放する。

決定論的な受付は、まず因果関係を満たして準備できた要求の集合を作り、その中を `(decision_time, strategy_priority, opportunity_id, attempt_id)` で全順序化する案。優先度の向き、ID比較規則、優先度設定を実験前に固定する。時間キーで未完成の上流を追い越したり、循環する因果辺を追加したりしない。審査・予約・受付を逐次確定し、次の要求が更新済み台帳を見る。

#### 4.7.5 注文状態と失効

発注試行は注文意図と保護計画を受け取り、リスク審査を経て数量付き注文として受付される。拒否した試行は終了し、再審査は既定の明示設定規則に従う。

受付前の試行と受付済み注文は別管理にする。受付済み注文の状態は第4.7.13節のPENDING / FILLED / CANCELED / EXPIREDとし、受付前拒否を注文状態に含めない。不変の要求と状態遷移イベントから現在状態を投影し、当初の要求へ任意のフィールドを後から埋めて履歴を失わない。

次足始値での成行も約定まで予約を持つ。注文に有効期限/有効な約定機会を宣言し、期限切れを注文の終端イベントとして記録して予約を解放する。欠損やデータ末尾で無期限に保留しない。具体的な次足の定義、満了時刻の包含、満了と約定の同時刻競合は執行契約で別途固定する。将来の指値も同じライフサイクルを使うが、対応前は実行を拒否する。

#### 4.7.6 SL所有権と管理要求の検査

初期SLはProtectionが生成し、注文受付後は保護計画として凍結する。未約定中にProtectionが更新し続けることはない。約定時の建玉初期化でSL管理権を単一のExit部品へ移す。複数のSL更新元を同じ建玉へ接続した構成は設計エラーとする。複合ロジックは1つの所有者の内部で明示的に合成できるが、外部に複数のSL書込権を持たせない。

- 買いSLは上げる方向、売りSLは下げる方向のみ許可する。同値は変更なしとして記録可能。初期SLからだけでなく、直前の有効SLに対しても単調性を検査する。
- 丸め後のSLが現在の決済側価格を越える、または等しくなる更新は理由付き拒否とする案。買いはbid、売りはask基準とし、ask不在なら明示されたspreadモデルを使用する。更新を暗黙の成行決済へ変換しない。
- 同じ建玉への更新と決済要求が同時なら決済を優先し、更新は理由を記録して破棄する。
- 閉じた建玉への要求は理由付き拒否であり、通常の競合として実行全体を停止させない。
- トレーリングは宣言した足の終値確定後に評価する。足内の到達判定は行わない。

#### 4.7.7 SL/TPの執行と足内時系列

SL/TPの到達判定は戦略部品のOnBarCloseとは独立し、約定モデルが執行用データの各足で処理する。ライブでの待機注文と、バックテストでの約定シミュレーションに相当する責務である。

既存建玉については、足Tの開始前に有効だったSL/TPで足Tの高値・安値による到達判定を行い、足Tの終値で計算・受付した更新は次の執行足以降へ適用する。管理足と執行足が異なる場合の「次」は次の執行用データの足を意味する。

ただし、この規則を新規約定直後の初期SL/TPに一律適用してはいけない。次足始値で約定した新規建玉は、約定→初期SL有効化→Exitによる初期TP算定を行い、同じ足のその後の値動きに対する保護判定の対象にする。終値約定なら過去の同一足の高値・安値を使わない。約定から初期化までの遅延は、初版では因果順序上連続した処理とし、将来の遅延モデルは明示的に追加する。

OHLCだけでSL/TP双方に触れたときの順序は観測できない。**初版は損切り（SL）優先。同一足内で SL と TP の両方に届いた場合は常に SL が先に成立したとみなす**（2026-09-20 確定、ADR-0030）。これは保守的な仮定であり、実際の価格経路が分かったことにはしない。

将来、下位足（例: 15分足）で先後を判定する方式へ拡張できるよう、次の拡張点を D06 に明記する。

1. **判定方式が差し替え可能であること**。足内の SL/TP 先後判定は約定モデル内の差し替え可能な判定方式として定義し、SL 優先規則をその初版の実装とする。呼び出し側に SL 優先を直接埋め込まない。
2. **初版の判定方式が結果に記録されること**。どの判定方式でその約定が決まったかを、約定記録および run manifest に記録する。後から別方式で再計算した結果と混同できないようにする。

gap、約定ずれ超過、既にSLを越えた始値での約定は実約定を記録した上で執行モデルが処理し、複数の緊急/保護決済で二重決済しない。

#### 4.7.8 判断根拠とID連鎖

```text
機会ID → 発注試行ID → 注文ID → 約定ID → 建玉ID → 管理要求ID
                         └→ リスク予約ID
```

注文意図、SL算定、数量審査、予約、約定時再計測、TP算定、更新/決済要求について、使った観測/出力ID、対象区間、実判断時刻、ポリシー版、丸め前後の値、承認/拒否理由を記録する。約定には執行データ・価格モデル・費用の根拠を関連付ける。名前だけ同じ指標の最新値を後から読み直して根拠を再構成しない。

#### 4.7.9 RiskPolicy配置・価格水準型SL・予約計算（構造を確定）

RiskPolicyのエンジン側配置、初版の価格水準型SL、許容不利約定幅を使う予約計算を採用する。具体的なリスク上限の追加決定と残る確認事項は第4.7.10節を正本とする。約定ずれ幅等の未提示の数値まで承認済みとはしない。

**A. RiskPolicy**

| 確定する観点 | 正面案 |
|---|---|
| 適用範囲・所有者 | 口座単位で1つのエンジン側ポリシーを適用。実験設定が版と内容を固定 |
| 戦略との境界 | StrategyDefinitionは数量予算を所有しない。戦略IDを審査へ渡す。将来の戦略別配分は口座側で管理 |
| 審査の基準時点 | 受付判断時の口座状態・予約台帳を使用。1試行予算の基準は口座残高へ変更（第4.7.10節）。MTMは証拠金等の検査に引き続き使用 |
| 1試行の予算 | 初版は受付判断時の口座残高×2%。使用率・率の上限とも2%。独立した金額上限の扱いは第4.7.10節で具体化 |
| 口座全体の予算 | 設定した総リスク枠から既存の消費済み枠・予約を引いた残額で制限 |
| その他の上限 | 数量上限、証拠金/レバレッジ、同時保有・未約定枠を合わせて検査 |
| 更新と再現性 | 実行中にポリシーを変更しない。審査ごとの口座snapshot、計算根拠を記録 |
| 競合 | 因果的に準備できた要求を全順序で処理し、審査・予約・受付を不可分に確定 |
| リスク枠回復 | 初版は建玉決済まで割当を戻さない。MTM資産低下等で新規余力がなくなれば新規を拒否する。既存建玉の強制縮小は別の口座保護規則として明示する |

初版は戦略別の異なるリスク率を導入せず、共通の比較条件を使う案とする。RiskPolicyは要求する上限、ExecutionPolicyは約定の意味、CostModelは価格差・費用を扱う。リスク計算はそれらの固定参照を利用し、費用モデルを別実装で複製しない。

**B. 価格水準型SL**

| 確定する観点 | 正面案 |
|---|---|
| 表現 | 初期SLは解決済みの絶対価格。銘柄と価格刻みを明確にする |
| 算定基準 | 利用可能な観測または明示した発注判断時の参照価格を使う。Protectionの観測区間とdecision_timeを記録 |
| 固定時点 | 審査・注文受付前に価格刻みへ丸め、受付後は凍結 |
| 受付前の妥当性 | 買いSLは判断時bidより下、売りSLは判断時askより上。逆側/同値、不正数値、必要な価格情報不足は拒否 |
| 丸め | 買いSLは価格刻みで下へ、売りSLは上へ。丸め後の値を数量・予約計算に使用 |
| 未約定中 | 市場価格やATRが変わってもSLを再計算しない。注文変更は将来の明示機能とする |
| 約定時 | 固定SLをそのまま引き継ぎ、数量を遡及変更しない。SLを越えた約定は通常のTP計算へ進めず保護/緊急処理へ |
| 非対応 | 実約定価格を起点にSLを移動させる距離型は初版では拒否 |

「発注判断時の参照価格−ATR×2」を価格へ解決して固定することは許可するが、実約定価格基準とは異なる部品意味として宣言する。

**C. 不利約定幅による予約**

受付前に、買いは購入側価格（ask）、売りは売却側価格（bid）を参照価格として固定する。bidしかない場合は指定したspreadモデルでaskを導く。参照価格・SLの価格側を明示し、spreadを価格にも費用にも重複して加算しない。

銘柄ごとの許容不利約定幅は実行ポリシーで事前設定し、受付時に絶対価格幅へ解決して記録する案。pips指定を許す場合も銘柄定義の換算を使う。値幅を有利に縮めないよう価格刻みへの解決を定義する。

```text
d = +1（買い）、-1（売り）
P_ref = 受付前の参照価格
Δ = 許容不利約定幅（非負の絶対価格幅）
P_limit = P_ref + d × Δ
S = 丸め後の初期SL
Q = 基準通貨単位の数量
X = 決済通貨から口座通貨への審査時換算率
C(Q) = 価格側に織り込んでいない費用の予約予算（口座通貨）

予約額 R(Q) = d × (P_limit − S) × Q × X + C(Q)
```

正常な受付条件で `d × (P_limit − S) > 0` を要求する。費用予算は往復手数料とSLでの決済slippage等、何を含むかを固定する。Δで含めたエントリーslippageを費用で重複加算しない。換算率は利用可能な市場データから取得し、不足時に将来値を使わない。Xや費用は将来まで保証された値ではない。

1試行の予算と口座残余予算の小さい方をBとし、R(Q)<=Bおよびその他の口座制約を満たす最大の数量を数量刻みで求める。数量は切り下げ、丸め後を再検査する。最小数量を満たせなければ拒否。固定手数料等があるため、単純な距離による割算だけを唯一の数量式にしない。

| 確定する観点 | 正面案 |
|---|---|
| Δの置き場所 | 戦略の利益探索パラメータにせず、固定した実行ポリシーに置く |
| 予約の確保 | 注文受付と不可分に確保し注文IDへ関連付ける |
| 不利約定の判定 | `max(0, d × (P_fill − P_ref)) > Δ` なら超過。上限一致は許容 |
| 約定時の再計測 | 実約定価格・固定SL・現在の換算/費用情報でリスクを記録し、予約との差を保存 |
| 許容内 | 実約定後の口座制約も検査し、建玉へ移行。初版は予約の余りを解放しない |
| 超過 | 実約定を残し緊急決済要求。約定をキャンセルしたことにしない |
| Δ内でも総量違反 | 換算変動・費用等による超過を隠さず口座保護処理へ。新規約定の緊急決済を初版の候補とする |
| 解放 | 注文の取消/拒否/失効確定、または建玉への移行。移行時は消費枠が消えないよう不可分に行う。建玉枠は決済まで保持 |

数値例（費用・通貨換算を省いた説明用）: USDJPY買い、P_ref=150.00、S=149.50、Δ=0.05なら、予約の価格幅は0.55。数量10,000なら予約は5,500円。150.03約定ではSLまでの幅は0.53で計測リスク5,300円、枠は5,500円を保持する。150.08約定なら不利幅0.08で上限を超えるため、実約定を記録して緊急決済へ進む。これらの数値を推奨パラメータとして採用するものではない。

数値の決定状況: 初版の使用リスク率2%、1試行の率上限2%、口座総量の率上限20%（第4.7.10節）。独立した固定金額上限は初版では設けない。レバレッジ/保有枠、銘柄ごとのΔ、費用予算、価格/数量刻みは別途具体化する。口座強制縮小の対象と優先順位、緊急決済の最短実行可能時点も明示する。どの上限もgap等に対する実損失の保証ではない。

#### 4.7.10 リスク率・金額上限の初期設定（確定）

- 使用リスク率と1試行の率上限はともに2%。予算は受付判断時のbalance×0.02。
- 口座全体の率上限は20%。予算は新規受付判断時のbalance×0.20。
- balanceは計上済みの実現損益・費用・入出金等を反映した口座残高で、未実現損益を含めない。equityは含み損益込みのMTM資産であり区別する。
- 初版は予算の分母にbalanceを使用する。equity基準への切り替えは、明示的なポリシー拡張とする。equityは証拠金/レバレッジ/口座保護検査に引き続き使う。
- 初版は独立した固定通貨額の上限を設けない。残高×2%から求めた予算を、受付時の金額上限として検証・記録する。
- 既存の予約・建玉の消費済み枠は、それぞれの注文受付時に確定した口座通貨額を保持する。新規受付時に分母だけを現在のbalanceで更新し、既存枠を現在残高・価格・SL・換算率で再計算しない。
- 実約定後やトレーリング後の計測リスクは別に記録・監視する。予約から建玉への移行で同じ枠を二重計上しない。

```text
B = 受付判断時のbalance（口座通貨）
r = 0.02
U = 建玉の受付時固定割当の合計 + 未約定注文の受付時予約額の合計

trial_budget = B × r
account_remaining = max(0, B × 0.20 − U)
admission_budget = min(trial_budget, account_remaining)
```

意図生成時と受付時の間にbalanceが変わっていれば、受付時のbalanceで再計算する。予約額R(Q)に許容不利約定幅・費用予算・通貨換算を含め、R(Q)<=admission_budgetかつ口座制約を満たす数量を求める。数量を数量刻みで切り下げ、丸め後の予約額を再検査する。最小数量でも超過なら拒否し、数量を切り上げない。Bが非正または口座状態が検証不能な場合も新規を拒否する。

2%は必ず消費する要求ではない。残余予算や数量刻み等で実際の予約額は小さくなり得る。残高の減少で既存枠が新しい総量上限を上回れば、新規受付を拒否する。既存枠を縮小して帳尻を合わせず、既存建玉への強制処理は口座保護契約に従う。

balance基準では含み損が増えても予算の分母が減らない。20%は単純には2%の10試行分であり、初版の同時1建玉では通常この総量枠は主要な制約にならない。複数戦略・複数建玉へ拡張する前に、20%という値とbalance基準の両方を見直す。これを一般的な推奨水準とは位置付けない。

これらは受付時の予算であり、gap等による実現損失や最大ドローダウンの保証値ではない。明示された約定超過・緊急処理を維持する。

#### 4.7.11 初版の成行約定方式（確定）

**方式**: 注文受付後、因果順序上まだ到来していない最初の執行足の始値で約定する。評価足と執行足を分け、実験設定が執行足を固定する。以下では既存データの15mを執行足とする。終値約定は初版に混在させない。

時刻だけでなくイベント段階を持つ。通常の公開遅延なし・注文処理遅延なしのモデルでは、境界Tで前足close→判断→審査/受付→次足openの順を明示し、Tのclose情報で受け付けた注文がTから始まる次足openへ進める。これはOHLCシミュレーターの明示的なゼロ遅延仮定であり、実市場で終値確認後に始値約定が保証される意味ではない。

| 例 | 判定 |
|---|---|
| 22:00 closeの公開・判断・受付が、同じ22:00のopen段階より前に完了 | 22:00〜22:15足のopenで約定可能 |
| 日足が2秒遅れ、WAIT再開で22:00:02に受付 | 22:00のopenは過去。次の22:15 openが最初の候補 |
| 22:15のopen段階より後に注文受付 | 次の22:30 openが最初の候補 |
| 対象のopenが取引セッション外 | 実際に存在する次の執行足が候補。ただし注文期限内であること |
| 本来存在する候補足が欠損 | 次の正常足へ黙って飛ばさない。データ不備/注文終端処理を次節で定義 |

受付時の数量・SL・予約計算に、まだ処理していないopen価格を利用しない。open処理は執行モデルだけが行い、戦略部品へ未完了足のHIGH/LOW/CLOSEを公開しない。Tの到来時には前足中に発生した既存建玉の保護決済等を反映した口座状態を作り、同時刻の審査と執行の順を一貫して記録する。既存保留注文も同じ受付・優先順位契約で管理する。

**約定価格**: 買いは対象open時のask、売りはbidを基準に執行モデルのslippageを適用する。bidのみならspreadモデルでaskを導く。参照価格との差は事前固定した許容不利約定幅で検査する。許容幅を超えても実約定は記録し、緊急決済要求へ進む。現在モデルで観測できない足途中の価格を補間して都合よく約定させない。

遅延注入で22:00:02受付が22:15約定になるのは15m OHLCモデルの粒度による近似であり、ライブ成行が必ず15分待つ意味ではない。細粒度データや別執行モデルを追加すれば、同じ注文意図でも実行機会が変わる。執行足・データ・遅延・コストの版を結果へ記録する。

**残る例外処理**: 約定候補の欠損、データ末尾、注文期限とopenの競合は次の設計対象。約定直後の緊急決済とSL gapの同じopen内での処理は第4.7.12節で定める。約定前に未来のopenを覗いて注文を拒否すること、足途中の受付を同じ足の始値へ遡らせることは許可しない。

#### 4.7.12 足内約定・未約定注文の境界・同じ始値での緊急決済

第4.7.11節の4点（始値約定への統一、執行足の固定、同時刻close→判断/受付→open、open処理後の受付は次のopen）を確定する。その前提となる執行規則を以下のように補足する。

**終値評価より先に足内約定を反映する**

```text
前の執行足が終了
→ その足で有効だったSL/TPによる内部約定を解決
→ 建玉・損益・balance・消費済み枠を更新
→ 確定データを戦略に公開
→ Feature・MarketState・Trigger・確認を依存順で評価
→ 注文意図・Protection・リスク審査・予約・受付
→ 次の執行足のopen処理
→ 既存建玉のgap保護決済・適格な成行注文の約定・新規建玉初期化
```

内部約定はエンジンが執行データから処理し、その後で戦略へ確定足と更新済みの許可された現在状態を公開する。終値で計算したSL更新を、その足の過去のhigh/lowへ適用しない。OHLCだけでは正確な足内到達時刻は不明なので、対象足・解決段階・モデル上の順序を記録し、実測の約定秒を捏造しない。同一足のSL/TP競合は約定モデルの固定規則を使う。

執行用データ自体が遅れる場合、内部約定解決前に同じ足を使う戦略判断だけを先へ進めない。執行用データの可用性と戦略向け公開遅延の区別、執行データ遅延/欠損時の停止はデータ・状態遷移設計で明示する。前足終了処理、既存建玉のopen-gap、新規注文の受付/約定を混ぜず、各段階を追跡する。

**初版では戦略から未約定注文を見せない**

戦略部品は未約定注文の一覧・状態を参照せず、取消要求も発行しない。注文層が有効期限・取消・失効を扱い、資金管理は未約定予約とポジション枠を引き続き検査する。RuntimeInputRefで未約定注文を指定する構成は初版の能力検査で拒否する。

待機注文がある間に新たな機会が発生しても、注文層・リスク層で同時保有枠、予約枠、重複試行を検査する。初版の1建玉制限は建玉がないことだけで判断せず、受付済みの新規エントリー注文による枠占有も含める。戦略が注文を見ないことによって無制限に受付できることにはしない。

**約定直後の緊急決済だけは同じopenで処理する**

通常の戦略による成行要求は次の適格なopenで約定する。例外として、openでの新規約定直後にエンジンが生成する緊急決済要求は、そのopenの反対売買側価格へ決済slippageを適用して処理する。戦略が要求に緊急フラグを付けて通常規則を迂回する経路は作らない。

買い建玉を閉じる価格はbid、売り建玉を閉じる価格はaskを基準とする。入場と撤退の各約定・spread・slippage・手数料を記録し、無損失の取消として扱わない。即時処理は執行モデルの仮定であり、ライブの無遅延約定を保証するものではない。これ以外の時点での口座保護処理の執行時点は別途設計する。

**SLを越えた始値の扱いと決済理由の優先**

- 買い建玉のSL/TP到達はbid、売り建玉はaskで判定する。ask未収録時は明示されたspreadモデルで必要な価格系列を構成する。
- 新規成行約定の直後、固定SLを越えるgapが成立していれば、同じopenで通常のSL決済として処理する。買いはopen bid、売りはopen askにSL用slippageを適用し、到達不能なSL価格で約定させない。
- この場合もエントリー約定は記録する。分類は緊急決済ではなくSL到達。約定ずれ上限超過も同時に成立していれば、超過は診断として残すが2件目の決済を実行しない。
- SL gapがなく、約定ずれ/口座保護条件により緊急撤退が必要なら同じopenの緊急決済へ進む。
- 生存している建玉だけに通常の初期TP・保有管理を継続する。閉鎖状態とポジションIDで二重決済を防止する。

既存建玉についてもopenでSLを飛び越えた場合は通常のSL gap処理を行う。SL/TP待機注文による約定はそもそも「戦略が生成した成行要求を次openまで待つ」規則の対象ではなく、約定モデルが市場の到達に応じて処理する。

**参照価格から約定までの経過時間を記録する**

参照価格の観測ID・市場時刻、受付時刻、約定時刻を保持し、参照価格から約定までの経過時間と受付から約定までの待ち時間を分けて算出する。22:00の価格を22:00:02の受付で固定し22:15に約定する場合、前者は15分、後者は14分58秒となる。参照価格を約定直前の値へ置き換えて許容幅超過を隠さない。

遅延シナリオ別・執行粒度別に、参照価格経過時間、不利約定幅、緊急決済件数を診断できるようにする。粗い執行足による待ち時間の影響と、戦略自体の機会品質を区別して評価する。

**保守的な執行変種を実験設定に用意する**

最初の適格なopenを使う基本モデルに加え、そのopenを1回見送り次の執行足openで入場する変種を用意する。型名案は `entry_delay_bars`、初期値域は0または1。設定値・モデル版は実験前に固定し、OOS結果を見て有利な方を採用しない。

この変種は新規エントリーの約定機会を遅らせるためのものとする案。通常の決済要求への適用は別途明示し、SL/TP到達判定や約定直後の緊急決済を1足遅らせない。遅延分だけ未約定予約は保持し、有効期限を暗黙延長しない。約定候補足が欠損したことを、意図的な1足見送りとして数えてはならない。

基本ケースは22:00受付→22:00 open、変種は22:00受付→22:15 open。公開遅延で22:00:02受付なら基本は22:15 open、変種は22:30 open。どちらも同じ注文/保護/リスク契約を使い、予約時の参照価格・数量・SLは約定待ち中に更新しない。

#### 4.7.13 注文状態・有効期限・欠損・末尾（補足を含め確定）

**A. 共通の注文状態**

受付済み注文の状態はPENDING / FILLED / CANCELED / EXPIREDの4つ。受付前の拒否は発注試行の終端であり、受付済み注文を作らない。ACCEPTEDは受付イベントとし、直後の状態をPENDINGにする。初版は部分約定なし、終端からの復活なし。

エントリー、Exitによる決済要求、エンジンによる緊急決済要求は同じ注文状態機械を通す。約定可能なタイミングと会計処理は注文目的で異なる。初版の戦略はPENDING注文を参照・取消できず、期限・取消は注文層が扱う。

| 遷移 | 原子的に確定する内容 |
|---|---|
| エントリーのPENDING→FILLED | 約定記録、建玉作成、初期SL/TPの有効化（該当するもの）、予約から建玉枠への移行 |
| 決済のPENDING→FILLED | 約定記録、建玉終了、実現損益・費用・balance更新、保護の終了、建玉枠の解放 |
| PENDING→CANCELED/EXPIRED | 終端理由、残る未約定予約の解放。決済注文の終了だけでは建玉を閉じない |

注文目的に応じた原子的な処理として検証・確定し、途中まで更新した状態を公開しない。初版のシミュレーションで内部処理が失敗した場合は、部分的な約定済み状態で継続せず、整合した直前状態と失敗診断を保存する。ライブの外部約定を取り消せるという意味ではない。

SL gapや約定直後の緊急決済でもエントリーを消さない。エントリー約定と直後の決済を順序付きで記録する。初期SLを越えている場合のTP算定省略等は明示した初期化分岐であり、中途半端な処理失敗と区別する。

イベントには一意のevent_idを持たせる。冪等性は注文IDだけでなくイベントIDと消費処理の識別で管理し、処理済み記録と状態更新を同じ確定単位に含める。再配送で約定・balance更新・予約解放を二重実行しない。異なるイベントIDで同じ終端効果を要求された場合も注文状態の検査で防ぐ。これにより1注文に対する正常な異なるイベントまで重複扱いしない。

**B. 有効期限と候補open**

- 注文のexpires_atは受付時を起算して事前設定した有限時間から求めるUTC絶対時刻。具体的な有効時間は次の詳細設計対象。
- 約定可能条件はopen_time < expires_at。時計イベントの期限処理フェーズをopen約定フェーズより前に置き、同時刻ならEXPIREDを先に確定する。
- 期限は足の到着に依存せず休場中も進む。受付後の期限延長は初版では行わない。
- 受付層は実験の市場カレンダー・執行系列の公開/足スケジュールを参照する。データ基盤と別のカレンダーを複製しない。因果順序とentry_delay_barsから候補を決め、将来価格や実ファイルの欠損を候補選択に使わない。
- 受付時点で期限内に候補がなければ受付前拒否。指定の1足遅延のために期限を延長しない。
- 短い有効時間では週末後の候補が期限外となるため受付前拒否になる。初版は未約定注文を週末へ持ち越さない方針とし、有効時間を長くするだけでこれを回避できないようにする。
- 将来の週末持ち越しは有効期限とは別の明示的な設定とする。その具体的な型名は未決定。週末休場の識別はカレンダーで行い、UTCの土日判定に置き換えない。これは未約定注文の規則であり、既存建玉の週末強制決済を意味しない。

WAIT_FOR_INPUTや取引機会の期限とは別の契約である。受付時に上流機会の有効性を検査する。緊急決済も同じ状態機械を通るが、約定直後の同一openで実行する例外は維持する。通常決済注文が失効しても既存SL/TPは継続し、建玉枠を解放しない。期限設定値はエントリーと決済の意味に応じて具体化する。

**C. データ完全性と候補欠損**

市場カレンダーは公開予定と同じデータ/スケジュール層に置き、版を実験設定で固定する。正常な休場には足を期待せず、存在すべき足がない場合を欠損と判定する。

実行前のデータ完全性検査を必須とする。要求した期間・系列・ウォームアップ・必要価格項目をカレンダーと照合し、既知の欠損・無効値・末尾不足はバックテスト開始前に失敗させる。検査結果は戦略へ渡さず、欠損付近だけを取引対象から外すこともしない。公開遅延シナリオは元データの欠損とは区別する。

実行中の読み込み不整合等に備え、執行時の検査も維持する。候補足の価格がない場合は実行失敗とし、後続の正常足へ飛ばさない。始値約定後に必要なhigh/lowを取得できなくなった場合も失敗し、既に確定した約定を消さない。

失敗時は注文・建玉・予約・口座状態と、系列・区間・項目等の欠損詳細を保存する。未約定注文はCANCELED、理由DATA_ERRORとして取消を確定し未約定予約を解放する。後処理前後を記録し、保有建玉は架空価格で閉じない。診断を保存しても正常完走の採用評価には混ぜない。

**D. 予定したrun_endと予期しないデータ末尾**

run_endは実験前に固定する。必要データがそれより前に尽きればDATA_ERRORであり、最後に取得できた時刻へrun_endを短縮したり、決済に都合のよい将来まで延長したりしない。

予定終了時の順序は次のとおり。

1. run_endで終了する足までの内部約定・口座更新を解決する。
2. run_endまでに期限到達したPENDING注文をEXPIREDにする。同時刻にrun_endもある場合は期限切れを優先する。
3. run_endまでに利用可能な確定情報で、通常の評価スケジュールに従って戦略評価を行い判断履歴を残す。終了だから未公開情報を解禁することはしない。
4. この評価からの注文意図は受付前にRUN_ENDで拒否する。新規エントリーだけでなく戦略の決済注文も末尾で約定させない。注文を生成してから取り消す方式にはしない。
5. 残った受付済みPENDING注文をCANCELED、理由RUN_ENDとして終了し、未約定予約を解放する。run_endから始まる足のopen処理は行わない。
6. 残存建玉は未決済のままMTM評価して最終snapshotを保存する。建玉割当も解放しない。

終了時に生成された管理要求も記録するが、将来に対する保護水準更新等を実行したことにはしない。適用しない理由はRUN_ENDで残す。足内で既に起きた保護約定は手順1で処理済みであり、末尾の新しい戦略注文とは区別する。

最終評価価格がない場合は正常な最終集計として扱わない。初版は次の実験へ口座・建玉・予約・部品状態を引き継がず、各実験を独立した初期状態から開始する。最終snapshotは監査用であり、次実験の暗黙の初期状態ではない。将来のWF持ち越しや実行再開は明示的な別設計とする。

**E. 末尾の3種類の集計**

| 集計 | 意味 |
|---|---|
| 確定損益 | 実際に確定した決済損益と、定義した計上済み費用の内訳。未決済分の入場費用等の所属も二重計上なく明示する |
| MTM込み資産 | 終了balanceと未決済建玉の含み損益。買いはbid、売りはaskの決済側価格で評価 |
| 参考損益：最終終値で閉じた場合 | 残存建玉を終了時の価格・費用モデルで仮に閉じた場合の損益を計算だけする。追加決済費用の仮定を併記する |

参考損益では、実際の注文・約定・完了取引数・balance・リスク枠を変更しない。既に計上した入場費用等をもう一度差し引かない。単一評価の採用指標と参考値を分け、都合のよい方を結果から選ばない。費用区分と正確な集計式は評価境界の詳細設計で決める。

**F. 時刻表**

15m執行、22:00:02受付、候補22:15 openとする。

| 条件 | 結果 |
|---|---|
| expires_at=22:20、候補データ正常 | 22:15にFILLED。約定・建玉・初期保護・予約移行を原子的に確定 |
| expires_at=22:15 | 期限内の候補なしとして受付前拒否 |
| 受付済み注文の期限とopenが同時 | 時計フェーズでEXPIRED。openでは実行しない |
| 候補22:15足が既知の欠損 | 実行前の完全性検査でDATA_ERROR |
| 事前検査後に候補データ取得が破綻 | 実行失敗、PENDING注文をCANCELED/DATA_ERROR。22:30へ飛ばさない |
| run_end=22:15、期限22:20 | 末尾openは実行せず、受付済みならCANCELED/RUN_END |
| run_endの評価で新しい注文意図が出る | 受付前拒否/RUN_END。受付済み注文と予約を作らない |

有効時間の具体値、候補がrun_end以降と受付時に分かる場合の早期拒否、失効後の機会状態、エラー後の再開は詳細設計対象。残存する決済要求を含め、注文終了と建玉終了を同一視しない。

#### 4.7.14 共通の理由コード（体系を採用、初期語彙の具体案）

理由コードを判断履歴・状態遷移・テスト・集計で共有する。状態と理由は別のフィールドとし、1つのReasonCode列挙から許可された組合せを検証する。エラーの具体的な系列・時刻・値は型付き詳細情報に保存し、すべてを長いenum名へ埋め込まない。

| ReasonCodeの案 | 主な使用箇所 |
|---|---|
| `RISK` | 受付前拒否。率・総量・数量・証拠金等の違反詳細を別に記録 |
| `NO_CANDIDATE` | 期限内の適格openがない場合の受付前拒否 |
| `RUN_END` | 末尾の受付前拒否、残存注文のCANCELED、管理要求の未適用 |
| `DATA_ERROR` | 完全性検査/実行失敗、失敗に伴う残存注文のCANCELED |
| `EXPIRED` | 期限による注文のEXPIRED |
| `CARRY_NOT_ALLOWED` | 初版の週末持ち越し禁止による受付前拒否 |
| `MARKET_STATE_INVALIDATED` | 継続成立を要求した条件が崩れたことによる取引機会の終端（第4.5節、ADR-0031） |
| `SUPERSEDED` | 新しいTriggerを優先する設定による取引機会の終端（第4.5節、ADR-0032） |
| `CLOSED_BY_ORDER_ACCEPTANCE` | 別の注文が受け付けられたことによる取引機会の終端（第4.5節、ADR-0032）。`on_order_accepted` に規則がある場合のみ |
| `REQUEST_SUPERSEDED` | 同じ系列の新しい足による評価要求の追い越し（第4.3.14節、ADR-0032 で改名）。取引機会の `SUPERSEDED` と混同しない |

同じ理由コードでもイベント種別・状態で意味を絞る。EXPIREDという理由でCANCELEDにする等の不整合は拒否する。DATA_ERRORには期待/実際の観測区間・項目・原因を添える。発注試行や注文を作る前の完全性検査失敗には、存在しない注文IDを要求しない。

SL到達・TP到達・約定ずれ超過・閉鎖済み建玉等の執行理由も同じ体系へ追加していくが、初期語彙の全件・複数理由が成立した場合の代表理由と診断一覧の扱いは次に具体化する。期限とrun_endの競合はEXPIREDが代表理由。run_endで新たに受付を試みた場合はNO_CANDIDATEへ丸めずRUN_ENDを記録する。

#### 4.7.15 注文要求・受付済み注文・約定・予約の型（フィールドの正面案）

既に確定した動作を次の4型へ落とす。型名・フィールド配置・補助型は今回の正面案であり、既存の合意と区別して確認する。Pythonでは不変のdataclassと判別可能なUnionを基本とする。共有フィールドを固定し、目的別の内容は型付きpayloadに置く。任意のdictや多数の無関係なOptionalで表現しない。

| 型 | 作成主体・時点 | 意味 |
|---|---|---|
| `OrderRequest` | エンジンの要求組立層。部品の出力が揃った時点 | 1回の審査対象。受付前拒否もこの記録に紐付く |
| `AcceptedOrder` | 注文受付層。審査・数量決定・必要な予約と同時 | 受付条件を固定した注文。不変 |
| `FillRecord` | 約定モデル。約定の原子的な確定時 | 実際にシミュレーションした約定の事実。不変 |
| `RiskReservation` | リスク層。エントリー受付と同時 | 未約定のエントリーが占有する口座通貨の枠 |

部品出力のOrderIntentは数量のない意図のまま維持する。OrderRequestはそれをProtection等と組み合わせたエンジン側の審査入力であり、同義語にしない。部品出力の生成時刻等は既存のOutputRecordを正本とし、要求から出力IDで辿る。

**共通の値型と参照**

- IDはPython上でも用途を区別する不透明な型とし、少なくともrun内で一意。永続参照はrun_idとの組で一意とする。各レコードにrun_idを持つ。時刻はtz-aware UTC。
- 金額は`Money(amount: Decimal, currency: CurrencyCode)`、価格と数量はそれぞれ`Price` / `Quantity`（Decimalを基礎）を使う。Quantityは基軸通貨の単位数で統一し、ロットの換算と刻みは銘柄仕様の版へ固定する。
- `ProcessingPoint(time, phase, sequence)`はエンジン処理順を表す。同じ時刻の評価・受付・始値処理を区別する。市場内で実際に起きた時刻とは別物。
- `EvidenceRef`は保存された根拠記録への参照。その記録には入力の出力IDまたは市場データのsnapshot・系列・区間・項目、読取時点、口座snapshot、使用した設定版を含む。型付き根拠を辿れる参照であり、説明文だけのログではない。
- `PolicyRef`はID・版・設定の識別子を含む不変参照。runの固定manifestから解決し、再実行時に最新版へ差し替えない。

**A. OrderRequest：審査前の要求**

| フィールド | 型 | 動作・制約 |
|---|---|---|
| run_id | RunId | 実行の識別 |
| attempt_id | AttemptId | 1回の試行の識別。要求IDも兼ねる |
| previous_attempt_id | AttemptId または None | 明示的な再審査の場合のみ、元の試行を指す |
| account_id | AccountId | 審査する口座 |
| strategy_id | StrategyId | 建玉・機会の帰属先。エンジン決済でも帰属は維持 |
| created_at | ProcessingPoint | 要求を組み立てた実処理時点。遅延時も過去に戻さない |
| origin | RequestOrigin | STRATEGY / ENGINE。戦略がENGINEを自己申告することは不可 |
| payload | EntryRequest または CloseRequest | 要求目的に応じた内容 |
| evidence_ref | EvidenceRef | 意図・保護・機会・管理要求等の根拠 |

EntryRequestのフィールド:

| フィールド | 型 | 意味 |
|---|---|---|
| opportunity_id | OpportunityId | 発端となる取引機会 |
| symbol | Symbol | 対象FXペア |
| side | OrderSide（BUY / SELL） | 注文の売買方向 |
| order_type | OrderType | 初版はMARKETのみ |
| protection | InitialProtectionPlan | Protectionの絶対価格SL案。受付層が丸め・検査し凍結 |
| exit_plan_ref | ExitPlanRef | 固定RR・SL管理者等を含む解決済み設定。実TP価格は約定後 |
| valid_for | timedelta | 受付からの有限有効時間。正値必須 |

CloseRequestは`position_id: PositionId`、`cause: CloseCause`、`valid_for: timedelta`を持つ。初版は全数量決済なので、銘柄・売買方向・数量を要求に重複指定せず対象建玉から決める。CloseCauseは初期案としてSTRATEGY_EXIT / EMERGENCY / STOP_LOSS / TAKE_PROFIT。緊急決済は原因となるfill_id、保護決済は有効な保護水準の版、戦略決済は管理要求の出力IDを根拠に残す。causeは執行契機であり、受付拒否のReasonCodeとは役割が違う。

新規リスクの2%審査はEntryRequestに適用する。決済を新規リスク予算の不足で拒否しない。決済には対象建玉の存否、数量、競合、期限、執行条件を検査する。試行結果は別のAttemptDecisionにACCEPTED(order_id)またはREJECTED(reason, details)を記録する。拒否では注文・予約を作らず、同じattempt_idで再試行しない。

**B. AcceptedOrder：受付条件を固定した注文**

| フィールド | 型 | 動作・制約 |
|---|---|---|
| run_id | RunId | 実行の識別 |
| order_id | OrderId | 受付済み注文の識別 |
| attempt_id | AttemptId | 元の要求。口座・戦略・機会等も辿れる |
| accepted_at | ProcessingPoint | 受付と予約を確定した点 |
| symbol | Symbol | 受付時に解決した銘柄 |
| side | OrderSide | 実際の売買方向。買い建玉の決済ならSELL |
| quantity | Quantity | 受付時に確定した全数量 |
| expires_at | datetime | accepted_at.time + valid_for |
| execution | ExecutionCommitment | 約定方式と候補を固定する内容 |
| terms | AcceptedEntryTerms または AcceptedCloseTerms | 目的固有の受付結果 |
| evidence_ref | EvidenceRef | 受付時の観測・検査・丸めの根拠 |

ExecutionCommitmentは`policy_ref`、`execution_series_ref`、`eligibility`を持つ。通常の初版成行のeligibilityは`ScheduledOpen(bar_id, open_time)`。因果順序・遅延設定・市場カレンダーから選んだ候補を固定し、欠損時に後続へ置換しない。

約定直後の緊急決済は`ImmediateAfterFill(trigger_fill_id, open_event_id)`を使う。通常の次足候補探索を通さず、エンジン生成の同一open内の例外であることを型で検査する。SL/TP到達による決済も追跡のためエンジンがCloseRequest→AcceptedOrder→FillRecordを生成し、`ProtectionHit(position_id, protection_version, execution_bar_id)`で既に有効だった保護に基づく到達と結び付ける。これは終値で新しく生成された戦略決済の遡及約定ではない。これらは同じ注文状態機械を使い、通常の成行だけに適用する候補open規則とは分ける。

AcceptedEntryTermsは`initial_stop: Price`、`exit_plan_ref: ExitPlanRef`、`reservation_id: ReservationId`、`reference_quote: ReferenceQuote`、`adverse_fill_limit: Price`を持つ。ReferenceQuoteは使用した価格・bid/ask区分・観測時点・根拠参照を持つ。adverse_fill_limitはリスク予算計算と約定後検査の境界であり、約定保証の指値ではない。

AcceptedCloseTermsは`position_id: PositionId`と`cause: CloseCause`を持ち、新規予約は作らない。既存建玉の割当は決済約定まで保持する。保護決済が先に建玉を閉じた場合、残る決済注文を二重約定させず取消する。その理由は共通ReasonCodeへのPOSITION_CLOSED追加を提案する。

注文の可変状態はAcceptedOrderを直接書き換えず、別の`OrderState(order_id, status, last_event_id, last_processed_at, terminal_reason)`としてイベントから投影する。正常約定でterminal_reasonは不要であり、何で決済したかはCloseCauseで記録する。イベントはevent_idを持ち、イベント処理済み記録・注文状態・会計への副作用を一緒に確定する。

**C. FillRecord：約定の事実**

| フィールド | 型 | 動作・制約 |
|---|---|---|
| run_id | RunId | 実行の識別 |
| fill_id | FillId | 約定そのものの識別 |
| event_id | EventId | この約定を通知するイベントの識別。再配送でも同じ値 |
| order_id | OrderId | 約定した注文 |
| position_id | PositionId | 新規なら作成する建玉、決済なら閉じる建玉 |
| processed_at | ProcessingPoint | エンジンが約定を確定・公開した処理点 |
| execution_time | ExactExecutionTime または BarExecutionInterval | 実際にモデルが特定できる時刻の精度 |
| price | Price | spread・slippageを反映した実約定価格 |
| quantity | Quantity | 初版では受付数量と同じ全数量 |
| costs | tuple[CostEntry, ...] | 別途計上する手数料等。価格反映済み費用は重複控除しない |
| evidence_ref | EvidenceRef | 執行足・約定モデル版・元bid/ask・slippage・競合判定等 |

始値約定はExactExecutionTimeでopen時刻を記録する。OHLC内部のSL/TP到達は正確な時刻を観測できないためBarExecutionIntervalに対象区間を記録し、終値時刻を実際の到達時刻として捏造しない。内部到達を解決するprocessed_atは終値評価より前のフェーズとなる。足内の順序仮定は根拠に記録する。

symbol / side / policyは不変のAcceptedOrderから辿り、FillRecordの正本に重複させない。集計用の表には結合して出力してよい。実約定SL・TPの有効化と約定後リスク再計測は別の建玉初期化・リスク計測記録とし、fill_idへ紐付けて同じ原子的処理で確定する。費用の換算はCostEntryに原通貨額、口座通貨計上額、換算根拠を保持する。

**D. RiskReservation：未約定リスクの予約**

| フィールド | 型 | 動作・制約 |
|---|---|---|
| run_id | RunId | 実行の識別 |
| reservation_id | ReservationId | 予約の識別 |
| order_id | OrderId | 対象のエントリー注文。初版1対1 |
| account_id | AccountId | 枠を消費する口座 |
| created_at | ProcessingPoint | 注文受付と同じ確定点 |
| amount | Money | 受付時に固定した消費枠。口座通貨 |
| assessment_ref | RiskAssessmentRef | 数量・予約額を決めた計算の不変記録 |

RiskAssessmentにはpolicy_ref、受付時balance、使用率・率上限・総量上限、既存消費枠、利用可能予算、参照価格、許容不利価格、丸め前後SL、数量刻みと丸め後数量、換算率と観測時点、費用予算の内訳、最終予約額、証拠金等の検査結果を記録する。2%・20%や価格差はここで実際に使用した値を保持し、将来の設定から逆算しない。

予約の状態も別の投影`ReservationState`で保持する。状態案はHELD / TRANSFERRED / RELEASED。取消・失効はHELD→RELEASED、約定はHELD→TRANSFERREDとして、同額の`PositionRiskAllocation`を作る。TRANSFERREDは予約として終端であり、二重解放・再移管を禁止する。建玉決済時は予約を再解放せず建玉割当を解放する。

PositionRiskAllocationはallocation_id、position_id、source_reservation_id、amount、作成/解放のイベント参照を持つ。集計UはHELD予約額＋未解放の建玉割当額とし、TRANSFERRED予約を加算しない。約定時・トレーリング後の計測リスクは`RiskMeasurement`として別記録にし、固定割当を上書きしない。失敗/run_endで保有建玉が残れば建玉割当も残る。

**E. 具体例と検証する境界**

口座通貨JPY、balance=1,000,000円、既存枠0、買い参照価格150.00、許容不利価格150.05、丸め済みSL149.55とする。説明用に費用予算0円、数量刻み1,000通貨を仮定する。これは本番の費用設定ではない。

1. OrderRequestは買いの機会とSL案・Exit設定を持つ。数量は持たない。
2. 予算20,000円、1通貨あたり予約リスク0.50円なので数量40,000通貨。AcceptedOrderと20,000円のRiskReservationを一緒に作る。
3. 実約定150.02ならFillRecordに150.02と40,000通貨を記録。初期SLに基づく計測リスクは18,800円となる。
4. 建玉割当は20,000円のまま移管し、差分1,200円を新規枠へ戻さない。計測リスクとの差は根拠付きで残す。
5. 決済要求ではposition_idを指定し、受付層がSELL・40,000通貨に解決する。新規予約なし。決済約定時に建玉割当を解放する。

実装時の意味論検証は、受付拒否で注文/予約が残らないこと、受付/約定の原子性、同じevent_idの再配送、終端後の別イベント、予約移管の二重計上、期限とopenの同時刻、保護決済と通常決済の競合、末尾MTMの非執行を対象にする。補助型の全フィールド、有効時間の具体値、SL/TPの細部、理由コードの追加語彙はこの構造を確認した後に詰める。

## 5. 先に設計する3つの契約

### 5.1 戦略契約

入力は戦略定義・確定したパラメータ・その時点で参照可能な市場/約定/建玉情報。出力は取引機会・注文意図・更新/決済要求と理由である。

- StrategyDefinition は宣言であり、実行中の状態と分ける。
- compiler/validator は型、参照、入力能力、依存関係、パラメータ範囲を検査する。
- 戦略は資産台帳や約定履歴を直接書き換えない。
- 部品の計算を全期間で一括実行する場合も、将来データ追加で過去出力が変わらない性質を検証する。
- データを使って学習する部品を将来導入する場合、fit と推論を分離し、fit の期間・成果物を固定する。
- 戦略は train/test 区分や評価点数を入力として取引判断を変えない。

### 5.2 バックテスト契約

入力はコンパイル済み戦略・データスナップショット・初期口座・リスク方針・執行/コストモデル・実行期間。出力は正規化された注文、約定、建玉、現金、MTM資産推移、判断 trace、終了状態。

設計時に決める事項:

- 同時刻の市場更新・足確定・判断・注文受付・約定の順序。時刻が同じでも情報の因果順序を保持する。
- 注文意図、リスク審査、数量確定、注文受付、約定を分ける。未確定の次足価格を事前の数量計算に使わない。
- 初版は第4.7.11節の次の適格な執行足始値で約定する。終値約定を混在させない。同時刻のclose→判断/受付→openは明示されたゼロ遅延モデルとして扱う。
- OHLCでSL/TPが両方触れた場合の扱い、gap時の価格、注文取消と約定の競合。
- bid/ask と spread、slippage、手数料のモデル。価格差と費用を二重計上しない。
- FX数量の単位、base/quote/account currency、価格刻み、数量刻み、丸め、証拠金・レバレッジ。
- quote通貨から口座通貨への損益・リスク換算。換算レートもその時点で利用可能な系列を使い、不足時は拒否する。
- swap/rollover をモデル化するか、初期は未計上とするかを明示する。未計上なら結果に残す。
- RiskPolicy は資産・既存建玉・必要なら未約定注文のリスクから注文可否/数量を決める。初版でも単位整合を検証する。
- 注文・約定・建玉は別IDで関連付ける。初版の1建玉制限を中核の唯一の状態表現にしない。
- Protection/Exit の複数要求の優先順位と有効時刻。戦略が直接約定や能動closeを実行する形にしない。
- データ末尾の未約定注文・保有建玉、評価期間境界、強制決済または未決済MTMの扱い。

最初は成行・同時1建玉でよい。指値・部分約定・分割決済などは将来の能力として設計境界を用意し、未実装の要求は明示的に拒否する。決済要求はシミュレーターに渡す意図であり、戦略が任意の価格で決済済みと記録する機能ではない。

### 5.3 評価契約

入力は仮説・戦略定義・探索計画・期間分割・評価規則・データ/モデル参照。評価基盤が単一実行または複数実行を組み立て、バックテスト結果から指標・診断・比較・選定結果を生成する。

- 単一実行の指標算出と、候補選択/最終判定を分ける。
- バックテストはWF窓生成や採否判定を担わない。評価側はバックテスト結果を都合よく修正しない。
- リターン、MTMドローダウン、リスク調整指標、年率化、取引数、exposure、コスト集計の定義を固定する。
- 0取引や計算不能な指標は、成功値や0への黙った置換をしない。
- 失敗・拒否・中断・完了の状態を区別し、失敗した候補も探索履歴に残す。
- 再実行に必要なデータ・コード・部品・実行モデル・パラメータ・乱数seed・環境情報を保存する。
- trainのみでの選定、ウォームアップと採点区間の分離、fold境界の建玉/状態、必要なpurge等を設計する。
- 最終holdoutへのアクセスを探索経路から分離する。過去の閲覧/使用履歴も評価上の制約に含める。
- 評価窓の長さ・選定指標・合否閾値・最終判定の集約方法は未決定。旧基盤の値を暗黙に継承せず、新しい評価規則を結果を見る前に決める。

## 6. 研究ポリシー：初期は共通1種類

「制約1つ」は、数値上限を1項目だけ置く意味ではなく、共通の研究ポリシーを1種類だけ運用する意味である。

| 対象 | 管理するもの |
|---|---|
| StrategyDefinition | 実際の戦略構成とパラメータ |
| ResearchPolicy | 研究で守る事前固定・記録・複雑性等の規則 |
| SearchPlan | 今回試す値・組合せ・探索アルゴリズム・終了条件 |
| RiskPolicy | 比較条件として固定する損失予算・数量・集中等 |
| Execution/Cost Model | 注文処理・約定・費用の意味 |
| Capability | 実装とデータで実際に実行できる範囲 |

初期には数値制限を増やさず、すべての実験が共通の ポリシーIDとバージョン を参照する。将来複数へ拡張できる形にするが、初版にポリシー選択UI・複数プリセット・複雑な継承機構を作らない。

計算量上限を厳しくしないことと、探索範囲が未定義であることは異なる。各実験の探索空間・終了条件は事前に記録する。任意の中断時も、試行済み・未試行・失敗を区別する。後から複雑性を制約する場合に備え、合成部品内部も含む条件数などの計測方法を定義する。

## 7. 構築順序と完了条件

| 段階 | 作るもの | 完了条件 |
|---|---|---|
| 0. 契約設計 | 3契約、共通の時刻/ID/単位、部品入出力、イベント順序、実験manifestの仕様 | 単純戦略とMTF戦略を紙上で追跡でき、同時刻・数量・末尾処理に暗黙の前提がない |
| 1. データ・時刻 | 既存CSV adapter、snapshot、足境界、as-of参照、ウォームアップ/欠損規則 | 未確定の上位足を参照できず、DST・欠損・再読込の検証が通る |
| 2. 最小の縦断実装 | Feature → Trigger → Order → Protection/Exit、成行・1建玉、risk、cost、MTM、基本指標と実行記録 | 人工データで注文・数量・損益・資産が手計算に一致。同一入力の再実行が一致 |
| 3. MTFと後続確認 | MarketState、複数足入力、取引機会、ExecutionFilter、期限/取消/再発火、基本合成 | 下記MTF例を同じ基盤で記述でき、時刻境界と取消理由をtraceできる |
| 4. 単一実行評価の整備 | manifest固定、指標定義、診断、共通研究ポリシー検査、結果保存 | 結果から設定と入力を特定でき、別プロセスで再現可能。失敗/0取引も説明できる |
| 5. 複数実行の評価 | 探索、train/validation、WF等の時系列検証、頑健性、隔離holdout | 選定がtrain内で閉じ、全試行を記録し、holdoutを通常探索で読めない |
| 6. 実需に応じた拡張 | 指値/逆指値、複数建玉・銘柄、分割決済、詳細コスト、並列化 | 追加能力ごとの意味論テストが通り、既存設定の意味を変えない |

段階2で既に「戦略定義 → バックテスト → 単一実行の基本評価」を通す。段階4まで評価・記録を全く作らない進め方にはしない。段階3〜4を終えた状態を最初の基盤リリースの推奨範囲とする。

### 7.1 最小構成を検証する2本の戦略

**A: 単純戦略（構造の検証用）**

- 1h終値で直近の確定高値突破を検出する。
- 後続確認なしで成行注文の意図を作る。
- 確定情報から初期SLと固定RRのTPを決める。
- 約定方式、数量確定時点、TP算定時点、費用は事前に指定する。
- ExecutionFilter は使わない。

**B: MTF・確認待ち戦略（構造の検証用）**

- 日足終値と日足EMAからMarketStateを作る。
- 1h終値と、利用可能な日足高値からTriggerを作る。
- 発火時の基準水準を取引機会に保存する。
- Triggerと同じ時刻に利用可能な15m確定足で確認してよい。未確認なら後続の15m確定時に再判定し、期限内に成立すれば発注、期限到達または失効条件で取り消す。
- 1hで管理水準を更新し、注文の約定判定には指定された市場データと執行モデルを使う。

2本ともアーキテクチャ検証用であり、収益性があると主張するものではない。まず人工データ、次にアクセス許可された既存研究データで検証する。保有データにない5m足は例の前提にしない。

### 7.2 優先する検証

- 将来のデータを追加しても、過去時点の部品出力・意思決定が変わらない。
- 上位足確定直前/直後、同時刻のclose/open、DST・週末で情報の可視性が正しい。
- Triggerの記憶、発火水準の固定、後続確認、期限切れ、再発火が宣言どおり。
- warmup中の注文がゼロ。欠損/鮮度切れから意図しない発注が起きない。
- gap、SL/TP競合、コスト、数量丸め、通貨換算を手計算で検証できる。
- 約定・現金・実現/未実現損益・MTM資産の台帳が整合する。
- 評価窓外の採点やtestを使った選定がない。異常終了を成功結果として扱わない。

## 8. 構造案と、初期に作らないもの

依存方向の案:

```text
evaluation（実験・探索・集計）
  → strategy compiler / backtest runner
      → strategy contracts / execution / portfolio
          → 共通の時刻・銘柄・数量・IDの型

data adapter → snapshot / 時点参照 interface
component catalog → strategy contracts
```

戦略部品は市場データ全体へ無制限にアクセスせず、契約で許可されたviewを使う。評価方式を変えても戦略部品や約定エンジンを書き換えない。実行エンジンを高速化するときも、まず確定したイベント意味論との同値性を検証する。

初期に不要: 複数研究ポリシーの管理UI、全資産対応、任意コードの独自言語、全注文種類、分散実行、戦略部品の大量実装、ライブ取引接続。バッチ計算かイベント駆動かなどの内部実装方式は未決定であり、因果関係の契約を先に固める。

## 10. 用語と引き継ぎ条件

| 用語 | 本書での意味 |
|---|---|
| OHLC | ある区間の始値・高値・安値・終値。この4値だけでは区間内の到達順序は分からない |
| bid / ask | 売却時・購入時に使う側の提示価格。両者の差がspread（スプレッド） |
| SL / TP / RR | 損切り価格、利確価格、想定損失幅に対する利益幅の比率 |
| MTM | 保有中の含み損益も反映した時価評価。決済済み取引だけで資産やドローダウンを計算しない |
| as-of参照 | 判断時点までに利用可能になった値のうち、条件を満たす最新値を読むこと |
| ウォームアップ | 指標や内部状態を準備する区間。採点区間と区別し、この間は発注しない |
| snapshot / digest | 固定した入力一式と、その内容を識別・検証するハッシュ値 |
| manifest | 入力・設定・使用バージョン等を列挙した、実行を再現するための記録 |
| provenance / trace | データの出所・加工履歴と、判断・注文・状態遷移を追跡する記録 |
| train / validation / holdout | 選定に使う期間、検証する期間、探索から隔離した最終評価期間。名称だけでなくアクセスと利用規則を定義する |
| WF（walk-forward） | 時系列順に学習・選定期間と後続の評価期間を移動させ、複数区間で検証する方法 |
| fold / purge | 時系列評価の各分割と、境界を跨ぐ情報・損益等の混入を避けるため必要な観測を除外する処理 |
| capability | データと実装が実行できる機能の範囲。戦略の表現力や研究ポリシーとは別に検査する |

新セッションに必要なのは本書と、実装段階で引き渡す市場データ・その出所および使用履歴である。旧コードや旧設計資料を読めることは前提にしない。新しいデータ読込処理・戦略部品・実行モデル・評価機能は、本書で定義した責務から設計する。

データ実体が未引き渡しでも、契約設計と人工データによる縦断実装は進められる。実データとの一致や利用可能期間は、引き渡し後の検査をもって確定する。本書の作成では実データの再処理・バックテスト・封印期間の読み出しは行っていない。
