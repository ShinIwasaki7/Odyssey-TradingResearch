# 外出運転の運用手順（無人運転プロトコル）

- 版: v1.1（2026-09-20 起草、承認待ち。独立レビューの指摘を反映）
- 位置づけ: 人間が iPhone からしか応答できない時間帯に、司令塔セッションと作業役（子セッション）で開発を進めるための運用手順。設計そのものは扱わない。
- 前提: モデルの振り分けは `.claude/skills/model-routing/SKILL.md`（以下「振り分け規則」）、PR のレビュー手順は `.claude/skills/pr-review/SKILL.md` と `docs/pr_review_policy.md` が正本。本書はそれらを**人間と司令塔の間の約束**として補う。
- 凡例: 【合意済み】= 既存の規則の再掲 / 【提案】= 本書で新たに置く運用 / 【要決定】= 人間の選択が要る

## 1. 役割と守るべき境界【合意済み】

| 役割 | 誰 | する | しない |
|---|---|---|---|
| 人間 | iPhone 上の利用者 | 設計の承認、選択式の質問への回答、merge の判断 | 手順の細部の指示（司令塔に任せる） |
| 司令塔 | Fable セッション（Remote Control 接続） | 現在地の管理、作業役の起動、質問の整形、進捗ファイルの更新指示 | コード・ログを読む、実装する、merge する |
| 作業役 | Opus / Sonnet / Haiku の子セッション | 設計文書1本または PR 1本の作業、Codex 往復、定型報告 | 未承認の設計判断、merge |

- 司令塔が人間に確認を取るのは **(a) 設計の承認、(b) merge の可否、(c) 作業役から上がった「要決定」** の3種類だけ。それ以外は止まらずに進める。
- 並列の作業役は最大2。人間待ちの項目は進捗ファイル（§4）の「人間待ち」に積み、回答が来るまで別の作業へ進む。

## 2. iPhone に送る質問の様式【提案】

質問は原則 `AskUserQuestion`（選択式 UI）で送る。文章で送らざるを得ないときも同じ構造を保つ。

```
【何を決めるか】<1行。結果にどう影響するかを先に書く>
【背景】<最大2行。内部識別子は「意味の分かる日本語名（ID）」の順で書く>
1. <推奨> ラベル — 影響1行
2. ラベル — 影響1行
3. ラベル — 影響1行
返信は番号だけで可。「他」と書けば自由記述を受け付ける。
```

守ること:

- 選択肢は **3つ以内**、**推奨を先頭**に置き、ラベルに「（推奨）」を付ける。
- 選択肢の説明には **ラベルに書いていない解釈を足さない**（例: 「下位足で判定」の説明に「初版は損切り優先」と書かない）。影響は「この案を選ぶと何が変わるか」の事実だけを書く。
- 1回の質問で扱う決定は1つ。複数の決定が溜まったら、質問を分けて連続で送る（1つの選択肢リストに複数の決定を束ねない）。
  振り分け規則 §3 の7「人間への質問はまとめて1回」は、**司令塔が作業役から上がった要決定を集約し、一度のやり取りでまとめて送る**という意味であり、1つの質問に複数の決定を詰めることを求めるものではない。両者はこの読み方で両立する。
- 質問を送ったら、その内容を進捗ファイルの「未回答の質問」に転記してから待つ。回答が来たら、決定を該当する設計文書または決定記録（ADR）に書き、質問の行を「完了」へ移す。
- merge の可否を問うときは、PR 番号・独立レビューの巡数・**残った重大な指摘（P0/P1）の有無と要約**・残った軽微な指摘（P2）の件数・仮置き事項を1行ずつ添える。重大な指摘が残っているのに「レビュー済み」とだけ書かない。

## 3. 作業役の報告様式【合意済み】

振り分け規則 §4 の様式（300語以内）をそのまま使う。司令塔はこの様式以外の報告（ログ全文・diff 全文）を受け取らない。

```
## 結果: 完了 / 要決定 / 失敗
- 成果物: PR #<n>（ブランチ名）/ 変更ファイル数
- 検証: ruff / mypy / lint-imports / pytest の合否（数字だけ）
- Codex: 巡数、各巡の件数、**残った重大な指摘（P0/P1）の件数と1行要約**、残った軽微な指摘（P2）の件数、**head**（下の分け方による）、仮置き事項（あれば1行ずつ）
- 要決定（あれば）: 何を決めるか1行 / 選択肢（推奨を先頭、最大3つ）/ 各選択肢の影響1行
- 次に着手可能な作業: 1行
```

- Codex 往復は**巡数ではなく指摘の残数で終える**（PR レビュー方針 §4.1）。**安全弁の6巡を使い切っても重大な指摘（P0/P1）が残っている場合は、報告の見出しを「要決定」にし、残った指摘を1行ずつ書き、指摘の傾向と収束しない理由の仮説を添える**。同 §4.4 の「6巡で収束しないときは人間の判断を仰ぐ」に当たる。この場合、**司令塔は merge の可否を問わない**（同 §7。レビューがまだ尽きていないため）。司令塔はこれを握りつぶさず、**「続行」「レビュー対象範囲の明記し直し」「別工程（紙上トレースなど）への切り替え」のどれを取るかだけ**を §2 の様式で人間に送る。人間が選んだ方法で収束させ、終了条件に達してから改めて merge を問う。
- **head の書き方は見出しによって分ける**。「完了」の報告だけが**終了条件を満たした head** を書く。**「要決定」で止まった報告（6巡の安全弁・利用上限8回）は、定義上まだ終了条件を満たした head が存在しない**ので、代わりに**最後にレビューされた head と、その時点で残っている P0/P1 の件数**を書く（応答のある巡が一度も無ければ「未確認」）。存在しない head を書かない。司令塔は、終了条件を満たした head が書かれていない報告を「完了」として扱わない。
- 「失敗」は原因の仮説1行と試したこと最大3行。全文ログは `docs/status/logs/` にファイルとして置き、報告にはパスだけ書く。
- 作業役は **PR を作った時点** と **Codex 1巡が終わった時点** で進捗ファイルを更新する（§4.2）。使用量枠が尽きたときに未報告分が失われないようにするため。

## 4. 進捗ファイル `docs/status/progress.md` の形式【提案】

### 4.1 形式

進捗ファイルは1つだけ。リセット後の再開時に司令塔が最初に読む唯一のファイルであり、ここに無いことは忘れられたものとして扱う。

```
# 進捗（正本）
更新: <UTC ISO8601> / 更新者: <司令塔 | 作業役(モデル名)>

## 現在地
- 段階: <段階番号と名前>
- 直前に終わったこと: <1行>
- いま止まっている理由: <人間待ち | 作業役実行中 | なし>

## 人間待ち（回答が来るまで進めない項目）
- [ ] <種別: merge | 設計承認 | 要決定> <対象: PR #n | 文書名> — <質問を送った時刻>

## 進行中（最大2行）
| 作業 | 担当 | ブランチ / PR | 状態 | 次の一手 |
|---|---|---|---|---|

## 未回答の質問
- Q-<連番>: <何を決めるか1行> / 選択肢: 1.<推奨> 2. 3. / 送信: <時刻>

## 次に着手する作業（上から順）
1. <作業1行。読む文書の場所>

## 完了（新しい順・5件まで。それ以前は git log と PR 一覧が正本）
- <日付> PR #n <1行>
```

### 4.2 更新の約束

| いつ | 誰が | 何を |
|---|---|---|
| 作業役が PR を作った | 作業役（Haiku に任せてよい） | 「進行中」に行を追加 |
| Codex 1巡が終わった | 作業役 | 「進行中」の状態と次の一手 |
| 人間に質問を送った / 回答が来た | 司令塔 | 「人間待ち」「未回答の質問」 |
| PR が merge された | 司令塔（Haiku に任せてよい） | 「進行中」から「完了」へ移し、「次に着手する作業」を1つ繰り上げ |
| 使用量枠が尽きる前の最後の更新 | 司令塔 | 「現在地」の3行 |

- 進捗ファイルの更新は **main へ直接コミット**する（`docs(status): ...`、PR と Codex レビューは省略）。作業ブランチに含めると並行 PR 同士で衝突するため。【決定済み 2026-09-20・§7 U-1】
- **同時更新の手順（作業役は最大2並列なので、2人が同時に書く前提で決めておく）**:
  1. 更新の直前に最新の main を取り込み直す（取り込みは rebase で行う）。古い写しの上に書かない。
  2. **自分が担当する行だけ**を書き換える。他の作業の行・人間待ちの行には触らない。
  3. 送信が「早送りできない」と拒否されたら、もう一度最新を取り込み、自分の行だけ当て直して送り直す。これを**最大3回**繰り返す。
  4. 3回失敗したら更新を諦め、**報告の「仮置き事項」に「進捗ファイル更新失敗（書こうとした内容）」を1行で書く**。司令塔が代わりに書き込む。
  更新を黙って落とすと、再開時の唯一の記録から作業が消える。失敗は必ず報告に出す。
- 「完了」に残すのは5件まで。それ以前の履歴は消してよい（git に残る）。

## 5. 1サイクルの流れ【合意済み】

1. 司令塔が進捗ファイルの「次に着手する作業」の先頭を取り、振り分け規則 §5 の型で作業役を起動する（コミットを生む作業は worktree 隔離）。
2. 作業役が PR を作り、**PR レビュー方針 §7 の2経路のどちらに当たるかを PR 本文に書いてから**レビューを回し、§3 の様式で報告する。
   - **Codex を実施する PR**（実装・骨格ツールは必須、設計文書も既定でこちら）: Codex 往復（**対象範囲の中の重大な指摘 P0/P1 がどちらも0件になる巡まで。安全弁6巡**）を承認停止なしで回し、続けて設計適合レビューを行う。**両方のレーンが同じ最終 head で新たな修正を生まなくなったら「完了」**。
   - **Codex を実施しない PR**（設計文書のみで、省略とその理由を PR 本文に明記したもの）: Codex 往復は行わず、**設計適合レビューが最終 head で新たな修正を生まなくなったら「完了」**。報告の巡数欄には「Codex 未実施（§2 で任意、本文に理由を記載）」と書く。
3. 司令塔が報告を読み、見出しで3つに分ける。
   - **「完了」**（2 のどちらかの経路で最終 head の条件を満たした）: **merge の可否だけ**を §2 の様式で人間に問う。報告の head と `gh pr view` の head が食い違う場合は、まだ検証されていない push があるので、merge を問わず作業役に一巡やり直させる。要決定があれば別の質問として続けて送る。
   - **安全弁（6巡）で止まった「要決定」**: **merge は問わず**、収束の方法（続行 / レビュー対象範囲の明記し直し / 別工程への切り替え）だけを問い、人間の選択を作業役へ戻して 2 へ帰る。「続行」「範囲の明記し直し」なら**巡数は 0 に戻り、同じ6巡の安全弁が再び適用される**（PR レビュー方針 §4.4）。
   - **利用上限（30分待ちの再投稿を8回使い切った）で止まった「要決定」**: **merge は問わず**、レビューを完了させる方法（利用枠の回復後に再開 / 対象範囲を絞って PR を分割 / Codex の設定変更）のどれを取るかを §2 の様式で問う。人間の選択を作業役へ戻して 2 へ帰る。**「レビューを飛ばして merge」は選択肢に入れない**（同 §4.4・§7）。回復待ちを選ばれた場合は、進捗ファイルの「人間待ち」に残したまま §6 の再開手順に乗せる。
4. 人間が merge する。司令塔は merge を確認して進捗ファイルを更新し、1 へ戻る。
5. 段階2の設計文書（D04〜D07）は **1本ずつ**、Opus が「最小範囲の案＋選択肢＋推奨」を起草し、司令塔が §2 の様式で承認を取る。**承認前に次の文書へ進まない**。

## 6. 使用量枠が尽きたとき・再開の手順【合意済み】

- 司令塔は停止し、リセット時刻が表示される。自動再開はしない（使用量クレジットは使わない）。
- 人間はリセット後に iPhone から「続けて」と送る。司令塔は `git pull` → 進捗ファイル → `gh pr list` の順に読み、「現在地」から再開する。
- 作業役が途中で止まった PR は、振り分け規則 §3-4 の引き継ぎ手順（既存 worktree と既存ブランチ名を明記して再起動）で続ける。

## 7. 要決定

| 番号 | 何を決めるか | 選択肢（推奨を先頭） | 影響 |
|---|---|---|---|
| U-1 | 進捗ファイルをどの経路で更新するか | 1.（推奨）main へ直接コミット（PR なし） / 2. 各作業 PR に含める / 3. 専用ブランチ `status/progress` を定期的に PR で取り込む | 1 は最も速く衝突しないが main の履歴に小さなコミットが増える。2 は並行 PR で衝突する。3 は人間の merge 作業が増える |

U-1 は 2026-09-20 に人間が選択肢1（main へ直接コミット、PR なし）を採用した。
