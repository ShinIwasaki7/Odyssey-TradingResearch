- **仮定**: 合成データ・取引 0 件・別の戦略での計測であり、実データの H7（取引あり・日足の局面の部品あり）で同じ割合になるかは確かめていない。探索の実験では準備の一部が単位の間で共有される（`ReadSurfaces`）ので、準備の割合は上より小さいはずである。単位ごとの評価（指標の計算）の時間はこの計測に入っていない。実データでの確認は手順 0（第5節）で行う。
- 計測の道具（cProfile）は関数の呼び出しの多い処理を重く見せる。割合は目安で、短縮の見込みは手順 0 の後に改める。

### 1.5 作業用の Mac の制約【事実】

- CPU: Intel Core i5-1038NG7（4 コア 8 スレッド）、メモリ 16 GB。
- 熱による制限: 手順 5 の run と並べて計測用の run を走らせたとき、`pmset -g therm` が `CPU_Speed_Limit = 71`（最高の 71% に制限）を示し、手順 5 の run の CPU 使用率が 94% から 58% に落ちた。計測用の run を止めると 98% に戻った。**2 本を並べても 2 倍にはならない**（第3.7節の見込みはこれを入れる）。
- Python は計算の多い処理を 1 プロセスの中で同時に走らせられない（GIL）ので、並列にするなら別プロセスにする。macOS の Python 3.12 の既定では、子プロセスは親のメモリを引き継がず、データを読み直す。

## 3. 改善 2: 標準と候補の組を並列に走らせる【提案】（D23-1 (a)・D23-2 (a)・D23-3 (a)・D23-4 (a) の推奨で書く）

### 3.1 なぜ組ごとか【導出】

- 並べるのは 2 本だけなので、メモリ 16 GB・4 コアの Mac で動く見込みがある（第3.3節）。fold の中の試行を並べる形（D23-1 (b)）は 4 本以上を並べないと効かず、この Mac ではメモリが足りない見込みが高い。

### 3.2 動き（仮置き 4・6）

1. 親プロセスは今と同じく、記録票の保存・事前検査・既存成果物の確認・台帳の開始の行・束縛の記録までを行う。
2. 親は組ごとに子プロセスを 1 つずつ起こす（計 2 つ）。子は自分の組の読み取り面を組み立て、**今と同じ順序で** fold の単位と経路の区間を走らせ、開始記録・試行記録・選定記録・経路の記録を今と同じファイルに書く（組ごとにディレクトリが分かれている: `search/standard/`・`search/candidate/`）。
