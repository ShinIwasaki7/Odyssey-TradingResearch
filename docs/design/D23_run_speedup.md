### 1.5 作業用の Mac の制約【事実】

- CPU: Intel Core i5-1038NG7（4 コア 8 スレッド）、メモリ 16 GB。
- 熱による制限: 手順 5 の run と並べて計測用の run を走らせたとき、`pmset -g therm` が `CPU_Speed_Limit = 71`（最高の 71% に制限）を示し、手順 5 の run の CPU 使用率が 94% から 58% に落ちた。計測用の run を止めると 98% に戻った。**2 本を並べても 2 倍にはならない**（第3.5節の見込みはこれを入れる）。
- Python は計算の多い処理を 1 プロセスの中で同時に走らせられない（GIL）ので、並列にするなら別プロセスにする。macOS の Python 3.12 の既定では、子プロセスは親のメモリを引き継がず、データを読み直す。

## 2. 改善 1: 記録の書き出しの無駄を削る【提案】

### 2.1 変えること

1. **データ能力検査の結果の文字列を 1 回だけ作る**: `FileSystemResultWriter.write` が manifest 用（`_manifest_payload`）と結果用（`_result_payload`）で同じ `DataCapabilityReport` を 2 回 `_capability_payload` にかけている。1 回作った辞書を両方に使う。2 つの報告が同じものでなければ（同じオブジェクトでも、等しくもない場合）今のとおり別々に作る。D06 §9.4 の「manifest と結果の両方が同じ内容を持つ」は変えない（書く中身は同じで、作る回数だけが減る）。
2. **型の情報を型ごとに 1 回だけ調べる**: `backtest/trace/recorder.py` の `_hints(cls)` を、型ごとに結果を覚える形にする（`functools.cache`）。型の定義は実行中に変わらないので、返す内容は今と同じ。

### 2.2 手順 0 の結果で足すもの（仮置き 3）

手順 0（実データの計測）で上の 2 つ以外に大きな無駄が見つかったら、**出力のバイト列を変えないもの**に限り同じ PR に足してよい。足したものは PR の本文に「何を・なぜ・どれだけ」で書く。出力を変えるもの（判断履歴の形・記録の中身・正規化エンコードの規則）は入れず、人間に報告する。

### 2.3 確かめ方（仮置き 2）

1. 識別子の固定値テスト（`test_mt5_run_identity.py`）が、変更の前と同じ期待値のまま合格する（`run_id`・結果のダイジェスト・判断履歴の全表のダイジェスト）。
2. 同じテストの作業場で、変更の前の木と後の木の `manifest.json`・`result.json` のバイト列が一致する（コードのダイジェストを固定）。PR #93 と同じく、期待値は変更の前の木で記録する。
3. 実データで 1 単位（手順 5 の版 2 の検証区間の単位 1 本。約 7.5 分）を、コードと環境のダイジェストをその単位の run manifest に記録された値に固定して作業用のディレクトリに走らせ、`run_id`・結果のダイジェスト・判断履歴の全表のダイジェストが手順 5 の成果物と一致する（成果物はダイジェストとファイルのバイト列だけを比べ、指標・取引の値は表示しない。`runs/` の本物の成果物には書かない）。
4. 合成データの 3 週間の run の時間を、変更の前と後で測って PR の本文に書く。

### 2.4 見込み【導出、仮定付き】

第1.4節の割合がそのまま当てはまるなら、1 本あたり約 3 割短くなる（2 回のうち 1 回を減らす 5.4 秒 + 型の情報の調べ直しの大半の約 4 秒 = 約 9.4 秒。28.4 秒の約 33%）。実データでは取引とシミュレーション本体の割合が増え、記録の割合が下がる可能性があるので、**見込みは 20〜33%**、実験 1 回は約 12.8 時間 → 約 8.5〜10 時間とする。手順 0 で他の無駄が見つかり仮置き 3 で足せば、さらに縮む。見込みは手順 0 の後に改める。

## 3. 改善 2: 標準と候補の組を並列に走らせる【提案】（D23-1 (a)・D23-2 (a)・D23-3 (a)・D23-4 (a) の推奨で書く）

### 3.1 なぜ組ごとか【導出】

- 標準の組と候補の組は、snapshot が違うので同じ `RunId` を持たない（`RunId` は snapshot を含む）。評価の使い回し（`cache`）は組をまたいで当たらない。組どうしの依存は、両組の全 fold と経路が終わった後の「組の判定・集約表・結末記録・台帳の結末の行」だけである（`execute_search`）。
- 組の中の順序（fold → 局面 → 試行、選定記録を検証の run より前に保存、経路の区間を順番に）は**変えない**ので、D09 §7.5 と経路の残高の引き継ぎはそのまま守られる。
- 並べるのは 2 本だけなので、メモリ 16 GB・4 コアの Mac で動く見込みがある（第3.3節）。fold の中の試行を並べる形（D23-1 (b)）は 4 本以上を並べないと効かず、この Mac ではメモリが足りない見込みが高い。

### 3.2 動き（仮置き 4・6）

1. 親プロセスは今と同じく、記録票の保存・事前検査・既存成果物の確認・台帳の開始の行までを行う。
2. 親は組ごとに子プロセスを 1 つずつ起こす（計 2 つ）。子は自分の組の読み取り面を組み立て、**今と同じ順序で** fold の単位と経路の区間を走らせ、開始記録・試行記録・選定記録・経路の記録を今と同じファイルに書く（組ごとにディレクトリが分かれている: `search/standard/`・`search/candidate/`）。
3. 子は結果（選定・試行記録・指標・経路の要約・事後検査の結果）を戻り値で親へ返す。
4. 親は両方の子が終わってから、今と同じ順（標準 → 候補）で集約表を書き、結末記録 → 台帳の結末の行を書く。
5. 並列か順番かは記録票に入れず、表示と実行の包みの `launch.json` にだけ残す（結果を変えないので識別子の材料にしない）。

**変わること**: 標準の組の終わりを待たずに候補の組が始まる。ファイルの更新時刻の並びと、途中で止まったときに「どこまで進んでいたか」の形が変わる（両組が途中まで進んだ状態がありうる）。**変わらないこと**: 各ファイルの中身、`run_id`、結末記録、台帳の行（実行ごとの乱数の文字列を除く。これは今も実行ごとに違う）。

### 3.3 メモリ（仮置き 5）

- 版 1 の最大メモリは 7.1 GB で、両組の読み取り面を 1 プロセスが持った結果である可能性が高いが、確かめていない。手順 0 で「組 1 つだけを持つプロセスの最大メモリ」を測る。
- 起動前に空きメモリを確かめ、「組 1 つの最大メモリ × 2」に足りなければ今の順番で走らせ、その旨を表示する。測った値は設定の既定値として実装 PR に書く（実行ごとの値ではない）。
- 測った結果、2 本でも 16 GB に収まらないと分かった場合は、実装に進まず人間に報告する（メモリを減らす変更は本書の範囲の外）。

### 3.4 確かめ方

1. 合成データの探索の実験（`test_search_v3_path.py` の作業場。2 fold・両組・経路あり）を、順番と並列の両方で走らせ、`search/` 配下と `runs/` 配下の全ファイルのバイト列、結末記録、台帳の行が一致する（実行ごとの乱数の文字列は固定する）。
2. 子プロセスの片方で例外を起こさせ、もう片方も止まり、終了コードと残る記録が今の「中断」と同じ形になる（D23-4 (a)）。
3. 同じ版の再実行で、止まる前に終わった単位が再利用される（`run_reused`）。
4. 空きメモリが足りないとき、今の順番で走り、その旨を表示する。
5. `experiment reproduce` でも 1. と同じ一致を確かめる（D23-3 (a)）。

### 3.5 見込み【導出、仮定付き】

- 両組の時間はほぼ同じ（第1.1節）なので、理想では約半分。熱による制限（第1.5節）と、子プロセスがデータを読み直す時間（手順 0 で測る）を入れ、**約 1.5〜1.8 倍速くなる**と見込む。
- 改善 1 と合わせると、実験 1 回は約 12.8 時間 → **約 5〜7 時間**（改善 1 の後の約 8.5〜10 時間を、改善 2 の 1.5〜1.8 倍で割った値）。
- 8 コア以上・32 GB 以上のマシンへ移す場合は、D23-1 (b)（fold の中の試行を並べる）を足すとさらに短くなる。本書では作らない（第6節）。

## 4. 要決定の詳しい候補と理由（推奨は決定ではない）

### D23-1 並列に走らせる単位の大きさ

| 候補 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| **(a) 組ごとの 2 本【推奨】** | 標準の組と候補の組を別プロセスで同時に走らせる。組の中の順序は今のまま | 組の中の順序・選定記録の時点・経路の残高の引き継ぎが変わらない。この Mac のメモリで動く見込み。実装が小さい（約 2〜3 日） | 最大でも 2 倍。**既決の改訂を伴う**（D09 §5.4 の「組（`standard` → `candidate`）」と「並列に走らせない」） |
| (b) fold の中の試行ごと | fold ごとに 4 試行の選定区間の単位を同時に走らせ、そろってから選定 → 検証区間 | 大きなマシンなら選定区間（全体の約 8 割）が試行の数だけ速くなる | 4 本を並べるとこの Mac ではメモリが足りない見込み。記録の書き込み順を親で並べ直す仕組みが要る。**既決の改訂を伴う**（D09 §5.4 の「並列に走らせない」）。実装は約 4〜5 日 |

推奨の理由: 本書の目的は今の Mac での実行時間を縮めることで、(a) が最小の変更で守るべき既決（D09 §7.5、経路の順序）を崩さない。(b) は実行環境を大きなマシンへ移すと決めたときに別の文書で設計するのがよい。

### D23-2 並列で走らせるかをどう選ぶか

| 候補 | 中身 |
|---|---|
| **(a) 引数で選ぶ【推奨】** | `experiment run`・`experiment reproduce` に並列を選ぶ引数を足す。引数の既定は今の順番。実行の包み（`tools/ops/run_experiment.py`）は並列を使う。何かあったときに今の順番へ戻せる |

| 候補 | 中身 |

### D23-4 片方の組が例外で止まったとき、もう片方をどうするか

| 候補 | 中身 |
