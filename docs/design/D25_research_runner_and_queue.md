### 2.4 実行器の動かし方【提案】（D25-14 (a)）

- 実行器の道具は「1 歩進める」コマンド（例の形: `uv run python -m tools.ops.research_runner step --repo <リポジトリ>`）だけを持つ。1 回の呼び出しで、全体の状態とカードごとの状態を `runs/runner/state/` から読み、進められる段を順に進め、状態を書いて終わる。長く待つ処理（run・審査・最終検証・作業役）はすべて別のプロセスに切り離し、次の呼び出しでその終わりを見る。
- Mac の定期起動（launchd の利用者のエージェント）が 5 分ごとに呼ぶ（間隔は登録で変えられる。登録は人間）。同時に 2 つの呼び出しが走らないよう、呼び出しは `runs/runner/step.lock` を排他的に作ってから進め、作れなければ何もせずに終わる。ロックを作った後に止まったときは、ロックの作成時刻が 30 分より古く、書いたプロセスが無ければ次の呼び出しが外す（台帳のロックとは別物で、台帳のロックは自動で外さない。D09 §10.12.1）。
- 状態のファイルは段を進めるたびに一時名に書いてから置き換える（`run_experiment.py` の `_write_json` と同じ形）。停電・再起動の後の最初の呼び出しは、各カードに「起動し直した」（表 2-1 の e17）を当て、次の**照合**で、その状態の中のどこまで済んでいたかを決める（プロセスが消えたことだけで失敗にしない）。
- **起動し直したときの照合**: 実行器は、自分が切り離して起動する処理（審査・最終検証・再現・作業役）を、終了コードと終了時刻を `runs/runner/state/<カード>/<処理>/` に書く小さな包みで起動する（`run_experiment.py` と同じ考え方。探索の run は `run_experiment.py` の `exit_code.txt`）。実行器は、処理を起動する**前に**、状態のファイルにその処理の「起動した」の印（処理の名前・試みの番号・時刻）を書く（予約しただけの処理には書かない）。照合は次の順で、最初に当たったものに従う。(0) その処理に「起動した」の印が無い（空きを待つ予約だけ）→ 変化なし（予約のまま空きを待つ）。(1) その処理の成果が永続の記録にある（探索の run の `exit_code.txt`、作業役の `out/` の決まったファイルがそろっている、審査台帳・最終検証の台帳にこの実行の行がある）→ 終わった処理として、その結果の出来事（e7・e8・e10・e11・e12・e13）を当てる。続く PR があれば、その PR の状態を GitHub から読み直す（無ければ作る）。(2) 記録した終了コードがある → その終了コードの出来事を当てる。(3) プロセスが生きている → 変化なし。(4) どれでもない → 途中で止まった処理として、表 2-1 のその状態の e17 のマスに従う。
- D25-14 (b) なら同じ「1 歩」を常駐のプロセスが繰り返す（再起動の後は人間か司令塔が起こし直す）。(c) なら司令塔のセッションが呼ぶ。

### 3.2 識別子【提案】（仮置き 4）

- カード: `<口の 1 文字>-<YYYYMMDD>-<title>`。日付は `created_at` の日付（UTC）。
- 実験と戦略: `c_<口の 1 文字><YYYYMMDD>_<title の - を _ に>_<通貨の小文字>`。実験と戦略は同じ識別子にし、戦略の版は改善で宣言を変えたときだけ上げる（`_v1`・`_v2`）。実験の版（`version`）は改善のたびに上げる（D14 の仮置き 8 の形）。
- 同じ識別子のカード・実験・戦略が既にあれば、CI が落とす（人間の口）か、実行器が `title` の後ろに `-2`・`-3` を足す（AI の口）。

### 3.3 置き場と移動【提案】（D23 §5.2、仮置き 21）

| 移動 | いつ | どの PR で |
|---|---|---|
| （無し）→ `queue/`（人間の口） | 人間がカードを書いたとき | 定型でない PR（人間が merge。カードを置くことは関所ではない） |
| （無し）→ `queue/`（AI の口） | 発想役のカードが機械の検査を通ったとき | 定型 PR（事前登録の種類） |
| `queue/` → `taken/` | 段 2 の事前登録の PR に含める | 定型 PR（事前登録） |
| `queue/` → `done/`（棄却） | 段 1 の機械の検査に通らなかったとき | 定型 PR（一巡の報告の種類。理由の識別子を `outcome` に書く） |
| `taken/` → `done/` | 段 8 を通ったとき、またはカードの停止で人間が「このカードを終える」と答えたとき | 定型 PR（一巡の報告） |

- `done/` は「一巡が終わった」を表す。審査の入口を通った後の候補の進み方（審査・固定・最終検証）は台帳と固定の記録が正本で、カードは `done/` のまま動かない。

### 3.4 凍結【提案】（D25-2 (a)）

1. **凍結の時点**: カードを `taken/` に移す事前登録の PR が main に merge された時点。以後、そのカードのファイルを変えない（CI が `taken/`・`done/` のカードの中身の変更を落とす。移動だけを許す）。
2. **凍結の対象**: カードのファイル全体のバイト列の SHA-256 と、生成物（戦略の宣言・実験設定）のバイト列の SHA-256 と、生成の道具のダイジェスト（道具のファイルの SHA-256）を、事前登録の注記 `research/loops/<カード>/prereg_v1.yaml` に書く。改善の版では、さらに変更の提案 `change_v<版>.yaml` の SHA-256 を書く。
3. **確かめ方**: CI が、PR で足された・変わった事前登録について、カード（と変更の提案）から生成の道具で作り直し、生成物とバイト単位で一致することを確かめる（第6.3節の 4）。生成の道具は、その PR の時点の main の道具を使う（後で道具を直しても、過去の生成物は作り直さない）。
4. 実行の前の凍結（宣言と実行の一致）は今のまま記録票と台帳で確かめる（D23 §2「事前登録の凍結」、関門の機械の項目。第5.5節）。

- D25-2 (b) なら 1・2 の生成物の SHA-256 だけを残し、3 を行わない。カードの書き換え・生成物の手の直しは CI で落ちない。

### 3.5 機械の検査【提案】（D23 §5.3、D25-3 (a)、仮置き 29）

取り出しの直後（段 1）に、次をこの順に当て、最初の不合格の理由の識別子で棄却する（棄却の型）。

| 順 | 検査 | 理由の識別子 |
|---|---|---|
| 1 | 書式（第3.1節の項目・型・語彙、識別子の形とファイル名、自由文に数字が無い、`rule` の数がパラメータか格子の値にある） | `CARD_FORMAT` |
| 2 | 部品がカタログにあり、版が合う | `CARD_COMPONENT_UNKNOWN` |
| 3 | 履歴窓が日足 60 本以下（部品の窓を日足の本数に直した最大） | `CARD_HISTORY_TOO_LONG` |
| 4 | 格子が 4〜6 試行（決定 99）、試行の上限 100 以下 | `CARD_GRID_SIZE` |
| 5 | 証拠の見込みが `UNLIKELY` でない | `CARD_EVIDENCE_UNLIKELY` |
| 6 | 既出の規則と重ならない: `configs/strategies/` の全宣言と `done/`・`taken/` の全カードの戦略を正規化した形のダイジェスト（仮置き 29）と、このカードのものが一致しない。**通貨の違いは数える**（D25-3 (a)。系列の名前の通貨を正規化で残す） | `CARD_DUPLICATE_RULE` |
| 7 | （段 2）生成・読込（照合 C1〜C7 と `final_holdout` の検査 4 を含む）・全試行のコンパイル・複雑さの上限・準備の確かめ（`prepare_search`）が通る | `CARD_PREREG_REJECTED` |

- 不合格の原因がカードの中身でなく道具や環境（snapshot が開けない、道具の例外）なら棄却にせず、失敗として数えてカードの停止（`TOOL_FAILURE`）にする（D23 §4.7 の「同じ種類の失敗」）。
- 改善の版（段 6）で 2〜4・6・7 に当たる変更は、棄却でなくカードの停止（D23 §4.2 の段 2「改善後の実験で通らないときは停止」）。6 は同じカードの前の版には当てない（改善は同じ規則の中の変更）。
- **D25-3 (a) の理由【推奨】**: 人間の指示 D「それがどの相場でも通用するのかを判定する」に合い、同じ規則を別の通貨で確かめることを機械で止めない。同じ着想の試行が通貨の数だけ増える偶然は、評価の側の判定と封印の最終検証で受ける（D23 §1.4 の 4・5）。AI のカードは同時に 3 枚まで（決定 153）なので、待ち行列が同じ規則の通貨違いで埋まる速さにも上限がある。D25-3 (b) なら正規化で系列の名前の通貨を外す。

### 3.6 取り出しの規則【既決】＋【提案】（決定 151、仮置き 5）

1. 待ち行列の人間の口のカードを、古い順に先に取り出す。
2. 人間の口のカードが無ければ、AI の口のカードを古い順に取り出す。
3. 「古い順」の鍵は、カードのファイルが main の first-parent の履歴で初めて現れたコミットの時刻（同じなら識別子の辞書順）。
4. 取り出すのは、実行の空き（第4.4節）が 1 つあり、起動待ち（表 2-1 の C3）のカードが無いときに 1 枚だけ。1 枚のカードが段 2〜段 8 にいる間も、空きがあれば次のカードを取り出す（並列 2 の空きを埋める）。
5. 全体の停止（第4.6節）の間は取り出さない。

### 3.7 上限【既決】＋【提案】（決定 153、仮置き 15）

- 待ち行列（`queue/`）の AI の口のカードは同時に 3 枚まで。3 枚あるときは発想役を起動しない。
- 発想役を起動するのは、(1) カードが `done/` に移ったとき（最大 1 回）、(2) 待ち行列が空で取り出せないとき（1 回だけ）。(2) で書けなかった（出力なし・機械の検査で全部棄却）ら、全体の停止（`QUEUE_EMPTY`）。
- 発想役の 1 回の起動で書けるカードは、上限までの空き（3 − 待ち行列の AI のカードの枚数）まで。

### 3.8 事前登録の生成【提案】（D25-4 (a)、仮置き 8〜11）

カードから次を作る。**判断を入れず、写す・決まった値を入れるだけ**（D25-1 (a)）。

| 生成物の項目 | 出どころ |
|---|---|
| 戦略の宣言 `schema_version`・`strategy_id`・`version` | 書式の版、第3.2節の識別子、版 1（改善で宣言を変えたら上げる） |
| 戦略の宣言の本体 | カードの `strategy` をそのまま |
| 実験設定 `schema_version`・`id`・`version` | 書式 v2、第3.2節の識別子、版 1（改善のたびに上げる） |
| `hypothesis` | カードの `rule` ＋ 定型の結び（仮置き 11） |
| `research_policy` | 生成の時点の登録簿の現行の版（仮置き 10） |
| `strategy` | 生成した戦略の宣言のパス |
| `environment`・`execution_series`・`resolution_hierarchy`・`seed` | 通貨ごとの型板（仮置き 9）。`seed` は 0 |
| `snapshots`・`conversion_snapshots`・`account`・`risk_policy`・`execution_policy`・`cost_model`・`conversion_policy` | 現行の研究ポリシーの `basis` の、その通貨の値（照合 C2〜C7 を生成の段で必ず満たす） |
| `evaluation` | 現行の研究ポリシーが求める指標集合の版（第 5 版の値は D24） |
| `search_plan` | `{kind: GRID, max_trials: <列挙した試行の数>, axes: <カードの grid.axes>}` |
| `split` | `STANDARD` |
| `final_holdout` | **最終検証を予定する宣言を必ず書く**（D25-4 (a)）: `{interval: {start: "2024-01-01T00:00:00Z", end: "2100-01-01T00:00:00Z"}, purpose: "順 11 の実行器のカード <カードの識別子> の研究候補の最終検証（D09 §9.10）"}` |
| `lineage`（改善の版だけ） | `{derived_from: <前の版の experiment_id と execution>, change_kinds: [<変更の提案の種類>], note: <変更の提案の理由の文>}`（第3.9節）。新しいカードの版 1 には書かない（D23 §4.3「系譜は任意」） |

- **D25-4 (a) の理由【推奨】**: 探索の run は `final_holdout` を読まない（D22 §1.4 の事実 3）ので、書いても実行の中身・時間・判定は変わらず、変わるのは実験の識別子だけである。`NONE` だと、審査が「進める」の候補が最終検証へ進むのに再実行（約 9〜14 時間。台帳が 2 行増える）と取り下げが要る（D22 §1.4 の事実 5）。宣言は封印データの要求・取得・閲覧のどれでもない。
- 生成の後に、読込・全試行のコンパイル・照合・準備の確かめ（`prepare_search`。snapshot を開くが run はしない）を実行器が行い、合否・試行の数・拒否の数・時間・最大メモリだけを注記に書く。CI は snapshot を読めないので、CI では読込とコンパイルだけを確かめる（第6.3節の 4）。

### 3.9 改善の変更の提案【提案】（決定 102・103、仮置き 6・12）

分析役は、版ごとに次の形の YAML を 1 つ書く（束の `out/change.yaml`）。実行器が検査し、通れば `research/loops/<カード>/change_v<次の版>.yaml` に写して改善後の事前登録を生成する。

```yaml
schema_version: 1
card: "<カードの識別子>"
from_version: 1            # この版の結果を読んで書いた
decision: CHANGE           # CHANGE か FINISH（FINISH は版 2 の後から。仮置き 12）
change_kind: PARAMETERS    # PARAMETERS（格子の変更）か STRATEGY_CODE（既存の部品の範囲の宣言の変更）の 1 つ
operations:                # 機械で当てる操作の並び（型のある値だけ。下の表）
  - {op: set_axis_values, instance: "<…>", parameter: "<…>", values: [<…>, <…>]}
reason: "<数字を含まない理由の文>"
prediction: "<数字を含まない予想の文>"
memo_sha256: "<分析メモの SHA-256>"
```

| 操作 | 種類 | 中身 |
|---|---|---|
| `set_axis_values`・`add_axis`・`remove_axis` | `PARAMETERS` | 軸の値・軸を足す・外す（試行 4〜6 のまま） |
| `set_parameter` | `STRATEGY_CODE` | 軸でないパラメータの値を変える |
| `add_component`・`remove_component`・`rewire_input`・`set_role` | `STRATEGY_CODE` | カタログにある部品を足す・外す、入力のつなぎ替え、役割の割当 |

- 実行器の検査（不合格は停止の型。D23 §4.2 の段 5・6）: (1) 書式と型、(2) `operations` が全部 `change_kind` の種類（1 種類。決定 102）、(3) 版が 3 を超えない（再評価 2 回まで。決定 103）、(4) `FINISH` が版 1 の後でない、(5) 部品がカタログにある・履歴窓・試行 4〜6・複雑さ（第3.5節の 2〜4・7）、(6) 値が書いてある（決定 67 の形。値の無い操作は `VALUE_MISSING`）、(7) 自由文に数字が無い。
- `PARAMETERS` で格子だけを変えるときは戦略の版を上げず、`STRATEGY_CODE` のときは戦略の版を上げる。どちらも実験の版を上げる。

### 4.7 関所 2 の問いの形【提案】（D25-10 (a)、仮置き 25）

**届け方**: 実行器が GitHub の issue を 1 つの止まりにつき 1 つ作る（題: `[runner] 止まった: <理由の識別子> <カードの識別子か「全体」>`、ラベル `runner-stop`）。本文は無人運転の取り決め §2 の様式に合わせる。

```
【何を決めるか】<止まった理由ごとの表の「問い」。結果にどう影響するかを先に書く>
【背景】<最大 2 行。カードの識別子・段・版・時刻・理由の識別子だけ。成績の数値・判定の値を書かない>

返信は番号だけで可。「他:」で始めれば自由記述を受け付ける（実行器は自由記述を読めないので、止まったまま司令塔・設計役の作業になる）。
```

**答えの受け方**: 実行器は、問いの issue に問いの後に書かれたコメントのうち、本文が番号 1 つだけ（前後の空白は許す）の最初のものを答えとし、コメントの識別子と時刻を状態に記録して issue を閉じる。「他:」で始まるコメントは答えとして扱わず、issue を開いたままにする。作業役のセッションは `runner-stop` の issue にコメントしない（仮置き 25。拒否の規則は人間が足す。第6.6節）。

**理由ごとの問いと選択肢と、答えの後に実行器がすること**（推奨を先頭。T39 の「止まる前の状態に戻す」の中身は右端の列が正本）:

- **答えの読み方**: 「止めたまま」の答えは記録するだけで、issue を開いたまま、その後の番号のコメントを待つ（後から別の番号を書けば、その答えに従う）。状態が動く答えを受けたら issue を閉じる。

- **自動で解ける理由**: 右端の列に「自動」と書いた理由は、答えが「止めたまま」（または答えが無い）でも、毎回の「1 歩」で書いた確かめを当て、通れば止まる前の状態に戻して issue を閉じる（人間の答えを待たずに進むのは、人間が既に選んだ「待つ」の内容が満たされたときだけ）。

| `rules/` | 研究ポリシーの現行の版のファイル、本書の第3.1節・第3.9節の写し | 写す | 写す | 写す |

- **D25-6 (a) の理由【推奨】**: ADR-0041 の改定文は、封印データと最終検証・前向き検証の結果を 4 つの役割としては読まないと定める。許可の一覧で写したものだけが見える形なら、新しい出力の置き場が後から増えても、写す一覧に足さない限り読めない（拒否の一覧で守る (b) は、漏れた置き場が読めてしまう）。コマンドの実行を許さないので、`cat` などで束の外を読む道も無い（`claude_review.py` の注記の限界と同じ問題を避ける）。束を作る時間とディスクは、レポートと記録の写しだけなので小さい（`runs/<run_id>/` の詳細は写さない）。
- **限界【事実】＋【導出】**: 作業役（AI）が学習で持ちうる 2024 年以降の相場の知識は、束では止められない。決定 150 で受け入れた形のまま（D23 §5.4、ADR-0045 の「受け入れた限界」）。
- 写した一覧（パスと SHA-256）を `runs/runner/bundles/<起動の識別子>/manifest.json` に残す。発想役のカードの `read_scope` は、この一覧の中のパスでなければ機械の検査で落ちる（`CARD_FORMAT`）。

### 5.3 発想役の手順【提案】（D23 §5.4、決定 152・153）

1. 束の `ledger/`・`reports/`・`analysis/`・`reviews/`・`records/` を読み、既存の部品（`catalog/`）だけで書ける仮説を考える。
2. 既出の規則（`records/` の宣言とカード）と部品の組み合わせ・接続が同じにならないものだけを書く（第3.5節の 6。値だけを変えたものは書かない）。
3. 第3.1節の書式でカードを書く。`mouth: ai`、`read_scope` に読んだ束のパスを書く。自由文に数字を書かない。証拠の見込みを部品の構造から書く。
4. 書けるのは上限の空き（第3.7節）まで。書けないときは何も書かずに終わる（出力なし）。
5. 実行器はカードに第3.5節の 1〜6 を当て、通ったものを AI の口の定型 PR で `queue/` に入れる（落ちたものは捨て、件数だけを週の要約に書く）。その PR の CI が落ちたら、カードは待ち行列に入らず（表 2-1 の状態を持たない）、失敗の種類 `CI_FAILED` として数える（2 回続けば全体の停止）。発想役は実行もコミットもしない（D23 §5.4）。

### 5.4 分析役の手順【提案】（D14 §2.4 の形、W7、仮置き 30）

- **段 5（版 n の後）**: 束の `reports/`・`analysis/`・`ledger/` を読み、D14 §2.4 の「原因分析で読む表示」の表と、第 5 版の報告の表示（局面ごとの損益の表・得意な局面の確かめ。名前は D24）を観点にして、数値入りの分析メモ（読んだ表示・原因の仮説・変更の候補・予想を先に書く）と、変更の提案 1 つ（第3.9節。版 2 の後は「終える」も選べる）を書く。規則に無い判断が要るなら `change.yaml` に `decision: AMBIGUOUS` と理由の識別子を書いて終わる（実行器が停止の型にする）。
- **段 7（最後の版の後）**: 全版の比較表（数値入り。版管理の外）と、一巡の報告の文（予想 → 変更の理由 → 変更の中身 → 結果の差の置き場。数字を書かない）を書く。結果の差の中身は比較表に書き、報告の文には比較表の置き場だけを書く（D14 §7.1・決定 104 の 2 層）。

### 5.5 確かめ役の手順と関門の機械の項目【提案】（D23 §4.2 の段 8、W9、仮置き 14）

- **確かめ役**: 束の報告の文・比較表・分析メモ・変更の提案・カードを読み、(1) 変更の理由が分析メモの原因の仮説から来ている、(2) 変更の中身が理由に対応している、(3) 予想が変更の前に書かれ、結果の差の置き場がある、(4) 報告の文に数字が無い、をそれぞれ `PASS`・`FAIL` で書く（理由の識別子つき）。報告を書いた分析役のセッションとは別のセッション・別のモデル（仮置き 16）。
- **実行器の機械の項目**（D22 の関門 X1〜X3・X5 の形のうち、見た成績の範囲の項目を除く。D23 §4.2 の段 7・8）:
  1. 全版の事前登録の merge のコミットが、その版の記録票の `git_commit` の祖先で、`git_dirty` が偽。
  2. 台帳に全版の開始と結末の行があり、改善の版の系譜が前の版を指し、変更の種類が 1 つで、理由の文のダイジェストがある。
  3. 全版のレポートが保存済みの成果物から作り直せる（`experiment report` が終了コード 0）。
  4. 元の実験の再現が一致する（決定 107）。
  5. 改善の版のレポートに「独立した確認ではない」の注記が出ている（注記の有無だけを、レポートの決まった見出しの有無で確かめる）。
- 出力は合否と理由の識別子だけ。

### 5.6 作業役の出力の検査【提案】

実行器は、作業役が終わったら `out/` のファイルの形だけを検査する（中身の良し悪しは判断しない）。

| 検査 | 不合格のとき |
|---|---|
| 決まったファイルがある・YAML として読める・項目と型が合う | 出力なし（`WORKER_FAILED`）。同じ段を 1 回だけやり直し、2 回目で停止 |
| 自由文に数字が無い（仮置き 6） | 規則の外（`CHANGE_OUT_OF_RULES`。発想役のカードは `CARD_FORMAT` で捨てる） |
| 束の外のパスを指していない（`read_scope`・メモの SHA-256 の対象） | 規則の外 |
| 決まったファイルのほかに `out/` に何も無い | 余分なファイルを捨てて記録（失敗にしない） |

## 6. 台帳の自動のコミット・定型 PR・CI・関所 1

### 6.1 台帳の行のコミットの経路【提案】（W1、D25-7 (a)、仮置き 20）

1. `experiment run`・`experiment review` が実行用の作業木の台帳に追記する（書き手は変えない）。
2. 実行器は、run・審査が終わったとき（と起動の前の確かめの 2）に、台帳のロックが無く、台帳が改行で終わっていることを確かめてから、実行用の作業木で `experiment ledger`（L0〜L11）を走らせ、終了コードが 0 なら台帳のファイルだけを `runner/exec` の枝にコミットする。コミットしたファイルの末尾が改行で終わっていなければ（追記の途中を拾った）コミットを取り消して次の「1 歩」でやり直す。
3. 実行記録の定型 PR（`runner/exec` → main）を作り、merge のコミットの方式で自動 merge を指定する（第6.4節）。
4. 最終検証の台帳は主の作業木で最終検証のコマンドが書き、実行器が `runner/final-<実験>-<実行番号>` の枝に写して定型 PR にする（仮置き 22）。merge の後、主の作業木に残る `research/final_validations.jsonl` の追記は、手元の内容が `origin/main` の内容とバイト単位で同じときだけ追跡の内容に戻し、主の作業木を `origin/main` に早送りする（仮置き 33）。違えば戻さずに停止（`MAIN_CHECKOUT_NOT_READY`）。行を手で消さない。

### 6.2 定型 PR の種類と中身【提案】（ADR-0043 第2項の 3、仮置き 21）

| 種類 | 枝 | 足す・変えるファイル | PR 本文 |
|---|---|---|---|
| 事前登録 | `runner/prereg-<カード>-v<版>` | 生成物（`configs/strategies/`・`configs/experiments/`）、`research/loops/<カード>/prereg_v<版>.yaml`・`change_v<版>.yaml`、カードの `queue/` → `taken/` の移動（版 1）、AI の口のカードの追加（`runner/cards-<時刻>` の枝でカードだけの PR も同じ種類） | 型（下）どおり |
| 実行記録 | `runner/exec`、`runner/final-…` | `research/trial_ledger.jsonl`・`adoption_reviews.jsonl`・`final_validations.jsonl` の追記、`research/loops/<カード>/run_v<版>.yaml` | 型どおり |
| 一巡の報告 | `runner/report-<カード>` | `research/loops/<カード>/report.yaml`、カードの `done/` への移動と `outcome`（棄却のときは移動と `outcome` だけ） | 型どおり |

- **PR 本文の型**: 題は `[runner] <種類> <カードの識別子> v<版>`。本文は種類・カードの識別子・版・実験の識別子・生成物と記録の SHA-256・時刻・件数（試行の数・行の数）と、「本 PR は実行器の定型 PR（ADR-0043）。成績の数値・判定の値を含まない」の定型の文だけ。台帳の行（判定の値を含む）を本文に写さない（決定 110 の形）。
- **定型 PR に入れないもの**（ADR-0043 第2項の 4）: 設計文書・実装（`src/`・`tools/`・`tests/`）・研究ポリシー・登録簿・CI の設定・型板・エージェント定義の変更と、固定の記録。

### 6.3 CI の検査【提案】（D25-11 (a)、仮置き 6・20）

CI に、全 PR と main への push で走る新しい段を 1 つ足す（PR 6）。

| # | 検査 | 当てる PR |
|---|---|---|
| 1 | **台帳**: 3 つの台帳を読込の検査 L0〜L10（鎖を含む。審査台帳と最終検証の台帳も同じ形の検査）にかけ、PR の基点の台帳の内容が PR の台帳の先頭とバイト単位で同じ（追記だけ）であることを確かめる | 全 PR と main への push（台帳を変えない PR でも当てる。軽いので） |
| 2 | **枝の名前と種類**: 枝が `runner/` で始まる PR は定型 PR として扱い、題の種類（第6.2節）を読む | 全 PR |
| 3 | **許されたパスだけ**: 定型 PR の変更が、その種類の許されたパス（第6.2節の表）だけ。カードは `queue/` への追加（`mouth: ai` だけ）・移動だけで、`taken/`・`done/` のカードの中身を変えない。定型でない PR が `mouth: ai` のカードを足していない、`taken/`・`done/` のカードの中身を変えていない | 全 PR |
| 4 | **作り直しの一致**（D25-2 (a)）: 事前登録の PR で足された・変わった生成物を、カード（と変更の提案）から main の生成の道具で作り直し、バイト単位で一致する。全生成物の読込と全試行のコンパイルは pytest の試験（PR 7）で確かめる | 事前登録の PR |
| 5 | **記録の書式**: `research/loops/` のファイルとカードが書式どおり（項目・型・語彙） | 定型 PR と、カードを足す定型でない PR |
| 6 | **自由文に数字が無い**: カードの `prediction`・`inspiration`、変更の提案の `reason`・`prediction`、報告の文に数字が無い。`rule` の数はパラメータか格子の値にある | 同上 |
| 7 | **PR 本文の型**: 定型 PR の題と本文が型（第6.2節）どおり（決まった項目のほかの文が無い） | 定型 PR |
| 8 | **自動 merge の守り**: 自動 merge が指定された PR が、定型 PR（2〜7 をすべて通る）でなければ落とす。固定の記録（`research/candidate_fixes/`）を含む PR に自動 merge が指定されていれば落とす | 全 PR（自動 merge の指定・外しの出来事でも走らせる） |

- **D25-11 (a) の理由【推奨】**: 人間の merge を経ずに main に入る PR の中身を、機械の検査だけで「定型の範囲」に閉じ込める（ADR-0043 第2項の 4）。8 は、同じアカウントで動く作業役が設計・実装の PR に自動 merge を付けても、CI が落ちるので main に入らないようにするためである（第1.1節の GitHub のアカウントの事実）。(b) は D25-2 (b) と組。(c) は定型 PR に何が入っても CI を通る。
- L11（成果物からの逆照合）は CI で読めない `runs/` を読むので、実行器がコミットの前に当てる（第6.1節の 2。仮置き 20）。

### 6.4 自動 merge【提案】

- 実行器は定型 PR を作った直後に、merge のコミットの方式で自動 merge を指定する（例の形: `gh pr merge <番号> --auto --merge`）。GitHub は必須の検査（既存のジョブと第6.3節の段）がすべて通ったときに merge する。
- 実行器は管理者の権限で検査を飛ばす merge をしない（`--admin` を使わない）。作業役のセッションは `gh pr merge` を使わない（拒否の規則は人間が足す。第6.6節）。
- CI が落ちたら PR を閉じずに残し、カードの停止（T6）にする。

### 6.5 関所 1 までの経路【提案】（ADR-0042 第1項、D25-15 (a)、仮置き 22）

1. 段 9 で審査が「進める」（T28）。
2. 固定のコマンドは D25-17 (a) なら PR 4c で実行器より先に main に入る。D25-17 (b) で main に無ければ、カードの停止（T31。`FIXATION_TOOL_MISSING`）。以下はそのコマンドがある経路。
3. 実行器が固定の前の機械の確かめ（D09 §9.11.10 の 8 項目）を起動する。項目 6（窓の長さ）だけが外れれば固定を延期し（C11 のまま）、次の定期取得の承認の後にやり直す（D15-15 (a)）。他の項目が外れれば停止（T32）。
4. 確かめを通れば、固定のコマンドが固定の記録を作り、実行器が**定型でない** PR（枝 `candidate-fix/<実験>-<実行番号>`）を作る。題は `[関所 1] <実験の識別子> 実行 <実行番号> の候補の固定（merge = 最終検証の go）`。本文は無人運転の取り決め §2 の様式で、【何を決めるか】「この候補の最終検証を始めてよいか。merge で固定時点が決まり、封印の期間を 1 つ使う（元に戻せない）」、固定の前の確かめの出力（日数・合否・理由の識別子だけ。D09 §9.11.10）、カードと実行の識別子。成績の数値・判定の値を書かない。自動 merge は指定しない（CI が落とす。第6.3節の 8）。
5. **Codex のレビューは求めない**（D25-15 (a)）。人間が PR を merge する（関所 1）か、閉じる（T34）。
6. merge の後、実行器が主の作業木の確かめ（仮置き 22）を通してから最終検証のコマンドを起動する（T35）。結果の数値は読まず、最終検証の台帳の行を定型 PR にする（T37）。

- **D25-15 (a) の理由【推奨】**: 固定の記録は固定のコマンドが作る 1 つの YAML で、中身は機械の確かめ（8 項目）が確かめ済みであり、Codex が見て直せる設計・実装の判断を含まない。関所 1 の人間の操作を merge 1 つにした決定 143・150 の意図に合う。**既決の改訂を伴う**（`docs/pr_review_policy.md` §2「Codex review はどの種別でも必須」に、固定の記録の PR の例外を足す。第9節）。(b) なら固定の PR ごとに Codex 1 巡の待ちが入る（安全弁 3 巡は従来どおり）。

### 6.6 人間が行う設定【提案】（仮置き 20・25。ADR-0043 第3項）

エージェントは次を編集しない。人間が行う。

| 設定 | 中身 | 無いときに起きること |
|---|---|---|
| GitHub: 自動 merge を許す | リポジトリの設定の「Allow auto-merge」 | 定型 PR が merge されず、C2・C6 で止まり続ける（実行器は待つだけ。週の要約に件数が出る） |
| GitHub: merge のコミットの方式を許す | 「Allow merge commits」 | `runner/exec` の早送りができず、2 本目が起動しない（D25-7 (a) の前提） |
| GitHub: main の保護の規則 | 必須の検査に既存のジョブと第6.3節の段を入れる | 自動 merge が検査を待たずに merge しうる |
| GitHub: 直接の push | 進捗ファイルの直接のコミット（無人運転の取り決め §4.2）と、最終検証の消費の行の push（D09 §9.10.2 の段 4）が、保護の規則の下でも通ること（管理者の迂回を許すか、対象を外す） | 進捗ファイルの更新が止まる。最終検証は消費の前に終了コード 8 で止まる（データは読まない。安全側） |
| `CLAUDE.md` | 「人間に確認するのは merge 前のみ」に、実行器の定型 PR の例外を足す（W5。ADR-0043 第3項の 4） | 例外が働かない |
| `.claude/settings.json` の拒否の規則 | 作業役のセッションに `Bash(gh pr merge:*)` と、`runner-stop`・週の要約の issue へのコメントを拒否する | 作業役が定型でない PR を merge したり、関所 2 の答えを書いたりする道が残る（CI の 8 と運用の約束だけで守る） |
| launchd の登録（D25-14 (a)） | 「1 歩進める」を 5 分ごとに呼ぶ利用者のエージェント | 実行器が動かない |

- **限界【事実】**: 人間・作業役・実行器が同じ GitHub のアカウントで動くので、GitHub の設定だけでは「設計・実装の PR は人間が merge する」を強制できない（管理者は迂回できる）。守りは、CI の 8（自動 merge の付いた定型でない PR を落とす）、作業役の拒否の規則、実行器のコードが `--admin` を使わないこと、の 3 つである。

## 7. 週の要約【提案】（決定 149、D25-12 (a)）

- **置き場**: 決まった 1 つの GitHub の issue（題 `[runner] 週の要約`、ラベル `runner-weekly`。最初の 1 回に実行器が作る）。毎週月曜 09:00 JST の後の最初の「1 歩」で、前の週（月曜 00:00〜日曜 24:00 JST）の分を 1 つのコメントとして書く。
- **形**（型どおり。**成績の数値・判定の値を書かない**）:

```
週: <YYYY-MM-DD>〜<YYYY-MM-DD>
カード: 取り出した <件>（人間 <件>・AI <件>）、終えた <件>、棄却 <件>、待ち行列 人間 <件>・AI <件>
実験: 完了 <件>、失敗 <件>、一時停止 <件>、計算時間 合計 <時間>
関門（段 8）: 合格 <件>、不合格 <件>
審査の入口: 通った <件>、通らない <件>／審査: 進める <件>、進めない <件>、保留 <件>
止まり: 新しく <件>（理由の識別子ごとの件数）、答え待ち <件>
発想役: 起動 <回>、書いたカード <枚>、捨てたカード <枚>
ディスク: 空き <GB>、自動で消した <件>・<GB>
（4 週が経っていれば）前の関所の答えから 4 週が経った
```

- **D25-12 (a) の理由【推奨】**: リポジトリを変えず（定型 PR の種類を増やさない）、人間が iPhone の GitHub の通知で読める。(b) は版管理に残る良さがあるが、ADR-0043 第2項の 3 の種類に 1 つ足す改訂を伴う。(c) は司令塔が動いていないと届かない。
