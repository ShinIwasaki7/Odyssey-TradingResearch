本リポジトリの PR レビューの方針を定める。対象は Codex による独立レビューと、
Claude による設計適合レビューの2つのレーン、および merge 判断の所在である。

## 1. 原則

- **レビューと merge 判断を分ける**。レビューは欠陥と設計違反を見つける作業であり、
  merge するかどうかの判断は含まない。**merge 判断は常に人間が行う**（CLAUDE.md）。
- **設計はドキュメントが正本**。実装 PR のレビューは、コードが `docs/design/` と
  `docs/decisions/` の承認済み内容に合致しているかを基準にする。
  設計そのものへの異論は PR ではなく設計文書へ差し戻す。
- **前提を silent に決めない**。レビュー中に未確定の設計判断が必要になった場合は、
  その場で決めずに PR 本文へ「仮置き」として明示し、人間の判断を仰ぐ。

## 2. PR 種別と Codex review の要否

**Codex review はすべての PR 種別で必須である**【決定 2026-09-23】。

| 種別 | 内容 | Codex review |
|---|---|---|
| 設計文書のみ | `docs/design/`、`docs/decisions/` の追加・更新のみ | **必須** |
| 骨格・ツール | ディレクトリ骨格、ビルド/CI 設定、品質ツール設定、運用スクリプト | **必須** |
| 実装 | `src/odyssey_fx/` の振る舞いを持つコード、およびそのテスト | **必須** |

以前は「設計文書のみ」を任意としていたが、**運用（PR #14〜#20）では設計文書の PR にも毎回実施していた**ため、
規定を運用に合わせた。例外を置かないことで、**レビューを省略する経路そのものが無くなり**、
§7 の merge 前提が1本になる。

1つの PR が複数種別にまたがる場合は、重い方（実装 > 骨格・ツール > 文書）に合わせる。
要否は変わらない（どれも必須）が、**レビュー対象範囲の決め方**は §3.1 の表で種別ごとに変わる。

## 3. 指摘の分類

| 優先度 | 内容 | 扱い |
|---|---|---|
| **P0** | 設計違反（承認済み設計・ADR・依存規則に反する）、データ破壊（原データの上書き、holdout の誤読）、先読み（判断時点で利用できない情報の参照）、決定論の破壊 | 必ず修正してから次へ進む |
| **P1** | バグ、契約違反（型・状態機械・不変条件の破り）、テストが検査すべき対象を検査していない | 必ず修正してから次へ進む |
| **P2** | 改善提案、命名、スタイル、将来の整理 | 修正するか、見送る理由を PR に記録する |

指摘に優先度タグが付いていない場合は、上の定義に照らして自分で分類し、
その分類を PR コメントに残す。

### 3.1 レビュー対象範囲による3分類【決定 2026-09-20、PR #14〜#20 で確立】

優先度（P0/P1/P2）を付ける前に、**その指摘が今回の PR のレビュー対象範囲に入るか**を先に判定する。
判定は次の3つのいずれかになり、**いずれも PR コメントに残す**。

| 分類 | 内容 | 扱い |
|---|---|---|
| **対象内** | 今回の PR が決める範囲の中の指摘 | §3 の表で P0 / P1 / P2 を付ける。P0 と P1 は必ず直す |
| **対象外（今回の範囲の外）** | 今回の PR が決める範囲の外への指摘。**担当がある場合と、無い場合の両方を含む** | 直さない。**担当があるなら**どの文書・どの段階かを書く。**担当が無いなら**（今回は変更しない既存仕様、別 PR で扱うコードなど）**対象外である理由**を書く。架空の担当を割り当てない |
| **不採用** | 人間の決定・承認済みの設計と衝突する指摘 | 直さない。**なぜ衝突するかの理由を書き**、設計を変える価値があるなら要決定として人間に上げる |

**範囲の正本は次の表で決める。PR が該当する行を、すべて併合する**。
1つを選んで他を捨てることはしない（§2 の「複数種別にまたがる PR は重い方に合わせる」と同じ考え方で、
**範囲は広い方に合わせる**）。行 D が包括の受け皿なので、**どの PR も必ず1つ以上の行に該当する**。

| 行 | PR に含まれる変更 | 範囲の正本 | 依頼本文に添える文 |
|---|---|---|---|
| A | §1.2 の境界表を持つ設計文書（D04 以降の各文書）の追加・改訂 | **その文書の §1.2**（本書が決めること／後続に委ねること／前提から受け取ることの境界表）。複数の文書を改訂するなら**各文書の §1.2 をすべて** | 「対象範囲は §1.2 の表。表の外は対象外」 |
| B | §1.2 を持たない文書の改訂（決定記録 `docs/decisions/`、D01〜D03、全体計画書、本書、無人運転プロトコル、スキル、README など） | **PR 本文に置く範囲表**。変更した文書と箇所を1行ずつ挙げ、「表の外は対象外」と明記する | 「対象範囲は PR 本文の範囲表に挙げた箇所。表の外は対象外」 |
| C | 実装（`src/` とそのテスト） | **承認済みの設計文書のうち、その PR が実装する範囲**。PR 本文に対象の文書と節を挙げる | 「対象範囲は PR 本文に挙げた設計文書の節。範囲外の設計変更の提案は対象外」 |
| D | 骨格・ツール（`.github/workflows/`、`pyproject.toml`、`uv.lock`、品質ツール設定、`tools/`、`.gitignore`、ディレクトリ骨格、依存の更新）、**および A〜C のどれにも当たらない変更** | **PR 本文に置く範囲表**（行 B と同じ形式）。根拠となる決定記録・設計文書があれば併せて挙げる | 「対象範囲は PR 本文の範囲表に挙げた箇所。表の外は対象外」 |

行 B・D の範囲表は、§1.2 と同じ役割を果たす。**「何を決める PR か」と「何を決めない PR か」の両方を書く**。
片方しか書かないと、書いていない側の指摘が毎巡湧く。

併合の具体例:

- **実装を含む PR は、必ず行 C を範囲に含める**。同じ PR に設計文書の改訂が入っていても、
  行 A や行 B がそれを置き換えることはない。§6 のとおり仮置きの決定は設計文書の改訂として
  実装 PR に含めるため、**この組み合わせは通常起きる**。行 A だけを正本にすると、
  その文書が扱わない別の設計に属する実装への指摘を「表の外」として落とせてしまう。
- 実装に CI 設定や依存の更新が伴う PR は、**行 C と行 D の両方**を範囲に含める。
- §1.2 を持つ文書と持たない文書が混じる PR は、**各 §1.2 と PR 本文の範囲表の両方**を範囲に含める。

併合した結果は PR 本文に1か所へまとめて書き、依頼本文ではそこを指す。

範囲を伝えずに依頼すると、後続文書が決める事項への指摘が毎巡湧き、収束しない。


## 4. Codex review の運用

前提（人間が一度だけ設定する）: 対象リポジトリで Codex の code review を有効にし、
mention 運用（`@codex review` の投稿で起動）にしておく。

```
1. push → gh pr create --base main
2. gh pr comment <PR#> --body "@codex review"   （投稿時刻を UTC で控える）
   §3.1 の表で範囲の正本を選び、その一文を依頼本文に添える
3. uv run python tools/ops/codex_review_poll.py \
       --pr <PR#> --since <その時刻> --interval 240 --timeout 1200
4. 応答を分類する（§3.1 の3分類 → 対象内のものに §3 の P0 / P1 / P2）
5. 対象内の P0 と P1 を直し（傾向を読んで根本対処を先に入れる）、push して 2 へ戻る
6. 対象内の P0 が0件かつ P1 が0件の巡が出たら、そこで終了する
   （終了後に何かを push したら、その最終 head に対して 2 からやり直す。§4.1）
```

- **ポーリングは4分間隔**、1巡あたりの無応答の打ち切りは20分。

### 4.1 終了条件は巡数ではなく「重大な指摘が残っていないこと」【決定 2026-09-20】

人間の決定（2026-09-20）:
「Codex レビューは P1 が0件になるまでは続けてください。ただ繰り返すのではなく、
指摘の傾向を読み取り収束方向に向かうようにしてください。
ただし無理やり設計を捻じ曲げたりはせず、あるべきを常に考えるように。」

これを運用規則にすると次のようになる。

- **終了条件は「必ず直す指摘が残っていないこと」**である。
  レビュー対象範囲の中で、**設計違反など必ず直す最重大の指摘（P0）が0件、
  かつバグ・契約違反など必ず直す重大な指摘（P1）が0件**になった巡で終了する。
- **終了条件は「その巡が見たコミット」に対して成立する**。Codex は依頼時点の head を見るため、
  **0件の判定が指すのはその head であって PR ではない**。
  したがって**0件の巡の後に何かを push したら、終了条件は成立していない**。
  push したものが新たな P0 / P1 を持ち込んでいないことを、**最終 head に対して確かめ直す**必要がある。
  再依頼して 2 へ戻り、その最終 head で0件の巡が出るまで続ける（この巡も §4.4 の巡数に数える）。
  これは次の3つの場合すべてに当てはまる。
  1. 0件の巡に残った軽微な指摘（P2）を直して push した場合。
     **再依頼を増やしたくないなら P2 を直さず、見送る理由を PR に記録する**（§3）。どちらを取ってもよい。
  2. §5 の設計適合レビューの指摘を直して push した場合。
  3. §6 の仮置きの決定を設計文書の改訂として反映し、push した場合。
- **2つのレーンは、どちらも最終 head を見ていなければならない**。
  Codex（§4）と設計適合レビュー（§5）は別レーンであり、片方をやり直したらもう片方も古くなる。
  したがって**最終 head に変更が入るたびに、Codex と設計適合レビューの両方を通し直す**。
  実装 PR では次の形になり、**どちらのレーンも新たな修正を生まなくなった head が最終 head**である。

  ```
  Codex を0件まで回す → 設計適合レビュー → 指摘があれば直して push
    → 直したなら Codex へ戻る → 0件 → 設計適合レビューへ戻る → … → 両方が同じ head で変更を生まない
  ```

  この往復も §4.4 の巡数に数える。仮置きの決定（§6）を反映した場合も同じ往復に入る。
- **merge の可否を問えるのは、最終 head に対して0件の巡が出てからである**（§7）。
- **固定の巡数は置かない**。以前の「基本2巡・1巡目で0件なら1巡・最大2巡」は本改訂で廃止する。
  2巡で P1 が残っていても、そこで止めずに収束させる。

### 4.2 収束させる: 毎巡、指摘の傾向を読んでから直す

同じ直し方を繰り返すだけでは巡数が増えるだけで収束しない。2巡目以降は次の順で進める。

1. **傾向を1行で PR コメントに書く**。直前までの指摘が何に集中しているか（例: 「表の列と本文の説明の食い違い」「対象外の後続文書に属する事項」）を書いてから修正に入る。
2. **同種の指摘が繰り返しているなら、個別の修正より先に根本対処を入れる**。
   根本対処とは、同じ種類の指摘が次の巡で再発しないようにする文書上・実装上の手当てである
   （例: 値の正本を1か所に集約して他は参照にする、境界表に欠けていた行を足す、
   依頼本文で対象範囲を明示し直す、検査を1件足して不整合を機械で止める）。
3. そのうえで個別の指摘を直す。

### 4.3 設計を捻じ曲げない

- 指摘を消すことが目的ではない。**人間の決定・承認済みの設計文書・ADR と衝突する指摘は「不採用」**とし、
  衝突の理由を書いて残す（§3.1）。指摘に合わせて設計を曲げてはならない。
- 指摘が正しく、設計のほうに直すべき点があるなら、その場で決めずに
  **要決定として人間に上げる**（本書 §1「前提を silent に決めない」）。
- 対象外の指摘も同様に直さない。**担当があるなら**どの文書・どの段階かを書き、**担当が無いなら**
  （今回は変更しない既存仕様、別 PR で扱うコードなど）**対象外である理由**を書いて残す（§3.1 と同じ条件分岐）。
  架空の担当を割り当てない。

### 4.4 安全弁: 6巡で収束しなければ人間に渡す

- **6巡回しても対象内の P0 / P1 が0件にならない場合は止める**。報告には
  **(a) 指摘の傾向、(b) 収束しない理由の仮説**を添える。
  人間が「続行」「レビュー対象範囲を明記し直す」「別工程（紙上トレースなど）に切り替える」
  のいずれかを選ぶ。巡数を機械的に打ち切るためではなく、**同じ所を回り続けている兆候を人間に渡すため**の上限である。
- **人間が「続行」または「範囲を明記し直す」を選んだら、巡数を 0 に戻し、同じ6巡の安全弁をもう一度適用する**。
  6巡目まで回したらまた止まり、**続行するたびに人間の明示が要る**。
  カウンタを6のまま続けると次の1巡で即停止し、安全弁を外すと無期限に回るため、
  **「0に戻す・上限は同じ6・延長には毎回人間の明示が要る」**の3点を規則とする。
  何度続行したかは PR コメントに残す（例: 「続行2回目、通算13巡目」）。
- Codex が利用上限（rate limit）で応答を返した巡は、**巡数に数えない**。
  30 分待って `@codex review` を再投稿する。再投稿は**最大8回**まで。
- **8回の再投稿を使い切っても利用上限のままなら、そこで作業を止める**。
  終了条件にも6巡の安全弁にも到達できないため、**「失敗」ではなく「要決定」として報告する**
  （レビューが尽きていないので merge は問わない。§7）。報告には
  **(a) 対象内の P0 / P1 の残件数、(b) 最後の利用上限応答の時刻**を書く。
  (a) は**応答のあった最後の巡の件数**であり、**どの head に対する件数かを併記する**
  （例: 「P1 が1件、head `abc1234` 時点」）。
  **一度も応答のある巡が無かった場合は、件数を「未確認」と書く**。
  レビューを受けていない状態を0件と記録しない。
  進捗ファイル（無人運転プロトコル §4）の「人間待ち」へ1行で残す。
  人間が取る次の行動は、**レビューを完了させる方法に限る**。例: 利用枠の回復後に再開を指示する、
  対象範囲を絞って PR を小さく分割し直す、Codex の設定（環境・枠）を変える。
  **レビューを飛ばして merge する選択肢は置かない**（§2 でレビューは必須、§7 で merge 前提は1本）。
  作業役は勝手に待ち続けず、次の作業へも進まない。

### 4.5 ループは承認停止なしで自走する

- この push → PR → 依頼 → ポーリング → 分類 → 修正 → 再依頼のループは、**承認停止なしで自走する**。
  ループの途中で承認を求めて止まらない。
- **止まるのは次の2つの場合だけである**。

  | # | 止まる場面 | 人間に問うこと | その後 |
  |---|---|---|---|
  | 1 | **merge の前**（§4.1 の終了条件に最終 head で達した） | merge の可否 | 人間が merge する |
  | 2 | **§4.4 の安全弁に当たった**（6巡で未収束、または利用上限の再投稿8回を使い切った） | **merge ではなく**、§4.4 が定める収束の方法 | 人間の選択を受けてループへ戻る |

- **2 は自走の例外である**。安全弁に当たった作業役は**自走を続けず、そこで止まって人間の選択を待つ**。
  **自分の判断で巡数を 0 に戻して続行してはならない**（巡数を戻せるのは人間が「続行」または
  「範囲の明記し直し」を選んだときだけ。§4.4）。待たずに回し続けると安全弁が働かない。
- 止まっているあいだ、作業役は次の作業へも進まない。進捗ファイル（無人運転プロトコル §4）の
  「人間待ち」に1行残す。

poller の終了コード:

| exit | 意味 | 次の行動 |
|---|---|---|
| 0 | 応答あり（JSON で `status: responded`） | §3.1 で分類し、対象内の P0 / P1 を修正 |
| 1 | `gh` の失敗（未認証、PR 不在など） | 原因を報告して停止（推測で進めない） |
| 2 | timeout（`status: timeout`） | 「Codex 未応答（GitHub App 未設定の可能性）」として報告し、それ以上待たない |


## 5. Claude による設計適合レビュー（別レーン）

Codex は差分の欠陥を見る。Claude は**設計文書との適合**を見る。両者は別レーンであり、
Codex が clean でも設計適合レビューは省略しない。

- **実装 PR では、Codex が §4.1 の終了条件に達した後にこのレビューを行う**。
  担当は実装したセッションとは別のセッション（既定では Sonnet の子セッション）で、
  **read-only**（コードを書き換えず、指摘を返すだけ）とする。
  指摘は §3 の P0 / P1 / P2 で報告し、実装したセッションが修正する。
- 設計文書 PR で見るものは、§3.1 の行によって変わる。
  - **行 A**（§1.2 を持つ文書）: 対象文書の **§1.2 の境界表そのもの**が上位文書と整合しているかを見る。
  - **行 B・D**（§1.2 を持たない文書、骨格・ツール）: **PR 本文の範囲表**を §1.2 の代わりに見る。
    表に挙げた「決めること」が承認済みの上位文書・決定記録と矛盾しないか、
    「決めないこと」に回した事項の担当（どの文書・どの段階）が実在するかを照合する。
  §1.2 が無いことを理由に設計適合レビューを飛ばさない。**どの PR にも見るべき正本がある**（§3.1）。

確認する観点:

- 承認済みの設計（全体計画書・上位設計書・ADR）の範囲内に収まっているか。
  承認外の設計判断を silent に行っていないか。
- 依存規則（`import-linter` の契約）と層の責務に反していないか。
- 未確定事項を「仮置き」として明示しているか。
- 段階の完了条件（全体計画書 §8.2）を満たしているか。

## 6. 仮置き事項（設計文書に無い振る舞いを実装が決めたもの）

実装中に、承認済みの設計文書が定めていない振る舞いを決めざるを得なかった箇所は
「**仮置き**」と呼び、その場で確定させない（§1「前提を silent に決めない」）。

- **PR 本文に番号付きで列挙する**。1件ごとに **(a) 何が未定義か、(b) 現在の実装が何をしているか、
  (c) 取り得る選択肢**を書く。
- **merge の前に、人間が1件ずつ選択式で決める**。レビューの巡数とは独立した手順で、
  Codex が clean でも省略しない。
- 決まった内容は**設計文書の改訂として同じ PR に含める**。
  決定を PR コメントだけに残さない（設計はドキュメントが正本・§1）。

## 7. merge

merge は人間が判断する。Claude と Codex は「レビューが尽きた」ことを報告するまでで、
自分で merge しない。報告には、実施した巡数、各巡の件数、残った P2、仮置きした事項を含める。

**merge の可否を問えるのは、次の3つをすべて満たす PR だけである。**

| # | 前提 | 根拠 |
|---|---|---|
| 1 | **未解消の仮置き事項が0件**である。PR 本文に挙げた仮置きを人間が1件ずつ決め、決定を**設計文書の改訂として同じ PR に反映して push し終えている** | §6 |
| 2 | **独立レビュー（Codex）が、その最終 head に対して §4.1 の終了条件に達している**（対象内の P0=0 かつ P1=0） | §4.1 |
| 3 | **設計適合レビューも、同じ最終 head で新たな修正を生まない** | §5 |

**順序が重要である。仮置きの決定は merge の質問より先に来る**。仮置きを添えたまま merge の可否を問うと、
**未決定の振る舞いを含む古い head に merge の承認が出てから設計文書を変える**ことになり、
承認されたものと merge されるものが食い違う。1 → 2・3 → merge の質問、の順を守る。

Codex review はすべての PR で必須なので（§2）、**レビューを省略して merge へ進む経路は無い**。

§4.4 の安全弁に当たって止めた PR は、まだレビューが尽きていないため、**merge の可否を問わない**。
この場合は「要決定」として、指摘の傾向と収束しない理由の仮説を添え、
**人間に「続行」「レビュー対象範囲の明記し直し」「別工程（紙上トレースなど）への切り替え」のどれを取るかだけ**を尋ねる。
人間の選択に従って収束させ、終了条件に達してから改めて merge を問う。
収束方法が決まる前に merge を問うと、安全弁の分岐が働かない。
