## 1. 原則

- **レビューと merge 判断を分ける**。レビューは欠陥と設計違反を見つける作業であり、
  merge するかどうかの判断は含まない。**merge 判断は常に人間が行う**（CLAUDE.md）。
- **設計はドキュメントが正本**。実装 PR のレビューは、コードが `docs/design/` と
  `docs/decisions/` の承認済み内容に合致しているかを基準にする。
  設計そのものへの異論は PR ではなく設計文書へ差し戻す。
- **前提を silent に決めない**。レビュー中に未確定の設計判断が必要になった場合は、
  その場で決めずに PR 本文へ「仮置き」として明示し、人間の判断を仰ぐ。

## 2. PR 種別と Codex review の要否

**Codex review はすべての PR 種別で必須である**【決定 2026-09-23】。

| 種別 | 内容 | Codex review |
|---|---|---|
| 設計文書のみ | `docs/design/`、`docs/decisions/` の追加・更新のみ | **必須** |
| 骨格・ツール | ディレクトリ骨格、ビルド/CI 設定、品質ツール設定、運用スクリプト | **必須** |
| 実装 | `src/odyssey_fx/` の振る舞いを持つコード、およびそのテスト | **必須** |

以前は「設計文書のみ」を任意としていたが、**運用（PR #14〜#20）では設計文書の PR にも毎回実施していた**ため、
規定を運用に合わせた。例外を置かないことで、**レビューを省略する経路そのものが無くなり**、
§7 の merge 前提が1本になる。

1つの PR が複数種別にまたがる場合は、重い方（実装 > 骨格・ツール > 文書）に合わせる。
要否は変わらない（どれも必須）が、**レビュー対象範囲の決め方**は §3.1 の表で種別ごとに変わる。

## 3. 指摘の分類

| 優先度 | 内容 | 扱い |
|---|---|---|
| **P0** | 設計違反（承認済み設計・ADR・依存規則に反する）、データ破壊（原データの上書き、holdout の誤読）、先読み（判断時点で利用できない情報の参照）、決定論の破壊 | 必ず修正してから次へ進む |
| **P1** | バグ、契約違反（型・状態機械・不変条件の破り）、テストが検査すべき対象を検査していない | 必ず修正してから次へ進む |
| **P2** | 改善提案、命名、スタイル、将来の整理 | 修正するか、見送る理由を PR に記録する |

指摘に優先度タグが付いていない場合は、上の定義に照らして自分で分類し、
その分類を PR コメントに残す。

### 3.1 レビュー対象範囲による3分類【決定 2026-09-20、PR #14〜#20 で確立】

優先度（P0/P1/P2）を付ける前に、**その指摘が今回の PR のレビュー対象範囲に入るか**を先に判定する。
判定は次の3つのいずれかになり、**いずれも PR コメントに残す**。

| 分類 | 内容 | 扱い |
|---|---|---|
| **対象内** | 今回の PR が決める範囲の中の指摘 | §3 の表で P0 / P1 / P2 を付ける。P0 と P1 は必ず直す |
| **対象外（今回の範囲の外）** | 今回の PR が決める範囲の外への指摘。**担当がある場合と、無い場合の両方を含む** | 直さない。**担当があるなら**どの文書・どの段階かを書く。**担当が無いなら**（今回は変更しない既存仕様、別 PR で扱うコードなど）**対象外である理由**を書く。架空の担当を割り当てない |
| **不採用** | 人間の決定・承認済みの設計と衝突する指摘 | 直さない。**なぜ衝突するかの理由を書き**、設計を変える価値があるなら要決定として人間に上げる |

**範囲の正本は次の表で決める。PR が該当する行を、すべて併合する**。
1つを選んで他を捨てることはしない（§2 の「複数種別にまたがる PR は重い方に合わせる」と同じ考え方で、
**範囲は広い方に合わせる**）。行 D が包括の受け皿なので、**どの PR も必ず1つ以上の行に該当する**。

| 行 | PR に含まれる変更 | 範囲の正本 | 依頼本文に添える文 |
|---|---|---|---|
| A | §1.2 の境界表を持つ設計文書（D04 以降の各文書）の追加・改訂 | **その文書の §1.2**（本書が決めること／後続に委ねること／前提から受け取ることの境界表）。複数の文書を改訂するなら**各文書の §1.2 をすべて** | 「対象範囲は §1.2 の表。表の外は対象外」 |
| B | §1.2 を持たない文書の改訂（決定記録 `docs/decisions/`、D01〜D03、全体計画書、本書、無人運転プロトコル、スキル、README など） | **PR 本文に置く範囲表**。変更した文書と箇所を1行ずつ挙げ、「表の外は対象外」と明記する | 「対象範囲は PR 本文の範囲表に挙げた箇所。表の外は対象外」 |
| C | 実装（`src/` とそのテスト） | **承認済みの設計文書のうち、その PR が実装する範囲**。PR 本文に対象の文書と節を挙げる | 「対象範囲は PR 本文に挙げた設計文書の節。範囲外の設計変更の提案は対象外」 |
| D | 骨格・ツール（`.github/workflows/`、`pyproject.toml`、`uv.lock`、品質ツール設定、`tools/`、`.gitignore`、ディレクトリ骨格、依存の更新）、**および A〜C のどれにも当たらない変更** | **PR 本文に置く範囲表**（行 B と同じ形式）。根拠となる決定記録・設計文書があれば併せて挙げる | 「対象範囲は PR 本文の範囲表に挙げた箇所。表の外は対象外」 |

行 B・D の範囲表は、§1.2 と同じ役割を果たす。**「何を決める PR か」と「何を決めない PR か」の両方を書く**。
片方しか書かないと、書いていない側の指摘が毎巡湧く。

併合の具体例:

- **実装を含む PR は、必ず行 C を範囲に含める**。同じ PR に設計文書の改訂が入っていても、
  行 A や行 B がそれを置き換えることはない。§6 のとおり仮置きの決定は設計文書の改訂として
  実装 PR に含めるため、**この組み合わせは通常起きる**。行 A だけを正本にすると、
  その文書が扱わない別の設計に属する実装への指摘を「表の外」として落とせてしまう。
- 実装に CI 設定や依存の更新が伴う PR は、**行 C と行 D の両方**を範囲に含める。
- §1.2 を持つ文書と持たない文書が混じる PR は、**各 §1.2 と PR 本文の範囲表の両方**を範囲に含める。

併合した結果は PR 本文に1か所へまとめて書き、依頼本文ではそこを指す。

範囲を伝えずに依頼すると、後続文書が決める事項への指摘が毎巡湧き、収束しない。


## 4. Codex review の運用

前提（人間が一度だけ設定する）: 対象リポジトリで Codex の code review を有効にし、
mention 運用（`@codex review` の投稿で起動）にしておく。

**本節の正本は §4.6 の状態×遷移表である。**
ループが取りうる状態と、そこで起きうる契機の組み合わせは、すべて §4.6 の表の1マスに対応する。
§4.1〜§4.5 は、その表がそう定まっている**理由**と、よく使う部分の**要約**であり、規則そのものではない。
**表と食い違う記述があれば §4.6 が優先する**。表に無い規則を §4.1〜§4.5 に書き足さない。

手順の概略（各手順が §4.6 のどの状態に当たるかを右に示す）:

```
1. push → gh pr create --base main
2. gh pr comment <PR#> --body "@codex review"   （投稿時刻を UTC で控える）   → 状態1 へ
   §3.1 の表で範囲の正本を選び、その一文を依頼本文に添える
3. uv run python tools/ops/codex_review_poll.py \
       --pr <PR#> --since <その時刻> --interval 240 --timeout 1200            → 状態1
4. 応答を分類する（§3.1 の3分類 → 対象内のものに §3 の P0 / P1 / P2）        → 契機A〜F
5. 対象内の P0 と P1 を直し（傾向を読んで根本対処を先に入れる）、push して 2 へ → 状態2 → 状態1
6. 対象内の P0 が0件かつ P1 が0件の巡が出たら Codex のループを終える          → 状態4
   （そのまま §5 の設計適合レビューへ進み、§6 の仮置き → §7 の merge の質問）→ 状態9・状態5
```

- **ポーリングは4分間隔**、1巡あたりの無応答の打ち切りは20分。

### 4.1 終了条件は巡数ではなく「重大な指摘が残っていないこと」【決定 2026-09-20】

人間の決定（2026-09-20）:
「Codex レビューは P1 が0件になるまでは続けてください。ただ繰り返すのではなく、
指摘の傾向を読み取り収束方向に向かうようにしてください。
ただし無理やり設計を捻じ曲げたりはせず、あるべきを常に考えるように。」

- **終了条件は「必ず直す指摘が残っていないこと」**である。
  レビュー対象範囲の中で、**設計違反など必ず直す最重大の指摘（P0）が0件、
  かつバグ・契約違反など必ず直す重大な指摘（P1）が0件**になった巡で終了する（§4.6 契機A・C・D → 状態4）。
- **固定の巡数は置かない**。以前の「基本2巡・1巡目で0件なら1巡・最大2巡」は本改訂で廃止する。
- **終了条件は「その巡が見たコミット」と「その巡に伝えた範囲」に対して成立する**。
  Codex は依頼時点の head と、依頼本文に添えた範囲しか見ない。
  したがって**レビューの入力が変われば終了条件は失効する**（§4.6 規則4）。
  入力は2つあり、§4.6 の契機G（push）と契機H（レビュー対象範囲の変更）がそれぞれに対応する。

  **契機H を見落としやすい**。行 B・C・D が使う PR 本文の記述（範囲表、対象の設計文書と節の一覧）は
  版管理の外にあるので、**head が変わらないまま範囲だけが変わる**。その状態で前の巡の0件を根拠に merge を問うと、
  **Codex が一度も見ていない範囲について「指摘なし」と主張する**ことになる。
  だから §4.6 では、状態4（終了条件成立）の契機H も状態1 へ戻る。
- **応答が最新の入力を見ていないことがある**。Codex が古い head を見ていた場合（PR #21 の10・11巡目で実際に起きた）と、
  依頼した後に push や範囲の変更が入った場合の両方がこれに当たる。
  **その巡は数え、指摘は分類して直すが、終了条件は成立しない**（§4.6 規則5）。
  0件の応答であっても状態4 へは進まず、最新 head・現在の範囲で依頼し直す。
  **毎巡、応答の `Reviewed commit` と現在の head を突き合わせて、どちらを見た応答かを PR コメントに書く**。
- **2つのレーンは、どちらも最終 head を見ていなければならない**。
  Codex（§4）と設計適合レビュー（§5）は別レーンであり、片方をやり直したらもう片方も古くなる。
  §4.6 では状態4 が両方を含み、そこから push（契機G）が入れば状態1 へ戻る。
  **どちらのレーンも新たな修正を生まなくなった head が最終 head**である。
- **merge の可否を問えるのは、最終 head に対して0件の巡が出てからである**（§7、§4.6 状態5）。

### 4.2 収束させる: 毎巡、指摘の傾向を読んでから直す

同じ直し方を繰り返すだけでは巡数が増えるだけで収束しない。状態2（分類・修正中）では次の順で進める。

1. **傾向を1行で PR コメントに書く**。直前までの指摘が何に集中しているか（例: 「表の列と本文の説明の食い違い」「対象外の後続文書に属する事項」）を書いてから修正に入る。
2. **同種の指摘が繰り返しているなら、個別の修正より先に根本対処を入れる**。
   根本対処とは、同じ種類の指摘が次の巡で再発しないようにする文書上・実装上の手当てである
   （例: 値の正本を1か所に集約して他は参照にする、**状態と遷移を表にして空欄をゼロにする**、
   依頼本文で対象範囲を明示し直す、検査を1件足して不整合を機械で止める）。
3. そのうえで個別の指摘を直す。

§4.6 の表そのものが、この根本対処を本書に適用した結果である。
**「この状態でこれが起きたらどうなるか」が決まっていない組み合わせが残っていたことが、
PR #21 で指摘が15巡続いた原因**だった。

### 4.3 設計を捻じ曲げない

- 指摘を消すことが目的ではない。**人間の決定・承認済みの設計文書・ADR と衝突する指摘は「不採用」**とし、
  衝突の理由を書いて残す（§3.1）。指摘に合わせて設計を曲げてはならない。
- 指摘が正しく、設計のほうに直すべき点があるなら、その場で決めずに
  **要決定として人間に上げる**（本書 §1「前提を silent に決めない」）。§4.6 の状態8 がこの停止である。
  **設計判断が必要かどうかは優先度では決まらない**。必ず直す指摘（P0・P1）だけでなく、
  **不採用にした指摘**や**軽微な指摘（P2）**からも立つ（§4.6.5 手順4）。
  **どちらのレーンでも同じである**。Codex の応答でも §5 の設計適合レビューの結果でも、
  設計を変える判断が要るなら状態8 へ行く（§4.6 の状態4 の契機J）。
  片方のレーンだけ「対象内 P0 / P1 だから直す」と進めると、そのレーンでだけ設計判断を silent に行うことになる。
- **人間が「設計を維持する」と答えることも正当な回答である**。そのときは設計文書を変えず、
  指摘を「不採用」として理由とともに記録してループへ戻る（§4.6 の状態8 の契機I）。
  **人間に問う選択肢には、必ず「承認済みの設計を維持する」を含める**。
  設計を変える選択肢しか置かないと、作業役が**変更を作り出さないと停止から抜けられなくなる**。
- 対象外の指摘も同様に直さない。**担当があるなら**どの文書・どの段階かを書き、**担当が無いなら**
  （今回は変更しない既存仕様、別 PR で扱うコードなど）**対象外である理由**を書いて残す（§3.1 と同じ条件分岐）。
  架空の担当を割り当てない。

### 4.4 安全弁: 6巡で収束しなければ人間に渡す

- **6巡回しても、最新の入力に対して対象内の P0 / P1 が0件にならない場合は止める**（§4.6 状態6）。
  **対象内 P0 / P1 が残っている場合だけでなく、6巡目まで応答が古い入力しか見ておらず
  「最新 head・現在の範囲に対する0件」が得られていない場合も同じ**（§4.6.5 手順5 の6行目）。報告には
  **(a) 指摘の傾向、(b) 収束しない理由の仮説**を添える。
  人間が「続行」「レビュー対象範囲を明記し直す」「別工程（紙上トレースなど）に切り替える」
  のいずれかを選ぶ。巡数を機械的に打ち切るためではなく、**同じ所を回り続けている兆候を人間に渡すため**の上限である。
- **どの選択肢を選んだ場合でも、その指示に従った対応を終えて Codex に戻る時点で巡数を 0 に戻し、
  同じ6巡の安全弁をもう一度適用する**（§4.6 規則2）。「別工程」を選んで工程を終えた場合も同じである。
  §7 は最終的に Codex の0件の巡を必須にしているため、別工程の後も必ず Codex へ戻る。
  ここで 0 に戻さないと、**カウンタが6のまま戻って次の1巡で即座に安全弁へ落ちる**。
  6巡目まで回したらまた止まるので、**延長するたびに人間の明示が要る**。
  何度目かは PR コメントに残す（例: 「続行2回目、通算13巡目」「別工程の後、数え直し1回目」）。
- **巡数と再投稿回数がどの場面で増え、どの場面で 0 に戻るかは §4.6 規則1〜3 が唯一の正本である**。
  作業役が自分の判断で 0 に戻すことはできない（§4.5）。
- **0件の巡が出たら、その時点で巡数は 0 に戻る**（§4.6 規則2(b)）。§5 の設計適合レビューの修正や
  §6 の仮置きの決定を反映して push すると終了条件は失効するが、**そのときの数え直しは新しい6巡である**。
  0件に達したことは収束した事実であり、その後の変更はそれとは別の、通常はもっと小さい作業だからである。
  カウンタを6のまま続けると次の1巡で即座に人間を呼ぶことになり、安全弁を外すと再検証が無期限に回る。
  再検証が6巡で収束しなければ、通常どおり安全弁に当たって人間へ渡す。
- Codex が利用上限（rate limit）で応答を返した巡は、**巡数に数えない**（§4.6 規則1）。
  30 分待って `@codex review` を再投稿する（§4.6 状態3）。再投稿は**最大8回**まで。
- **この8回は「連続する1つの利用上限の事象」についての上限である**。
  レビューの応答が1回でも返れば、その事象は終わったので再投稿回数も 0 に戻る（§4.6 規則3）。
  人間の指示で再開したときも、巡数と同じく再投稿の回数を 0 に戻す。
  回数を持ち越すと、再開した直後にもう1回上限に当たっただけで要決定へ逆戻りし、
  「枠の回復後に再開」という選択肢が機能しない。何度目の再開かは PR コメントに残す。
- **8回の再投稿を使い切っても利用上限のままなら、そこで作業を止める**（§4.6 状態7）。
  終了条件にも6巡の安全弁にも到達できないため、**「失敗」ではなく「要決定」として報告する**
  （レビューが尽きていないので merge は問わない。§7）。報告には
  **(a) 対象内の P0 / P1 の残件数、(b) 最後の利用上限応答の時刻**を書く。
  (a) は**応答のあった最後の巡の件数**であり、**どの head に対する件数かを併記する**
  （例: 「P1 が1件、head `abc1234` 時点」）。
  **一度も応答のある巡が無かった場合は、件数を「未確認」と書く**。
  レビューを受けていない状態を0件と記録しない。
  進捗ファイル（無人運転プロトコル §4）の「人間待ち」へ1行で残す。
  人間が取る次の行動は、**レビューを完了させる方法に限る**（選択肢は §4.6.1 の状態7 の行）。
  **レビューを飛ばして merge する選択肢は置かない**（§2 でレビューは必須、§7 で merge 前提は1本）。
  作業役は勝手に待ち続けず、次の作業へも進まない。

### 4.5 ループは承認停止なしで自走する

- この push → PR → 依頼 → ポーリング → 分類 → 修正 → 再依頼のループは、**承認停止なしで自走する**。
  ループの途中で承認を求めて止まらない。
- **止まるのは §4.6 の状態5〜状態11 の7つだけである**。§4.6.1 の表が、それぞれについて
  **何を人間に問うか・何を添えるか**を定め、§4.6.3 の表がその後どこへ遷移するかを定めている。
  7つは2種類に分かれる。

  | 種類 | 状態 | 性質 |
  |---|---|---|
  | **正常なレビューの流れの中の停止**（人間の判断を待つ） | 状態5（merge の可否）、状態6（安全弁・6巡で未収束）、状態7（安全弁・再投稿8回）、状態8（設計判断）、状態9（仮置きの決定）、状態10（同時成立） | 人間に問い、回答を受けてループへ戻る |
  | **流れが回らなくなったことによる停止** | 状態11（運用上の異常。poller の exit 1 / exit 2） | 問うのではなく**原因を報告**する（推測で進めない） |

- **状態8 と状態9 は「前提を silent に決めない」（§1）の実装である**。
  指摘を消すために承認済みの設計を曲げること（§4.3）も、仮置きを自分で確定させること（§6）も、
  どちらも自走してはならない。**止まって問うことが正しい**。
  ここで止まるのは自走の違反ではなく、自走が守るべき境界そのものである。
  **人間の判断を待つ停止は、§1 の原則が要求するもの（merge・安全弁・設計判断・仮置き）に尽きる**。
  新しい停止場面を足したくなったら、まず §1 のどれに当たるかを確かめ、§4.6 の表に状態として足す。
- **状態6・状態7 は自走の例外である**。安全弁に当たった作業役は**自走を続けず、そこで止まって人間の選択を待つ**。
  **自分の判断で巡数を 0 に戻して続行してはならない**（§4.6 規則2）。
  待たずに回し続けると安全弁が働かない。
- **複数の停止場面が同じ巡で同時に成立したら、状態10 として1通の「要決定」にまとめて人間へ送る**。
  典型は**6巡目の応答が、設計判断（状態8 の契機）と、それとは別の対象内 P0 / P1 の両方を含む**場合である。
  **片方を先に処理して戻ってはならない**。設計判断だけを処理して戻ると**カウンタが6のままで即座に安全弁へ落ち**、
  安全弁だけを処理して戻ると**設計判断が未解決のまま**になる。手順は §4.6 規則6 と状態10 の行。
- 止まっているあいだ、作業役は次の作業へも進まない。進捗ファイル（無人運転プロトコル §4）の
  「人間待ち」に1行残す。

poller の終了コード:

| exit | 意味 | 次の行動 |
|---|---|---|
| 0 | 応答あり（JSON で `status: responded`） | §3.1 で分類する（§4.6 契機A〜E のいずれかになる）。対象内の P0 / P1 を修正 |
| 1 | `gh` の失敗（未認証、PR 不在など） | §4.6 契機F。原因を報告して状態11 で停止（推測で進めない） |
| 2 | timeout（`status: timeout`） | §4.6 契機F。「Codex 未応答（GitHub App 未設定の可能性）」として報告し、それ以上待たない |

### 4.6 ループの状態と遷移【本節がループの正本。2026-09-23 に追加】

§4.1〜§4.5 を指摘のたびに1件ずつ書き足していたあいだ、**「この状態でこれが起きたらどうなるか」が
決まっていない組み合わせ（空欄）が残り続け、PR #21 の指摘が15巡収束しなかった**。
そこで、ループが取りうる**状態**と、そこで起きうる**契機**を列挙し、
**すべての組み合わせに答えを書いた表**を本節に置く。**空欄はゼロである**。
起きない組み合わせにも「到達しない（理由）」を書いてあるので、
「書いていないから未定義」という箇所は残らない。

規則を足すときは、**まず本節の表を直し、そのあとで §4.1〜§4.5・§7 の説明を表に合わせる**。
逆の順で直すと、また表に空欄が生まれる。

#### 4.6.2 契機の定義

| 契機 | 内容 |
|---|---|
| A | **対象内0件の応答**（対象内の P0・P1・P2 がいずれも0件で、対象外・不採用も無い） |
| B | **対象内に P0 または P1 を含む応答** |
| C | **対象内が P2 のみの応答**（対象内 P0=0 かつ P1=0） |
| D | **対象外・不採用のみの応答**（対象内は0件） |
| E | **利用上限（rate limit）の応答** |
| F | **未応答**（poller exit 2 = 20分無応答）または **`gh` の失敗**（exit 1） |
| G | **push**（修正・決定の反映で head が変わった） |
| H | **レビュー対象範囲の変更**（行 B・D の範囲表、行 C の対象の設計文書と節の一覧、行 A の参照先 §1.2 のいずれかが変わった。§3.1） |
| I | **人間の回答が返る**（続行 / 範囲の明記し直し / 別工程 / 枠の回復後に再開 / PR の分割 / 設定変更 / 設計判断 / 仮置きの決定 / merge の可否） |
| J | **設計適合レビュー（§5）の結果が出る** |
| K | **30分の待ちが明ける** |

契機A・C・D は**どれも終了条件を満たす**（対象内 P0=0 かつ P1=0）。
その後に行う動作（P2 の扱い、対象外・不採用の理由の記録）が違うので列を分けてある。
**1つの応答が契機C と契機D の両方に当てはまることがある**（対象内 P2 と対象外の指摘が混ざる場合）。
3つの列はいずれも状態4 へ向かうので競合せず、**両方の動作を行う**。
契機B が1件でも含まれていれば、応答全体は契機B として扱う。

状態10（停止場面の同時成立）に**実際に至る組み合わせは、状態6（安全弁）と状態8（設計判断）だけ**である。
状態7 は契機E（利用上限）から立ち、利用上限の応答は指摘を含まないので設計判断とは同時に立たない。
状態9 は契機A・C・D（対象内0件）から立ち、状態8 の前提（対象内に P0 / P1 を含む）と両立しない。
規則そのものは「2つ以上の人間待ちが同時に立ったら状態10」と一般に書いてある（規則6）。

#### 4.6.5 応答が届いたときの判定手順（契機A〜D で共通）

状態1 の契機A・B・C・D は**同じ判定を通る**。4つのマスに同じ手順を書き写すと必ず食い違うので、
**判定はここ1か所に置き、4つのマスはここを指す**。契機E（利用上限）と契機F（未応答）はレビューではないので、
この手順を通らず、状態1 の該当するマスがそのまま答えになる。

| 手順 | 内容 |
|---|---|
| 1 | **応答が見た入力を確かめる**。応答の `Reviewed commit` が現在の head と一致し、依頼本文に添えた範囲が現在のレビュー対象範囲と同じなら「**最新**」、どちらかが違えば「**古い**」。判定結果を PR コメントに書く（規則5） |
| 2 | **n:=n+1、r:=0**（規則1・規則3）。**古い入力への応答でも数える** |
| 3 | **§3.1 の3分類**（対象内 / 対象外 / 不採用）を行い、**対象内のものだけ**に §3 の優先度（P0 / P1 / P2）を付ける |
| 4 | **設計判断が必要かを判定する**。承認済みの設計・ADR・人間の決定を変える価値がある指摘があるかどうかで決まり、**優先度では決まらない**。対象内の P0・P1 だけでなく、**不採用にした指摘**（§3.1「設計を変える価値があるなら要決定として人間に上げる」）と**対象内の P2** も対象になる |

| 7 | 下の表を**上から順に**当てはめ、最初に条件が合った行の状態へ移る |

| 順 | 条件 | 次の状態と動作 |
|---|---|---|

| 3 | 設計判断は不要 かつ 修正を生む指摘あり かつ n≦5 | **状態2**。傾向を1行書き、根本対処を先に入れてから直す |
| 4 | 設計判断は不要 かつ 修正を生む指摘あり かつ n=6 | **状態6**（安全弁） |
| 5 | 設計判断は不要 かつ 修正を生む指摘なし かつ 手順1 が「**古い**」 かつ n≦5 | **状態1 のまま**。最新 head・現在の範囲で再依頼する。**終了条件は成立しない**（規則4・規則5） |

| 7 | 設計判断は不要 かつ 修正を生む指摘なし かつ 手順1 が「**最新**」 | **状態4**。終了条件が成立（n・r は手順6 で 0 になっている）。n=6 でもここは安全弁ではなく終了である |

7行で条件は尽きている（設計判断の要否2通り × 修正を生む指摘の有無2通り × 入力の新旧2通り × n の位置2通り = 16通りを、

**手順6 の効果**: 最新の入力への応答で対象内 P0 / P1 が0件なら、この表に入る時点で n=0 になっている。
したがって**1行目・4行目・6行目（n=6 の行）には当たらず、安全弁は発動しない**。
0件に達したうえで残った P2 を直すときは3行目（状態2）、設計判断が要るときは2行目（状態8）へ進み、
どちらも**新しい6巡**として数え直す。これは §4.4 の「0件の巡が出たら巡数は 0 に戻り、
その後の再検証は新しい6巡である」と同じ規則である。


## 5. Claude による設計適合レビュー（別レーン）

Codex は差分の欠陥を見る。Claude は**設計文書との適合**を見る。両者は別レーンであり、
Codex が clean でも設計適合レビューは省略しない。

- **どの PR でも、Codex が §4.1 の終了条件に達した後にこのレビューを行う**（§4.6 の状態4。
  終了条件の成立と設計適合レビューは1つの状態にまとめてあり、承認停止を置かずに続けて行う）。
  担当は実装したセッションとは別のセッション（既定では Sonnet の子セッション）で、
  **read-only**（コードを書き換えず、指摘を返すだけ）とする。
  **指摘の分類は §4 の Codex 応答と同じ手順による**。まず §3.1 の3分類（対象内 / 対象外 / 不採用）を行い、
  **対象内のものだけ**に §3 の P0 / P1 / P2 を付けて報告する。修正は実装したセッションが行う。
  対象外・不採用に優先度を付けない。付けると、**対象外の指摘が必須修正として扱われ、
  レビューのたびに範囲が広がって収束しなくなる**（Codex 側と同じ理由。§3.1）。
  **レビューの主体が変わっても、対象範囲と分類の規則は変わらない**。
  **このレビューが push を生むのは、修正を生む指摘があるときだけである**。
  対象内の P0・P1 と、直すことにした対象内 P2 がそれに当たる。
  対象外・不採用の指摘と、見送る P2 は**理由を記録するだけで、修正も push もしない**（§4.6 状態4 の契機J）。
  ここを「指摘が1件でもあれば直す」にすると、対象外の指摘を直すことで**対象範囲が広がり収束しなくなる**。
  **修正の前に、設計判断が要るかを §4.6.5 手順4 と同じ基準で判定する**。要るなら直さずに状態8 で人間に問う（§4.3）。
  この判定を飛ばすと、**設計適合レーンでだけ承認済みの設計が silent に変わる**。
- **§3.1 の表（§1.2 または PR 本文の範囲表）は、見る対象を特定するためのものであって、見る対象そのものではない。**
  表は「どこを変えたか」「何を決める PR か」を列挙するだけで、**変更後に実際に書かれた規則や値を含まない**。
  表だけを照合すると、たとえば範囲表に「再試行の規則を変更」と正しく書いてあっても、
  **変更後の再試行回数が決定記録と矛盾している**ことを見逃す。
  したがって次の2段で見る。

  | 段 | 見るもの |
  |---|---|
  | 1 | **表を使って対象を特定する**。行 A なら対象文書の §1.2、行 B・D なら PR 本文の範囲表、行 C なら PR 本文に挙げた設計文書の節 |
  | 2 | **特定した対象の、変更内容そのもの**を上位文書・決定記録・承認済み設計文書と照合する。差分に現れた規則・値・語彙を1件ずつ見る |

  表そのものの整合も段1 で併せて見る（行 A なら §1.2 の境界が上位文書と合っているか、
  行 B・D なら「決めないこと」に回した事項の担当が実在するか）。
  §1.2 が無いことを理由に設計適合レビューを飛ばさない。**どの PR にも見るべき正本がある**（§3.1）。

確認する観点:

- 承認済みの設計（全体計画書・上位設計書・ADR）の範囲内に収まっているか。
  承認外の設計判断を silent に行っていないか。
- 依存規則（`import-linter` の契約）と層の責務に反していないか。
- 未確定事項を「仮置き」として明示しているか。
- 段階の完了条件（全体計画書 §8.2）を満たしているか。

## 6. 仮置き事項（設計文書に無い振る舞いを実装が決めたもの）

実装中に、承認済みの設計文書が定めていない振る舞いを決めざるを得なかった箇所は
「**仮置き**」と呼び、その場で確定させない（§1「前提を silent に決めない」）。

- **PR 本文に番号付きで列挙する**。1件ごとに **(a) 何が未定義か、(b) 現在の実装が何をしているか、
  (c) 取り得る選択肢**を書く。
- **merge の前に、人間が1件ずつ選択式で決める**（§4.6 の状態9）。
  仮置きの列挙そのものは Codex の巡ではないので巡数に数えない（§4.6 規則1）。
  Codex が clean でも省略しない。
- 決まった内容は**設計文書の改訂として同じ PR に含める**。
  決定を PR コメントだけに残さない（設計はドキュメントが正本・§1）。

## 7. merge

merge は人間が判断する。Claude と Codex は「レビューが尽きた」ことを報告するまでで、
自分で merge しない。報告には、実施した巡数、各巡の件数、残った P2、仮置きした事項を含める。

**merge の可否を問えるのは、次の3つをすべて満たす PR だけである。**

| # | 前提 | 根拠 |
|---|---|---|
| 1 | **未解消の仮置き事項が0件**である。PR 本文に挙げた仮置きを人間が1件ずつ決め、決定を**設計文書の改訂として同じ PR に反映して push し終えている** | §6、§4.6 状態9 |
| 2 | **独立レビュー（Codex）が、その最終 head に対して §4.1 の終了条件に達している**（対象内の P0=0 かつ P1=0） | §4.1、§4.6 規則4・規則5 |
| 3 | **設計適合レビューも、同じ最終 head で新たな修正を生まない** | §5、§4.6 状態4 の契機J |

この3つがそろった状態が **§4.6 の状態5（merge の可否待ち）**である。
状態5 で push（契機G）や範囲の変更（契機H）が起きたら、**merge の質問を取り下げて状態1 へ戻る**。
**人間の回答は3通りある**（§4.6 状態5 の契機I）。**merge する**（ループ終了）、
**merge せず PR を閉じる**（却下・保留。ループ終了。作業役は close の指示に従い、進捗ファイルに結果を1行残す）、
**追加の修正や範囲の直しを指示する**（状態1 へ戻る）。
merge しない判断も人間のものなので、**作業役が自分で close を決めることはない**。

**順序が重要である。仮置きの決定は merge の質問より先に来る**。仮置きを添えたまま merge の可否を問うと、
**未決定の振る舞いを含む古い head に merge の承認が出てから設計文書を変える**ことになり、
承認されたものと merge されるものが食い違う。1 → 2・3 → merge の質問、の順を守る。
§4.6 では、状態4 の契機J が「仮置き1件以上なら状態9、0件なら状態5」と分岐することでこの順序を保っている。

Codex review はすべての PR で必須なので（§2）、**レビューを省略して merge へ進む経路は無い**。

§4.4 の安全弁に当たって止めた PR は、まだレビューが尽きていないため、**merge の可否を問わない**。
「要決定」として報告し、**merge ではなく、次に何をするかだけ**を尋ねる。
**安全弁には2つの入口（§4.6 の状態6 と状態7）があり、添えるものと尋ねる選択肢はそれぞれ違う。
その正本は §4.6.1 の「人間待ちの6状態で何を問い、何を添えるか」の表である**（ここには写さない）。
**2つを混ぜない**理由も同表に書いてある。どちらの入口でも、**レビューを飛ばして merge する選択肢は置かない**。

人間の選択に従って対応し、**Codex に戻って §4.1 の終了条件に達してから**改めて merge を問う
（別工程を選んだ場合も、工程の後に Codex へ戻る。§4.6 規則2）。
収束方法が決まる前に merge を問うと、安全弁の分岐が働かない。
