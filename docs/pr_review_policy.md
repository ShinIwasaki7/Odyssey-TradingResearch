# PR レビュー方針

作成日: 2026-09-18
状態: 段階−1 で新規作成（ADR-0017）。運用しながら更新する。
更新: 2026-09-22。Codex レビューの終了条件を、固定の巡数から
「**レビュー対象範囲の中の必ず直す指摘（P0・P1）が0件になるまで続ける**」へ改めた（§4、人間の決定 2026-09-20）。
併せて、PR #14〜#20 の運用で確立した手順（レビュー対象範囲の明示と3分類 §3.1、
毎巡の傾向の読み取りと根本対処 §4.2、安全弁6巡 §4.4、仮置き事項の扱い §6）を明文化した。

本リポジトリの PR レビューの方針を定める。対象は Codex による独立レビューと、
Claude による設計適合レビューの2つのレーン、および merge 判断の所在である。

## 1. 原則

- **レビューと merge 判断を分ける**。レビューは欠陥と設計違反を見つける作業であり、
  merge するかどうかの判断は含まない。**merge 判断は常に人間が行う**（CLAUDE.md）。
- **設計はドキュメントが正本**。実装 PR のレビューは、コードが `docs/design/` と
  `docs/decisions/` の承認済み内容に合致しているかを基準にする。
  設計そのものへの異論は PR ではなく設計文書へ差し戻す。
- **前提を silent に決めない**。レビュー中に未確定の設計判断が必要になった場合は、
  その場で決めずに PR 本文へ「仮置き」として明示し、人間の判断を仰ぐ。

## 2. PR 種別と Codex review の要否

| 種別 | 内容 | Codex review |
|---|---|---|
| 設計文書のみ | `docs/design/`、`docs/decisions/` の追加・更新のみ | 任意 |
| 骨格・ツール | ディレクトリ骨格、ビルド/CI 設定、品質ツール設定、運用スクリプト | **必須** |
| 実装 | `src/odyssey_fx/` の振る舞いを持つコード、およびそのテスト | **必須** |

1つの PR が複数種別にまたがる場合は、重い方（実装 > 骨格・ツール > 文書）に合わせる。

## 3. 指摘の分類

| 優先度 | 内容 | 扱い |
|---|---|---|
| **P0** | 設計違反（承認済み設計・ADR・依存規則に反する）、データ破壊（原データの上書き、holdout の誤読）、先読み（判断時点で利用できない情報の参照）、決定論の破壊 | 必ず修正してから次へ進む |
| **P1** | バグ、契約違反（型・状態機械・不変条件の破り）、テストが検査すべき対象を検査していない | 必ず修正してから次へ進む |
| **P2** | 改善提案、命名、スタイル、将来の整理 | 修正するか、見送る理由を PR に記録する |

指摘に優先度タグが付いていない場合は、上の定義に照らして自分で分類し、
その分類を PR コメントに残す。

### 3.1 レビュー対象範囲による3分類【決定 2026-09-20、PR #14〜#20 で確立】

優先度（P0/P1/P2）を付ける前に、**その指摘が今回の PR のレビュー対象範囲に入るか**を先に判定する。
判定は次の3つのいずれかになり、**いずれも PR コメントに残す**。

| 分類 | 内容 | 扱い |
|---|---|---|
| **対象内** | 今回の PR が決める範囲の中の指摘 | §3 の表で P0 / P1 / P2 を付ける。P0 と P1 は必ず直す |
| **対象外（後続文書へ）** | 後続の設計文書・後続の段階が決める事項への指摘 | 直さない。どの文書・どの段階の担当かを書いて残す |
| **不採用** | 人間の決定・承認済みの設計と衝突する指摘 | 直さない。**なぜ衝突するかの理由を書き**、設計を変える価値があるなら要決定として人間に上げる |

**範囲の正本は次の順で決める**（上から順に、存在する最初のものを使う）。
すべての PR に、**必ずどれか1つの正本がある**ようにするための順序である。

| 順 | PR の中身 | 範囲の正本 | 依頼本文に添える文 |
|---|---|---|---|
| 1 | §1.2 の境界表を持つ設計文書（D04 以降の各文書）の追加・改訂 | その文書の **§1.2**（本書が決めること／後続に委ねること／前提から受け取ることの境界表） | 「対象範囲は §1.2 の表。表の外は対象外」 |
| 2 | §1.2 を持たない文書の改訂（決定記録 `docs/decisions/`、D01〜D03、全体計画書、本書、無人運転プロトコル、スキル、README など） | **PR 本文に置く範囲表**。変更した文書と箇所を1行ずつ挙げ、「表の外は対象外」と明記する | 「対象範囲は PR 本文の範囲表に挙げた箇所。表の外は対象外」 |
| 3 | 実装（`src/` とそのテスト） | **承認済みの設計文書のうち、その PR が実装する範囲**。PR 本文に対象の文書と節を挙げる | 「対象範囲は PR 本文に挙げた設計文書の節。範囲外の設計変更の提案は対象外」 |

順2 の範囲表は、§1.2 と同じ役割を果たす。**「何を決める PR か」と「何を決めない PR か」の両方を書く**。
片方しか書かないと、書いていない側の指摘が毎巡湧く。

範囲を伝えずに依頼すると、後続文書が決める事項への指摘が毎巡湧き、収束しない。


## 4. Codex review の運用

前提（人間が一度だけ設定する）: 対象リポジトリで Codex の code review を有効にし、
mention 運用（`@codex review` の投稿で起動）にしておく。

```
1. push → gh pr create --base main
2. gh pr comment <PR#> --body "@codex review"   （投稿時刻を UTC で控える）
   §3.1 の表で範囲の正本を選び、その一文を依頼本文に添える
3. uv run python tools/ops/codex_review_poll.py \
       --pr <PR#> --since <その時刻> --interval 240 --timeout 1200
4. 応答を分類する（§3.1 の3分類 → 対象内のものに §3 の P0 / P1 / P2）
5. 対象内の P0 と P1 を直し（傾向を読んで根本対処を先に入れる）、push して 2 へ戻る
6. 対象内の P0 が0件かつ P1 が0件の巡が出たら、そこで終了する
```

- **ポーリングは4分間隔**、1巡あたりの無応答の打ち切りは20分。

### 4.1 終了条件は巡数ではなく「重大な指摘が残っていないこと」【決定 2026-09-20】

人間の決定（2026-09-20）:
「Codex レビューは P1 が0件になるまでは続けてください。ただ繰り返すのではなく、
指摘の傾向を読み取り収束方向に向かうようにしてください。
ただし無理やり設計を捻じ曲げたりはせず、あるべきを常に考えるように。」

これを運用規則にすると次のようになる。

- **終了条件は「必ず直す指摘が残っていないこと」**である。
  レビュー対象範囲の中で、**設計違反など必ず直す最重大の指摘（P0）が0件、
  かつバグ・契約違反など必ず直す重大な指摘（P1）が0件**になった巡で終了する。
- その巡に残った軽微な指摘（P2）は、直して push してよい。**P2 だけのために再依頼はしない**。
- **固定の巡数は置かない**。以前の「基本2巡・1巡目で0件なら1巡・最大2巡」は本改訂で廃止する。
  2巡で P1 が残っていても、そこで止めずに収束させる。

### 4.2 収束させる: 毎巡、指摘の傾向を読んでから直す

同じ直し方を繰り返すだけでは巡数が増えるだけで収束しない。2巡目以降は次の順で進める。

1. **傾向を1行で PR コメントに書く**。直前までの指摘が何に集中しているか（例: 「表の列と本文の説明の食い違い」「対象外の後続文書に属する事項」）を書いてから修正に入る。
2. **同種の指摘が繰り返しているなら、個別の修正より先に根本対処を入れる**。
   根本対処とは、同じ種類の指摘が次の巡で再発しないようにする文書上・実装上の手当てである
   （例: 値の正本を1か所に集約して他は参照にする、境界表に欠けていた行を足す、
   依頼本文で対象範囲を明示し直す、検査を1件足して不整合を機械で止める）。
3. そのうえで個別の指摘を直す。

### 4.3 設計を捻じ曲げない

- 指摘を消すことが目的ではない。**人間の決定・承認済みの設計文書・ADR と衝突する指摘は「不採用」**とし、
  衝突の理由を書いて残す（§3.1）。指摘に合わせて設計を曲げてはならない。
- 指摘が正しく、設計のほうに直すべき点があるなら、その場で決めずに
  **要決定として人間に上げる**（本書 §1「前提を silent に決めない」）。
- 対象外の指摘も同様に、直さずに担当の文書・段階を書いて残す。

### 4.4 安全弁: 6巡で収束しなければ人間に渡す

- **6巡回しても対象内の P0 / P1 が0件にならない場合は止める**。報告には
  **(a) 指摘の傾向、(b) 収束しない理由の仮説**を添える。
  人間が「続行」「レビュー対象範囲を明記し直す」「別工程（紙上トレースなど）に切り替える」
  のいずれかを選ぶ。巡数を機械的に打ち切るためではなく、**同じ所を回り続けている兆候を人間に渡すため**の上限である。
- Codex が利用上限（rate limit）で応答を返した巡は、**巡数に数えない**。
  30 分待って `@codex review` を再投稿する。再投稿は**最大8回**まで。

### 4.5 ループは承認停止なしで自走する

- この push → PR → 依頼 → ポーリング → 分類 → 修正 → 再依頼のループは、**承認停止なしで自走する**。
  止めて確認を取るのは **merge の前だけ**（CLAUDE.md）。§4.4 の安全弁に当たった場合も、
  merge ではなく「要決定」としての報告になる。

poller の終了コード:

| exit | 意味 | 次の行動 |
|---|---|---|
| 0 | 応答あり（JSON で `status: responded`） | §3.1 で分類し、対象内の P0 / P1 を修正 |
| 1 | `gh` の失敗（未認証、PR 不在など） | 原因を報告して停止（推測で進めない） |
| 2 | timeout（`status: timeout`） | 「Codex 未応答（GitHub App 未設定の可能性）」として報告し、それ以上待たない |


## 5. Claude による設計適合レビュー（別レーン）

Codex は差分の欠陥を見る。Claude は**設計文書との適合**を見る。両者は別レーンであり、
Codex が clean でも設計適合レビューは省略しない。

- **実装 PR では、Codex が §4.1 の終了条件に達した後にこのレビューを行う**。
  担当は実装したセッションとは別のセッション（既定では Sonnet の子セッション）で、
  **read-only**（コードを書き換えず、指摘を返すだけ）とする。
  指摘は §3 の P0 / P1 / P2 で報告し、実装したセッションが修正する。
- 設計文書 PR では、対象文書の §1.2 の境界表そのものが上位文書と整合しているかを見る。

確認する観点:

- 承認済みの設計（全体計画書・上位設計書・ADR）の範囲内に収まっているか。
  承認外の設計判断を silent に行っていないか。
- 依存規則（`import-linter` の契約）と層の責務に反していないか。
- 未確定事項を「仮置き」として明示しているか。
- 段階の完了条件（全体計画書 §8.2）を満たしているか。

## 6. 仮置き事項（設計文書に無い振る舞いを実装が決めたもの）

実装中に、承認済みの設計文書が定めていない振る舞いを決めざるを得なかった箇所は
「**仮置き**」と呼び、その場で確定させない（§1「前提を silent に決めない」）。

- **PR 本文に番号付きで列挙する**。1件ごとに **(a) 何が未定義か、(b) 現在の実装が何をしているか、
  (c) 取り得る選択肢**を書く。
- **merge の前に、人間が1件ずつ選択式で決める**。レビューの巡数とは独立した手順で、
  Codex が clean でも省略しない。
- 決まった内容は**設計文書の改訂として同じ PR に含める**。
  決定を PR コメントだけに残さない（設計はドキュメントが正本・§1）。

## 7. merge

merge は人間が判断する。Claude と Codex は「レビューが尽きた」ことを報告するまでで、
自分で merge しない。報告には、実施した巡数、各巡の件数、残った P2、仮置きした事項を含める。

**merge の可否を問えるのは、§4.1 の終了条件に達した PR だけである。**
§4.4 の安全弁に当たって止めた PR は、まだレビューが尽きていないため、**merge の可否を問わない**。
この場合は「要決定」として、指摘の傾向と収束しない理由の仮説を添え、
**人間に「続行」「レビュー対象範囲の明記し直し」「別工程（紙上トレースなど）への切り替え」のどれを取るかだけ**を尋ねる。
人間の選択に従って収束させ、終了条件に達してから改めて merge を問う。
収束方法が決まる前に merge を問うと、安全弁の分岐が働かない。
