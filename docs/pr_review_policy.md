# PR レビュー方針

作成日: 2026-09-18
状態: 段階−1 で新規作成（ADR-0017）。運用しながら更新する。

本リポジトリの PR レビューの方針を定める。対象は Codex による独立レビューと、
Claude による設計適合レビューの2つのレーン、および merge 判断の所在である。

## 1. 原則

- **レビューと merge 判断を分ける**。レビューは欠陥と設計違反を見つける作業であり、
  merge するかどうかの判断は含まない。**merge 判断は常に人間が行う**（CLAUDE.md）。
- **設計はドキュメントが正本**。実装 PR のレビューは、コードが `docs/design/` と
  `docs/decisions/` の承認済み内容に合致しているかを基準にする。
  設計そのものへの異論は PR ではなく設計文書へ差し戻す。
- **前提を silent に決めない**。レビュー中に未確定の設計判断が必要になった場合は、
  その場で決めずに PR 本文へ「仮置き」として明示し、人間の判断を仰ぐ。

## 2. PR 種別と Codex review の要否

| 種別 | 内容 | Codex review |
|---|---|---|
| 設計文書のみ | `docs/design/`、`docs/decisions/` の追加・更新のみ | 任意 |
| 骨格・ツール | ディレクトリ骨格、ビルド/CI 設定、品質ツール設定、運用スクリプト | **必須** |
| 実装 | `src/odyssey_fx/` の振る舞いを持つコード、およびそのテスト | **必須** |

1つの PR が複数種別にまたがる場合は、重い方（実装 > 骨格・ツール > 文書）に合わせる。

## 3. 指摘の分類

| 優先度 | 内容 | 扱い |
|---|---|---|
| **P0** | 設計違反（承認済み設計・ADR・依存規則に反する）、データ破壊（原データの上書き、holdout の誤読）、先読み（判断時点で利用できない情報の参照）、決定論の破壊 | 必ず修正してから次へ進む |
| **P1** | バグ、契約違反（型・状態機械・不変条件の破り）、テストが検査すべき対象を検査していない | 必ず修正してから次へ進む |
| **P2** | 改善提案、命名、スタイル、将来の整理 | 修正するか、見送る理由を PR に記録する |

指摘に優先度タグが付いていない場合は、上の定義に照らして自分で分類し、
その分類を PR コメントに残す。

## 4. Codex review の運用

前提（人間が一度だけ設定する）: 対象リポジトリで Codex の code review を有効にし、
mention 運用（`@codex review` の投稿で起動）にしておく。

```
1. push → gh pr create --base main
2. gh pr comment <PR#> --body "@codex review"   （投稿時刻を UTC で控える）
3. uv run python tools/ops/codex_review_poll.py \
       --pr <PR#> --since <その時刻> --interval 240 --timeout 1200
4. 応答を P0 / P1 / P2 に分類する
5. P0 / P1 を修正して push し、2 へ戻る
```

- **ポーリングは4分間隔**、無応答の打ち切りは20分。
- **round 1 で P0 / P1 が0件なら、そこで終了する**（2巡目を行わない）。
- P0 / P1 があれば round 2 を実施し、**最大2巡で停止**する。
  2巡で収束しない場合は人間の判断を仰ぐ。
- この push → PR → 依頼 → ポーリング → 修正 → 再依頼のループは、
  **承認停止なしで自走する**。止めて確認を取るのは merge の前だけ。

poller の終了コード:

| exit | 意味 | 次の行動 |
|---|---|---|
| 0 | 応答あり（JSON で `status: responded`） | 指摘を分類して修正 |
| 1 | `gh` の失敗（未認証、PR 不在など） | 原因を報告して停止（推測で進めない） |
| 2 | timeout（`status: timeout`） | 「Codex 未応答（GitHub App 未設定の可能性）」として報告し、それ以上待たない |

## 5. Claude による設計適合レビュー（別レーン）

Codex は差分の欠陥を見る。Claude は**設計文書との適合**を見る。両者は別レーンであり、
Codex が clean でも設計適合レビューは省略しない。確認する観点:

- 承認済みの設計（全体計画書・上位設計書・ADR）の範囲内に収まっているか。
  承認外の設計判断を silent に行っていないか。
- 依存規則（`import-linter` の契約）と層の責務に反していないか。
- 未確定事項を「仮置き」として明示しているか。
- 段階の完了条件（全体計画書 §8.2）を満たしているか。

## 6. merge

merge は人間が判断する。Claude と Codex は「レビューが尽きた」ことを報告するまでで、
自分で merge しない。報告には、実施した巡数、残った P2、仮置きした事項を含める。
