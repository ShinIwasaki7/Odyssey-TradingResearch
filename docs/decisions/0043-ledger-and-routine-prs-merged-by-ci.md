# ADR-0043: 台帳の行と、実行器が作る定型の PR は、CI の機械の検査で main に入れる（候補の固定の記録は除く）

- 状態: **提案**（2026-11-15。順 11 の文書 PR 2「決定記録と改訂」（[D23](../design/D23_step11_research_automation_plan.md) §8 の表の 2 行目）。中身は人間の決定 144（W1・W5 を撤回）・145 で決まっている。本 ADR の文面は本 PR の merge で承認になる。**定型の PR を CI だけで merge する例外が働くのは、第3項の条件がそろった後**）
- 決定者: ユーザー
- 関連: [D23](../design/D23_step11_research_automation_plan.md) §0.5・§1.1（CI の事実）・§4.3・§4.4（W1・W5）・§9、[D09](../design/D09_multi_run_evaluation.md) §9.10.5・§10.10・§10.12、[D14](../design/D14_step5_research_loop_plan.md) §2.1（D14-11 (a)）、[D16](../design/D16_adoption_review_design.md) §10.2、[D22](../design/D22_step10_research_round3_plan.md) §4 の D22-1 の行 1-10、[`docs/pr_review_policy.md`](../pr_review_policy.md) §1・§2・§7、[全体計画書](../design/fx_research_platform_overall_plan.md) §8.3 の 7、[ADR-0017](0017-codex-review-tooling.md)、[ADR-0042](0042-two-human-gates-per-research-loop.md)

## 文脈（人間の指示の原文。D23 §0.1）

> **指示 B**: 「仮説の承認」「一巡の go」「原因分析」「終了判定」って、それぞれ何を判断しているのですか？人間の判定はボトルネックになりやすいので極力関所は減らしたいです。

> **指示 D**（前半）: できれば4は無くしたいです。記録が面倒なのと思考の幅を狭めてしまう可能性があるので、バックテストの成績評価側で、特定の期間だけに過剰最適化されていないかは判断できるようにするような全体の仕組みとしたい。

（司令塔の記録の注: 「4」は「実験をまたぐ記録（台帳の累計・系譜・見た成績の範囲の申告・成績を読まない規律）」の層。）

順 10 までは、試行台帳の行のコミットと push を人間が行い（D09 §10.10、D14-11 (a)、決定 57・108）、すべての PR を Codex のレビューの後に人間が merge してきた（CLAUDE.md、`docs/pr_review_policy.md` §2・§7）。台帳には鎖（各行が直前の行のダイジェストを持つ）が既にあるが、版管理の本物の台帳の鎖を確かめる CI の段は無い（D23 §1.1）。

### 1. 撤回する既決と出典（D23 §4.4）

| 行 | 撤回する既決 | 出典 | 撤回の後 |
|---|---|---|---|
| W1 | 台帳の行の人間のコミットと push | 決定 57・108、D09 §10.10、D14-11 (a) | 実行器がコミットし、CI が鎖と追記だけであることを確かめる。台帳の累計と「独立した確認ではない」の注記は表示のままで、判定のどの入力にもしない（決定 Q17 のまま） |

- W1 の「台帳」は、試行台帳（`research/trial_ledger.jsonl`）に加え、審査台帳（`research/adoption_reviews.jsonl`）と最終検証の台帳（`research/final_validations.jsonl`）を含むと読む（本 PR の仮置き。D23 §4.3 の CI の新しい段が 3 つの台帳を読むこと、D23 §4.1 で審査と最終検証を実行器が走らせることによる）。
- 撤回した既決の原文は、各文書の記録として残す（消さない）。

### 2. 台帳と定型の PR（D23 §4.3）

1. **台帳の書き手は変えない**: 試行台帳に書くのは今のまま `experiment run` だけ（D09 §10.12.1 の W1）。実行器は台帳に書かず、追記された行のコミットと定型 PR を作るだけ。
2. **CI の新しい段**: 版管理の 3 つの台帳を読込の検査（L1〜L11 と鎖。D23 §4.3。成果物の束縛の記録（`runs/` の下。版管理の外）を読む L11 を CI でどう当てるかは PR 6 で決める）にかけ、さらに PR の基点（main）の台帳の内容が PR の台帳の先頭とバイト単位で同じ（追記だけ）であることを確かめる。どちらかが崩れたら CI が落ちる。
3. **定型 PR の種類**: 事前登録（戦略の宣言・実験設定・注記）、実行記録（台帳の行・数値なしの記録）、一巡の報告（数値なしの部分）。
4. **定型 PR に入れないもの**: 設計文書・実装・研究ポリシー・登録簿・CI の設定の変更と、候補の固定の記録。入っていたら CI が落ちる検査を置く。
5. **候補の固定の記録の PR は人間が merge する**（関所 1。ADR-0042）。固定時点は merge の時刻（D09 §9.10.10・§9.11）。
6. **定型 PR のレビュー**: Codex のレビューを求めない（決定 145）。Codex のレビューは設計文書・実装の PR だけで、安全弁 3 巡も従来どおり（`docs/pr_review_policy.md` §4.4）。

### 3. 当てる時点（例外が働く条件）

定型 PR を CI だけで merge してよいのは、次がすべてそろった後である。そろうまでは、台帳の行のコミットと push は人間が行い（D14-11 (a) の形）、すべての PR は `docs/pr_review_policy.md` の従来の規則（Codex のレビュー・人間の merge）による。

1. 第2項の 2 の CI の新しい段と、第2項の 4 の定型 PR の中身の検査が main にある（D23 §8 の PR 6）。
2. 実行器（PR 8）が main にある。
3. 人間が GitHub の設定（保護の規則・自動 merge）を足した（D23 の仮置き 20。設定と権限は人間が足す）。
4. 人間が CLAUDE.md の merge の文を直した（W5。エージェントは CLAUDE.md を編集しない）。

- **順 10 は順 10 の手順（台帳の行は人間がコミットと push。決定 108）で最後まで行う**（D23 の仮置き 17）。
