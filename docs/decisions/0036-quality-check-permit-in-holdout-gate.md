# ADR-0036: 2024 年以降のデータの品質確認の読み取りは、読み取りの関所の品質確認専用の許可を通す

- 状態: 提案（2026-10-28。順 6 の封印レーンの文書 PR S1（[D15](../design/D15_step6_adoption_path_plan.md) §2.2）。保留中の PR #80（2026-10-14〜15 に起草）の品質確認の許可の決定記録の案を、D15 の決定（OANDA MT5 の 1 分足の経路、2024 年以降と前向きの封印）に合わせて起こし直した（D15-1 (a)）。決定の内容は人間の決定 P1-3（2026-10-11）・K-55・K-56（2026-10-13）と D15-17 (a)（2026-10-28）による。細部は PR #80 の仮置き 6〜10・12・13・16〜18（2026-10-14）と 19（2026-10-15）への人間の決定による。本 ADR の文面は本 PR の merge で承認になる）
- 決定者: ユーザー
- 関連: [D15](../design/D15_step6_adoption_path_plan.md) §1.3・§2.2・§3.1・§3.7・§3.9、[D11](../design/D11_long_range_data_and_evaluation.md) §5.2・§6 の改訂依頼 6-7c・§7.9・§7.11・§9 の順 4・4a・§10 の受入条件 25、[ADR-0014](0014-period-access-classification.md)（期間のアクセス分類）、[ADR-0035](0035-quality-check-access-vs-strategy-selection-access.md)（品質確認の閲覧と戦略選定の閲覧の区別）、[D01](../design/D01_architecture_and_dependency_rules.md) §4・§10.2、[D03](../design/D03_marketdata_and_time.md) §3.8・§15.3、[D09](../design/D09_multi_run_evaluation.md) §9.3、PR #80（保留中。本 ADR の元の案）

## 文脈

2024 年以降の区分（ADR-0035 第0項の 3）の partition は、読み取りの関所（`evaluation.application.holdout_gate`）を通らない読込経路を持たない（D01 §10.2・ADR-0014）。関所が今定めている許可は、封印期間（`SEALED`）を最終評価で 1 回だけ読む許可だけであり、読んだ時点で `CONSUMED` へ遷移する（ADR-0014）。関所はまだ実装されていない（D15 §1.1。モジュール `evaluation.application.holdout_gate` が無い）。最終評価の許可の手順の具体化は D09 の後続版（D15 の R2）の担当である（D09 §9.3・§19）。

順 6 では、2024-01-01 以降の OANDA MT5 の 1 分足を新たに取得し、関所の下に封印として取り込む（D15 の決定 2'）。前向きの封印も取り込む（決定 2''）。取り込みは取得のたびに snapshot として受け入れ、partition を封印の状態で作る（D15-14 (a)）。受入れは snapshot を作るために価格を解析し、時刻・件数・欠落の区間・価格 4 値の整合・負のスプレッドを検査する（D15-17 (a)）。つまり、封印のデータを最終評価より前に読む処理が要る。この読み取りを最終評価の許可で行えば取り込みのたびに封印が使用済みになり、許可なしで行えば関所を迂回する経路ができる。

原ファイル（原 CSV・1 分足）は期間をまたぐことがあるので、partition の許可集合だけでは原ファイルの読み取りを止められない。

本 ADR は PR #80 の案（2026-10-14〜15）を出発点にした。PR #80 は旧データ（HistData・Dukascopy の補充）の経路を前提に書かれ、2026-10-15 に人間の指示で保留になった。本 ADR は、今の経路で要る部分（2 種類の許可、承認の形、転用の防止、fail-closed の順、原ファイル、依存関係、受入れを許可の下に置くこと、保護された生成物）を残した。PR #80 からの変更点は末尾の表にある。

## 決定

### 1. 関所に品質確認専用の許可を足す（人間の決定 P1-3）

P1-3 の原文（2026-10-11、D11 §7.9）:

> 既存の読み取り関所（holdout_gate）を通し、品質確認専用の許可を追加します。
> ただし、最終評価用の許可に目的名だけを追加する設計では不十分です。
> - 品質確認の許可は、承認された道具・版・設定・対象期間に限定する。通常の戦略実行へ転用できないようにする。
> - 原CSV・1分足も対象に含め、関所を迂回する読み取り経路を作らない。
> - 閲覧記録と消費記録を明確に区別する。品質確認の記録を追加しても、封印状態を消費済みにしない。消費済みを封印へ戻すこともない。
> - 許可確認や必須記録に失敗したら、読み取りを開始しない。
> - 2026年分は品質確認の許可があっても隔離を維持する。
> - 価格を出力しないだけでなく、内部で戦略成績を計算して判断に使う経路も禁止する。
> 依存規則の設計（D01）、期間アクセス分類の決定記録（ADR-0014）、市場データ設計（D03）、品質確認用の新しい決定記録を整合させてから実装する方針です。

本 ADR が、原文の最後の行の「品質確認用の新しい決定記録」である。

### 2. 受入れも許可の下に置く（人間の決定 K-55・D15-17 (a)）

K-55 の原文（2026-10-13、D11 §7.11）:

> 「今決める：許可の下に置く」を選択
> 既存の受入れ処理も、2024年以降の原CSV・1分足を読む場合は許可対象に含めます。受入れを理由に関所を迂回する経路は認めません。
> 承認された道具・版・設定・対象期間に限定し、許可確認と必須の閲覧記録が成功してから読み取りを開始してください。条件を満たす受入れは戦略評価による消費とは区別し、生成物にも保護区分を引き継ぎます。
> 2026年分の隔離を保った取り込みと、研究・戦略実行への読み取り許可を区別してください。この原則を今決め、具体的な許可方式と依存関係は、品質確認の許可に関する決定記録と依存規則の設計（D01）の改訂で確定してください。

D15-17 の決定（2026-10-28、原文は D15 §0.5.2）: 「(a) 受入れの検査を品質確認専用の許可の下で行い、出力は件数・時刻・区間・ハッシュ・合否だけ (推奨)」。

本 ADR と D01 の改訂（D11 の改訂依頼 6-17）が、K-55 の原文の最後の行の「具体的な許可方式と依存関係」を定める。下の【決定】の箇所がそれであり、PR #80 の仮置き 7 への人間の決定（2026-10-14）で確定した。封印の取り込みの受入れ（D15-14 (a)・D15-17 (a)）は、この許可の下で行う。

### 3. 許可の 2 種類を分ける

関所は次の 2 種類の許可を、**別の型・別の手順**として持つ（P1-3 の「最終評価用の許可に目的名だけを追加する設計では不十分」）。

| | 最終評価の許可（既存。ADR-0014） | 品質確認の許可（本 ADR） |
|---|---|---|
| 読める対象 | 封印の区分の `SEALED` の partition | 許可に書いた対象の区分と期間の partition と原ファイル（原 CSV・1 分足） |
| 使える道具 | 最終検証のコマンド 1 本（D09 §9.3） | 承認された品質確認の道具だけ（第4項） |
| 記録 | 消費の記録（`access_log.jsonl`）。`SEALED → CONSUMED` | 品質確認の閲覧の記録（ADR-0035 第4項）。封印の状態を変えない |
| 出力 | 制限は D09 の後続版 | ADR-0035 第2項の「出力してよいもの」だけ。例外は保護された生成物（第10項）。【決定】照合の差の詳細を人間だけが見る非公開の出力（ADR-0035 第6項の 3。PR #80 の仮置き 16）も例外としたが、照合の差の手順は当面使わない（ADR-0035 第6項の 3。仮置き S1-5） |
| 隔離の区分 | 読めない（ADR-0014） | 隔離を保つ（第6項） |

品質確認の許可で最終評価・run・探索の実験の入力を作れない（第5項）。最終評価の許可で品質確認の記録を書いて消費を避けることもできない。

### 4. 「承認された道具・版・設定・対象期間」の形

**【決定】承認の形**（PR #80 の仮置き 6）: 品質確認の道具ごとに、許可の定義ファイル（`configs/quality_checks/<道具の名前>.yaml`）を版管理に置き、人間が PR の merge で承認する。定義には、道具の名前と版、設定のダイジェスト、対象の区分と期間、対象（partition か原ファイルか、銘柄・時間足）、出力の種類を書く。関所は、実行しようとする道具の名前と版・設定のダイジェスト・要求する区分と期間が、承認済みの定義と一致することを確かめてから許可を出す。一致しなければ許可を出さない。

**許可の定義が覆ってよい範囲**【仮置き S1-4】: 許可の定義の対象は、制約の改定文の決定記録（D15 §2.2 の S2a。D15-2 (a)）が取得と封印の取り込みを許す範囲（OANDA MT5 の 1 分足と、それから作る partition）の中に限る。手元の旧データの CSV（`data/raw/market/` の 15 分足・1 時間足と `data/raw/histdata/` の 1 分足）の 2024 年以降を含むファイルは、許可の定義の対象にしない（凍結のまま、2024 年以降の部分も読まない。D12-1、D15 §0.1.2 の §2）。改定文の承認までは、2024 年以降を対象にする許可の定義を置かない（D15 の仮置き 2。関所の確認は人工データだけで行う。D15 の仮置き 8）。

### 5. 許可を通常の戦略の実行へ転用させない

1. 品質確認の許可は、品質確認の読み取りの経路だけが受け取れる型にする。as-of ビュー（`marketdata.application.asof`）へ渡す許可 partition 集合（D03 §3.8）には、品質確認の許可から partition を入れない。`app.composition` の中で、run・探索の実験・最終検証を組み立てる入口は品質確認の許可を受け取らない。品質確認の許可を受け取るのは、品質確認のコマンド（受入れを含む）を組み立てる**専用の入口**だけである（入口の名前は関所の品質確認の許可を実装する PR（D15 §2.2 の S3。PR #80 の時点の呼び名は D11 §9 の順 4a。仮置き S1-1）で付ける。【決定】PR #80 の仮置き 7）。
2. 内部で戦略の成績を計算して判断に使う経路を作らない（P1-3）。**【決定】保証の仕方**（PR #80 の仮置き 9）: 品質確認の道具の処理を `marketdata` に置く。`marketdata` は既存の依存規則（D01 §3・§6 の L1）で `strategy`・`backtest`・`evaluation` を import できないので、道具の中で戦略を動かす経路が構造上無い。品質確認のコマンド（`app.cli`）は `backtest`・`strategy` の組み立てを呼ばないことを、S3 のテストで検査する。依存規則（import-linter の契約）は変えない。

### 6. 隔離の区分は隔離を保つ

- P1-3 の原文「2026年分は品質確認の許可があっても隔離を維持する」と K-55 の原文「2026年分の隔離を保った取り込みと、研究・戦略実行への読み取り許可を区別してください」による。両原文の「2026年分」は、隔離の区分（`QUARANTINED_UNASSIGNED`）と読む【仮置き S1-3】。どの期間が隔離の区分に入るかは ADR-0014 と、それを置き換える決定記録（S2a）が定める（決定 2' により、新たに取得する OANDA MT5 の 2024 年以降の 1 分足は封印の区分に入る）。
- 人間の決定 L-29（2026-10-09、原文は D11 §7.7）の「履歴が未確定でも、承認された品質確認だけで隔離状態を保った整備を行う方針です」と「整備を進めても、研究・最終検証への利用許可にはなりません」により、品質確認の許可で隔離の区分を取り込める（整備できる）ことと、隔離の区分を研究・戦略の実行で読めることは別である。品質確認の許可は隔離の区分の分類を変えず、取り込みの出力（partition）も隔離の区分を引き継ぎ、通常の研究の経路から読めない（L-29 の実行の前提 3）。
- 隔離の区分の再分類は、ADR-0014 を置き換える決定記録（S2a）だけが行う（PR #80 の時点では 2026 年分の ADR（D11 の改訂依頼 6-7b、順 5）としていた。D15-5 を外し、置き換え先が S2a になった）。

### 7. 読み取りの手順（fail-closed）

品質確認の読み取りは次の順で行い、どの段階で失敗してもデータを返さない（読み取りを始めない）。

1. 許可の確認: 関所が第4項の一致を確かめ、品質確認の許可を出す。
2. 閲覧の記録: 関所が ADR-0035 第4項の閲覧の記録を追記し、記録に成功したことを確かめる（「成功」の意味は ADR-0035 第4項の 5）。
3. 読み取り: 許可が覆う partition と原ファイルだけを読む。

- 【決定】4 段目として、読み取りの後に閲覧の記録の**終了の行**（ADR-0035 第4項の 6）を書く。書くのは開始の行と同じく関所で、`app` の品質確認専用の入口が道具の終了（完了・途中で停止）を関所へ渡し、関所が `QualityAccessLog` で追記する（PR #80 の仮置き 7）。終了の行を書けなければ、結果を出さずに失敗として終わる（PR #80 の仮置き 13）。
- 【決定】**受入れで終了の行を書けなかったときの暫定 snapshot**（PR #80 の仮置き 18）: 受入れは 3 段目で暫定 snapshot（D03 §3.7.1）を書いてから 4 段目に進むので、終了の行に失敗しても暫定 snapshot は残る。これは消さずに残す（原因の調査のため）が、その受入れの閲覧の識別子に「完了」の終了の行が無い間は、分類・確定・承認（`data classify` / `data approve`）へ進めない（それらのコマンドが、暫定 snapshot に記録した閲覧の識別子の終了の行を確かめ、無ければ拒否する）。進めるには、人間が受入れをやり直して新しい暫定 snapshot を作る。
  - **【決定】暫定 snapshot と閲覧の識別子の結び方、やり直しとの両立**（PR #80 の仮置き 19）: 受入れは、品質確認の閲覧の識別子を暫定 manifest の項目に書く。この項目は `created_at` と同じく暫定の識別子（`provisional_id`）と `SnapshotId` の計算の対象外とする（D03 §3.7.1。同じ入力なら同じ識別子のまま）。同じ入力でやり直すと前の暫定 snapshot と同じ識別子になり、D03 の R1-D03-1（暫定×受入れ: 存在すれば失敗する）に当たる。そこで、やり直しの前に人間が前の暫定 snapshot を消さずに `data/snapshots/_pending/_failed/<provisional_id>.<n>/` へ退避する（`n` は 1 から数える。退避先は版管理の外）。退避した暫定 snapshot は分類・確定・承認の対象にならない。閲覧の識別子を持たない暫定 snapshot は、品質確認の許可を要しない受入れ（読んだ原ファイルがすべて研究履歴だけか、第8項の確認済みの一覧に載りハッシュが一致したもの）の結果に限って分類・確定・承認へ進める。どちらに当たるかは、受入れが暫定 manifest に「品質確認の許可を要したか」の項目を書き（識別子の計算の対象外）、classify / approve がそれを見て決める。許可を要したのに閲覧の識別子が無い、または項目が無い（S3 より前に作られた）暫定 snapshot は拒否する（fail-closed）。
- 消費の記録（`access_log.jsonl`）は書かない。`HoldoutState` は変わらない（`SEALED` は `SEALED` のまま、`CONSUMED` は `CONSUMED` のまま）。
- 許可を出しただけで記録が無い状態、記録があるのに読めない状態は、どちらも「読めない」に倒す（ADR-0014 の fail-closed と同じ考え方）。

### 8. 原ファイル（原 CSV・1 分足）も関所の下に置く

P1-3 の原文「原CSV・1分足も対象に含め、関所を迂回する読み取り経路を作らない」による。対象の原ファイルは置き場によらず `data/raw/` 配下のすべてである（OANDA MT5 の 1 分足の原ファイル `data/raw/oanda_mt5/`（D03 §15.1）、手元の旧データの CSV `data/raw/market/` と HistData の 1 分足 `data/raw/histdata/`、今後置く原ファイルを含む）。

**【決定】原ファイルが 2024 年以降を含むかの判定**（PR #80 の仮置き 8）: 原ファイルは、**既定で 2024 年以降を含むものとして扱う**（fail-closed）。許可なしで読める原ファイルは、次の 2 つを両方満たすものだけである。
1. データ源の設定（`configs/datasources/`）で、ファイルの期間の終わりが 2024-01-01T00:00Z より前と宣言されている。
2. そのファイルを**品質確認の許可の下で**一度読み、足の終わりの時刻（`bar_end`）がすべてその前であることを確かめ、確かめたファイルのハッシュを記録してある（この確認の読み取り自体は許可と閲覧の記録を経るので、関所を迂回しない）。以後の許可なしの読み取りは、読む前にファイルのハッシュが記録と一致することを確かめ、一致しなければ読まない。ハッシュの計算はファイルのバイト列を行に分けず・解析せず・保持せずにダイジェストへ畳み込むだけで、出力は「一致・不一致」だけとする（時刻・件数・価格のどれも取り出さない）。これは品質確認の閲覧（行を読む読み取り）に当たらない。不一致のときの扱いは下の仮置き 17 への決定による（許可なしの読み取りは始めずにエラーで止まる）。

**【決定】確認済みのハッシュの置き場と不一致の扱い**（PR #80 の仮置き 17）: 確認済みのファイルの一覧（ファイルの置き場・ハッシュ・確認した品質確認の閲覧の識別子）は、データ源の設定（`configs/datasources/`）の中に版管理で置き、人間が PR の merge で足す（確認の読み取りの終了の行が「完了」であることを確かめてから）。許可なしの読み取りは `marketdata` がこの一覧の値（`app.config` が読んで渡す）とだけ照合し、関所も品質確認の閲覧の記録も使わない。不一致のときは読み取りを始めずにエラーで止まり、置き場とハッシュをエラーとして人間に示す（品質確認の閲覧の記録には書かない。閲覧ではないので閲覧の識別子を持たないため）。原ファイルの置き場は上書き禁止（D01 §10.2）なので、不一致は事故として人間が調べる。不一致のファイルは、人間が一覧を直すまで確認済みとして扱わない（既定の「含む」扱い）。品質確認の許可がそのファイルを覆う読み取り（受入れを含む）は、許可なしの経路ではないので、この照合に関わらず許可の手順（第7項）で読む。

確認で宣言に反する行（2024 年以降の行）が見つかったファイルは、宣言を誤りとして許可なしでは読めないままにする（宣言の訂正は人間の判断）。それ以外の原ファイルを読む処理（受入れを含む）は、品質確認の許可を要する。手元の旧データの CSV のうち 2024 年以降を含むもの（今の原 CSV は 2026 年まで含む。ADR-0014 の文脈）は、第4項のとおり許可の定義の対象にしないので、本基盤の経路からは読めない【仮置き S1-4】。

### 9. 関所と受入れ・品質確認の道具の依存関係

**【決定】依存関係**（PR #80 の仮置き 7。K-55 で本 ADR と D01 の改訂に委ねられた点）:

1. 品質確認の許可を出すのは関所（`evaluation.application.holdout_gate`）である（P1-3 の原文「既存の読み取り関所（holdout_gate）を通し」）。
2. 受入れ・品質確認の道具の処理は `marketdata` にあり、`marketdata` は `evaluation` を import できない（D01 §3.2）。そこで、`app`（`app.cli` の品質確認のコマンドと、`app.composition` の品質確認専用の入口。第5項の 1）が関所から品質確認の許可を受け、閲覧の記録の成功の後に、**読み取りの許可の値**（`marketdata.domain` に置く型。許可の識別子・対象の区分と期間・対象の partition と原ファイル）を `marketdata` の受入れ・品質確認の道具に渡す。`evaluation` は `marketdata.domain` を参照できる（D01 §6 の F7）ので、関所はこの型の値を作れる。
3. `marketdata` の原ファイルと partition の読み取り（`RawBarSource` の実装と 1 分足の読み取り、`SnapshotStore` の partition の読み取り）は、渡された読み取りの許可の値が覆わない 2024 年以降を含むファイル・partition を読まない（第8項）。値が渡されなければ、研究履歴だけを読む。
4. 品質確認の閲覧の記録の追記は、関所が新しいポート（`QualityAccessLog`。定義は `evaluation.application.ports`、実装は `marketdata.adapters` の追記の adapters を `app` が適合させる。行の型は `marketdata.domain`。`HoldoutAccessLog` と同じ形）を通して行う。消費の記録のポート（`HoldoutAccessLog`）とは別のポートにする（P1-3 の「閲覧記録と消費記録を明確に区別する」）。
5. パッケージ間の依存規則（D01 §3.2 の許可表と第6節の契約）は変えない。

### 10. 受入れの生成物は保護の区分を引き継ぐ（K-55）

- 品質確認の許可の下で行う受入れは、戦略評価による消費（`SEALED → CONSUMED`）と区別する。受入れは消費の記録を書かない。
- 受入れの生成物（snapshot の partition など）は、元の期間の区分（封印の区分・隔離の区分）を引き継ぐ（D03 §3.8 の partition 単位の分離のまま）。封印の取り込みで作る partition の初期状態は ADR-0014 と、それを置き換える決定記録（S2a。D15-14 (a)）が定める。
- **【決定】出力の制限と受入れの生成物の関係**（PR #80 の仮置き 12）: ADR-0035 第2項の「出力しないもの」（価格の値など）は、**研究者に返す・表示する・版管理に入れる出力**（報告・検査報告・標準出力・記録）についての制限と読む。受入れが書く partition（価格の値を含む足のファイル）は研究者への出力ではなく、保護の区分を引き継いで関所の下に置かれる**保護された生成物**として扱い、ADR-0035 第3項の条件 1 に反しない。条件: (1) partition は版管理の外（`data/snapshots/` の実体）にだけ書く。(2) 受入れは partition の価格の値を表示・報告しない（今の検査報告と同じ）。(3) 書いた partition は関所を通らない経路から読めない（D01 §10.2）。この 3 つを満たさない書き出しは品質確認とみなさない。受入れの検査報告（`integrity_report.json`）は今も価格の統計を含めない（D03 §3.9・D01 §10.2）。

### 11. 実装の位置

- 人間の決定 K-56（2026-10-13、原文は D11 §7.11）: 「順 4a に入れる（推奨）」。品質確認専用の許可の実装は、閲覧の記録の実装（K-49）と同じ PR に入る。順 6 では、その PR は D15 §2.2 の S3（関所の品質確認の許可と閲覧の記録。D11 順 4a 相当）である【仮置き S1-1】。
- 実装は、本 ADR・ADR-0035・ADR-0014 の注記・D01 §10.2・D03 §3.8 の整合（本 PR）の後に始める（P1-3 の最後の行）。S3 は、これに加えて S2a・S2b の承認の後に始める（D15 §2.2）。
- **【決定】D09 §9.3 の 7 との関係**（PR #80 の仮置き 10）: D09 §9.3 の 7 は「後続版の承認までは gate の実装も始めない」とする。S3 では関所のうち**品質確認の許可だけ**を実装し、最終評価の許可は D09 の後続版（D15 の R2）の承認まで実装しない（呼ばれたら拒否する。実装は D15 の R4）。D09 §9.3 の 7 にこの旨の注記を足した（本 PR。D09 v0.4 の注記）。

## 影響

- **ADR-0014**: 注記の 1〜5 は決定を変えない。注記の 7 は、ADR-0035 第3項（PR #80 の仮置き 15・21）により `SEALED → CONSUMED` の契機（後からの違反判定）を 1 つ足す。ADR-0014 を置き換える決定記録（S2a）は、これらの注記を新しい区分に引き継ぐ。

- **D09 §9.3 の 7**: 品質確認の許可だけを S3 で先に実装する注記を足す。
- **受入れ（`data accept` と MT5 経路の 1 分足の受入れ。D03 §15.3）**: S3 の後は、2024 年以降を含む原ファイルを読む受入れは品質確認の許可を要する。それまで、2024 年以降を含む原ファイルを読む受入れを行わない（D11 §5.3 の 1）。封印の取り込み（D15 の S4a・S5a・S5b）はこの許可の下で行う。
- **テスト**: D11 §10 の受入条件 25 の検査（許可の範囲外・記録の失敗・封印の状態の不変・隔離の区分・関所の外の経路が無いこと）を S3 に入れる。
