# ADR-0035: 2024 年以降のデータの閲覧は品質確認と戦略選定に分け、品質確認の閲覧は必ず記録する

- 状態: 提案（2026-10-14。決定の内容は人間の決定 L-12・L-13・L-20・L-21・L-27・K-38〜K-40・P1-3（2026-10-09〜10-11）による。細部は PR #80 の仮置き 2〜5・12〜16（2026-10-14）と 20・21（2026-10-15）への人間の決定による。本 ADR の文面は PR #80 の merge で承認になる）
- 決定者: ユーザー
- 関連: [D11](../design/D11_long_range_data_and_evaluation.md) §5.2・§5.3・§6 の改訂依頼 6-7a・§7.5・§7.9・§7.10、[ADR-0014](0014-period-access-classification.md)（期間のアクセス分類）、[ADR-0036](0036-quality-check-permit-in-holdout-gate.md)（読み取りの関所の品質確認専用の許可）、[D03](../design/D03_marketdata_and_time.md) §3.8、[D01](../design/D01_architecture_and_dependency_rules.md) §4・§10.2

## 文脈

長期評価の設計（D11）は、2017 年から 2026 年までの市場データについて、出所・時刻・休場・欠落を追跡する。追跡には 2024 年以降のデータ（旧封印期間 `LEGACY_HOLDOUT` と未分類の隔離 `QUARANTINED_UNASSIGNED`。ADR-0014）の時刻と件数を数える読み取りが要る。

D11 §5.1 の確認（2026-10-09）の時点の事実:

- 品質確認の閲覧と戦略選定の閲覧の区別は、どの文書（ADR-0014・D03・D09）にも無かった。
- ADR-0014 の記録の仕組み（`access_log.jsonl`）は snapshot の partition の読み取りだけを対象にする。原ファイル（原 CSV・1 分足）の閲覧は記録の外にある。
- 監査（PR #76 `docs/data/audit_usdjpy_2026-10.md`）は、2024 年以降の USDJPY の原 CSV と 1 分足、他の 9 銘柄の原 CSV 18 本の**時刻と件数**を数えた。価格の列は解析・表示・保存していない（同 §0・§8 の 6）。この閲覧は記録の仕組みの外で行われた。

品質確認の閲覧を封印期間の使用に数えると、データの整備のたびに未使用の期間が失われる。区別が無いまま数えないと、品質確認を名目にした戦略選定の閲覧を止められない。

## 決定

### 1. 区別の規則を置く場所

人間の決定 L-12（2026-10-09、原文は D11 §7.5）: 「1: 新しい ADR（推奨）」。本 ADR がその ADR である。

### 2. 品質確認の閲覧と戦略選定の閲覧の区別（D11 §5.2 の表。人間の決定 K-38）

人間の決定 K-38（2026-10-11、原文は D11 §7.10）: 「このまま + P1-3 の条件を反映（推奨）」。D11 §5.2 の表を次のとおり写す。

| | 品質確認の閲覧 | 戦略選定の閲覧 |
|---|---|---|
| 目的 | 出所・時刻・休場・欠落の追跡（D11 第2・3節） | 戦略・パラメータ・評価基準を選ぶ・調整する・判断する |
| 出力してよいもの | 件数、時刻、区間、ハッシュ、合否、照合の一致・不一致の件数、根拠の資料 | 制限なし（区分が許す範囲で） |
| 出力しないもの | 価格の値・収益率・価格の図・指標の値・戦略の判断や損益 | — |
| 例 | 受入れの完全性検査、欠落一覧、区間台帳の作成、カレンダーの宣言と公表記録の照合 | run、探索の実験、評価のレポート |
| 記録 | 品質確認の閲覧の記録（本 ADR の第4項）に、日時・道具と版・対象の区分と期間・出力の種類を残す。消費の記録とは別（P1-3） | 封印期間なら ADR-0014 の許可判定と消費の記録。研究履歴なら試行台帳 |

### 3. 品質確認だけで封印を消費しない条件（人間の決定 L-13・K-39・P1-3）

L-13 の原文（2026-10-09、D11 §7.5）の該当部分:

> 品質確認だけで封印を消費しないための条件も、先ほど決めた新しい閲覧ルールで明文化します。

K-39 の原文（2026-10-11、D11 §7.10）: 「3 つ + P1-3 の条件（推奨）」。

P1-3 の原文（2026-10-11、D11 §7.9）:

> 既存の読み取り関所（holdout_gate）を通し、品質確認専用の許可を追加します。
> ただし、最終評価用の許可に目的名だけを追加する設計では不十分です。
> - 品質確認の許可は、承認された道具・版・設定・対象期間に限定する。通常の戦略実行へ転用できないようにする。
> - 原CSV・1分足も対象に含め、関所を迂回する読み取り経路を作らない。
> - 閲覧記録と消費記録を明確に区別する。品質確認の記録を追加しても、封印状態を消費済みにしない。消費済みを封印へ戻すこともない。
> - 許可確認や必須記録に失敗したら、読み取りを開始しない。
> - 2026年分は品質確認の許可があっても隔離を維持する。
> - 価格を出力しないだけでなく、内部で戦略成績を計算して判断に使う経路も禁止する。
> 依存規則の設計（D01）、期間アクセス分類の決定記録（ADR-0014）、市場データ設計（D03）、品質確認用の新しい決定記録を整合させてから実装する方針です。

これらにより、次の**すべて**を満たす閲覧だけを品質確認の閲覧とする。1 つでも満たさない閲覧は戦略選定の閲覧として扱う（D11 §5.2 の K-39 の反映）。

1. 第2項の表の「出力しないもの」を出さない。【決定】受入れが保護の区分を引き継いで書く partition（保護された生成物）は、ここでいう出力に当たらない（条件は ADR-0036 の第10項。PR #80 の仮置き 12）。
2. 第4項の閲覧の記録がある。
3. 戦略・パラメータ・評価基準の判断に使わない。
4. 読み取りの関所（`holdout_gate`）の品質確認専用の許可を通る（ADR-0036）。
5. 閲覧の記録は消費の記録と別であり、品質確認の記録で封印の状態を消費済み（`CONSUMED`）にしない。消費済みを封印（`SEALED`）へ戻さない。
6. 内部で戦略の成績を計算して判断に使わない。

品質確認の閲覧は封印期間の使用に数えない。したがって、品質確認の閲覧は `HoldoutState` を変えない（ADR-0014 の注記）。

**【決定】条件を満たしていなかったと後から分かったとき**（PR #80 の仮置き 15）: 許可と閲覧の記録は通ったが、後から条件 1・3・6 のどれか（価格を出した、判断に使った、内部で戦略の成績を計算した）を満たしていなかったと分かった閲覧は、その時点で戦略選定の閲覧として扱う。人間が判定し、判定の事実を品質確認の閲覧の記録に**判定の行**（第4項の 6 の開始の行・終了の行とは別の第 3 の種別。閲覧の識別子・違反した条件・判定の日時と判定者を持ち、1 つの閲覧の識別子に 0 行か 1 行）として追記する。対象に `LEGACY_HOLDOUT` の partition が含まれていれば、その partition の状態（`SEALED` か `CONSUMED` か）によらず、既にあるすべての snapshot の同じ系列・重なる期間の `SEALED` の partition に、消費の記録を追記して `CONSUMED` にする（同じ期間の価格を見たことは snapshot にも対象の状態にもよらないため。対象が partition と原ファイルの両方を含むときは、この規則と下の原ファイルの規則の両方を当てる。下の原ファイルだけの閲覧の扱い（仮置き 21）と揃える）（不可逆。ADR-0014 の消費の記録の手順に従い、origin への push まで行う）。**【決定】書き手と経路**（PR #80 の仮置き 20）: 最終評価の許可は D09 の後続版まで実装しないので、この消費の記録は関所の最終評価の手順では書けない。順 4a の実装 PR で、人間だけが使う管理コマンド（`app.cli`。判定の行の追記と、`HoldoutAccessLog` を通した消費の記録の追記・コミット・origin への push を、この順で fail-closed に行う）を足し、それで書く。消費の記録の行の種別は ADR-0014 の `CONSUMED` の行のまま（理由として閲覧の識別子と判定の行を指す）。対象が 2026 年分なら、判定を 2026 年分の利用の調査（順 5）の材料に入れる。

**【決定】原ファイルだけを対象にした閲覧の違反判定**（PR #80 の仮置き 21）: 違反と判定した閲覧の対象に原ファイル（原 CSV・1 分足）が含まれるとき（partition を含まないときも）、その原ファイルの期間と重なる旧封印期間（`LEGACY_HOLDOUT`、2024〜2025）の `SEALED` の partition を、既にあるすべての snapshot についてすべて使用済み（`CONSUMED`）にする。原ファイルの期間は、閲覧の記録の対象（原ファイルの置き場とハッシュ）と、データ源の設定のファイルの期間から決める。期間が分からなければ、旧封印期間の全体と重なるとみなす（fail-closed）。書き手と経路は上の仮置き 20 の管理コマンドである。

### 4. 2024 年以降の品質確認の閲覧の記録（人間の決定 L-20・L-27）

L-20 の原文（2026-10-09、D11 §7.5）: 「1: 必須（日時・道具と版・区分と期間・出力の種類）（推奨）」。

L-27 の原文（2026-10-09、D11 §7.6）: 「1: 記録に残す（L-20 の対象に原ファイルの閲覧を含め、今回の監査の閲覧も後から記録）（推奨）」。

1. 2024 年以降の区分（`LEGACY_HOLDOUT` と `QUARANTINED_UNASSIGNED`）の品質確認の閲覧を、**必ず**記録する。項目は少なくとも、日時・道具と版・区分と期間・出力の種類の 4 つ。
2. 記録の対象は、snapshot の partition の読み取りだけでなく、**原ファイル（原 CSV・1 分足）の閲覧を含む**。
3. 記録は ADR-0014 の消費の記録（`data/snapshots/<snapshot_id>/access_log.jsonl`）とは**別の記録**にする（P1-3 の「閲覧記録と消費記録を明確に区別する」）。
4. 記録の追記に失敗したら読み取りを始めない（P1-3。手順は ADR-0036）。
5. **【決定】記録の置き場と「記録に成功した」の意味**（PR #80 の仮置き 2）: リポジトリの根の `research/quality_access_log.jsonl`（版管理・追記専用・1 行 1 JSON）に 1 本で置く。既存の行を書き換えない・消さない・並べ替えない。追記した行がファイルに書き込まれ、読み直して一致したことをもって「記録に成功した」とし、その後にだけ読み取りを始める。追記の後のコミットと origin への push は人間が行う（試行台帳 `research/trial_ledger.jsonl` と同じ運用。D01 §10.4）。記録を失わないための規則（試行台帳の D09 v0.3 §10.12.1・§10.12.5 に揃える）:
   1. 追記は 1 回ごとに作って消すロック `research/quality_access_log.lock`（版管理しない）の下で行う。ロックを取れなければ記録に失敗したとして読み取りを始めない。
   2. 品質確認の記録を伸ばす作業木は同時に 1 つだけとし、足した行を `main` に取り込んで push してから別の作業木で伸ばす。
   3. 合流で衝突したときは両方の行を残す（行を消さない）。
   4. 足した行を origin へ push するまで、その作業木を消さない。
   5. 記録のファイルは追記で作らない。順 4a の実装 PR が空のファイルを版管理で最初に置き、無ければ記録に失敗したとして読み取りを始めない（試行台帳の D09 v0.3 §10.12.1 の W2・§10.12.2 の L0 と同じ）。
   6. 末尾に改行で終わらない断片（前の追記が途中で止まった跡）があれば、試行台帳の W3 と同じ規則で扱い、断片につなげて追記しない。断片を扱えなければ記録に失敗したとして読み取りを始めない。
   ロックの除外（`.gitignore`）は順 4a の実装 PR か別の実装 PR で足す（D11 §9 の順 4a。改訂依頼 6-18）。ただし、品質確認の閲覧の記録を追記する前に入れる。理由: 原ファイルの閲覧は snapshot に属さないので snapshot ごとのファイルに置けない。`research/` は既に版管理の対象である。品質確認の記録は封印の状態を変えないので、消費の記録のような origin への push による排他（ADR-0014「消費遷移の直列化」）は要らない。
6. **【決定】行の項目**（PR #80 の仮置き 3）: 決定の 4 項目に、次を足す。許可の識別子（ADR-0036）、対象（partition の識別子、または原ファイルの置き場とハッシュ）、品質確認の種類（受入れ・欠落一覧・区間台帳・照合など）、結果（完了・途中で停止）、記録の種別（その場の記録か、後から記録したものか）。既存の行を書き換えないので、1 回の閲覧は 2 行で記録する: 読み取りの前に書く**開始の行**（決定の 4 項目・許可の識別子・対象・品質確認の種類・記録の種別。これが「必須の記録」）と、読み取りの後に書く**終了の行**（結果・記録の種別）。記録の種別は両方の行に持たせ、同じ閲覧の 2 行で同じ値にする（違えば読込で構造の誤り）。各行は自分の行の識別子（行の鍵）を持つ。1 回の閲覧の 2 行を結ぶのは**閲覧の識別子だけ**であり、開始の行が閲覧の識別子を決め、終了の行は同じ閲覧の識別子を持つ（終了の行は開始の行の行の識別子を持たない）。1 つの閲覧の識別子に開始の行は 1 行、終了の行は 0 行か 1 行とする。読込は次をすべて構造の誤りとして止まる（試行台帳の読込の検査 D09 §10.12.2 の主キーの重複 L6・開始の行の無い結末の行 L8 と同じ考え方）: 同じ閲覧の識別子の開始の行が 2 行以上、終了の行が 2 行以上、開始の行の無い終了の行（第3項の判定の行も同じく、開始の行が無ければ誤り）、同じ閲覧の識別子の判定の行が 2 行以上、行の識別子の重複。構造の誤りがある間は、記録に失敗したとみなして新しい品質確認の読み取りを始めない（P1-3 の「必須記録に失敗したら、読み取りを開始しない」）。直すのは人間で、行を消さずに直す方法（合流の取り違えなら落ちた行を戻す）を取る。終了の行が無い開始の行は「結果不明」として扱い、閲覧が無かったことにはしない。【決定】読み取りの後に終了の行を書けなかったときは、道具は品質確認の結果（件数・合否など）を出さずに失敗として終わる（成功を報告しない）。開始の行は「結果不明」として残る（PR #80 の仮置き 13）。

### 5. 監査（PR #76）の閲覧を後から記録する（人間の決定 L-27）

L-27 の原文は第4項のとおり。監査の閲覧は記録の仕組みができる前に行われたので、第4項の記録の仕組みができた後に、後から記録した行として足す。

**【決定】後から記録する時期と中身**（PR #80 の仮置き 4）: 閲覧の記録を実装する PR（D11 §9 の順 4a）で、記録の形と同時に足す。行は、監査の作業日（2026-10-09）・道具（監査 PR #76 のブランチ `docs/audit-usdjpy-history`、head `1873761` の道具）・対象（USDJPY の原 CSV と 1 分足の 2024 年以降、他の 9 銘柄の原 CSV 18 本の 2024 年以降）・出力の種類（時刻と件数。価格の列は解析・表示・保存していない）を、監査文書 §0・§8 の記述から写し、記録の種別を「後から記録した」とする。許可の識別子は「許可の仕組みの前の閲覧」と明記し、空にしない。第4項の 6 の形に合わせ、開始の行（品質確認の種類は「監査（時刻と件数の数え上げ）」）と終了の行（結果は「完了」。監査 PR #76 が merge 済みで、監査文書が出力の全体であるため）の 2 行を、どちらも記録の種別「後から記録した」として足す。

**【決定】監査の閲覧の分類**（PR #80 の仮置き 14）: 監査の閲覧は、第3項の条件 2（閲覧の記録がある）と条件 4（関所の品質確認の許可を通る）を、その時点では満たしていない（記録と許可の仕組みが無かった）。第3項を文字どおり当てると戦略選定の閲覧になる。そこで、監査の閲覧は**品質確認の閲覧とみなす**。根拠は、出力が時刻と件数だけで価格の列を解析・表示・保存していないこと（条件 1・3・6。監査文書 §0・§8 の 6、D11 §5.3 の 3）と、L-27 が監査の閲覧を品質確認の閲覧の記録の対象として後から記録すると決めたこと。条件 2 は上の後からの記録で満たし、条件 4 は「許可の仕組みの前の閲覧」の例外として、この 1 件（監査 PR #76 の閲覧）に限る。以後の閲覧にこの例外を使わない。2026 年分の利用の調査（D11 §5.3 の 4、順 5）は、この分類にかかわらず監査の閲覧を「どの操作が・いつ・どの期間を・何の目的で読んだか」の一覧に入れ（人間の決定 K-42）、2026 年分を使用済みとみなすかの判断は順 5 で人間が行う（L-13）。

### 6. 2024 年以降の照合の差（人間の決定 L-21・K-40）

L-21 の原文（2026-10-09、D11 §7.5）:

> ③ 照合差は、研究者向けには件数と合否だけにします。
> pip差には配信差やスプレッドなどの情報が含まれるため、保護期間については出力を限定するのがよいです。
> ただし、合否だけでも情報は伝わります。そこで、検査方法・閾値・実行対象を研究期間で先に固定し、保護期間で閾値を変えて繰り返し試さない条件を加えます。
> 原因調査に詳細な差が必要になった場合は、別途定めた手順で扱い、その情報を戦略調整へ流さないようにします。

K-40 の原文（2026-10-11、D11 §7.10）: 「閲覧の区別の ADR（推奨）」（照合の差の詳細を扱う手順の置き場を本 ADR とする）。

1. 2024 年以降の照合（補充の照合など、価格を比べる検査）の結果は、研究者向けには**件数と合否だけ**を出す。差の大きさは出さない。
2. 検査の方法・閾値・実行対象を**研究期間で先に固定**し、固定した版を版管理に入れる。保護期間で閾値を変えて繰り返し試さない（D11 §10 の受入条件 16: 変えた版での実行は拒否される）。
3. **【決定】詳細な差を扱う手順**（PR #80 の仮置き 5。K-40 で本 ADR に置くと決まった「誰が・どの出力を・どこに保存し・研究者に何を返すか」）:
   1. 誰が: 原因の調査ごとに人間が承認したうえで、人間が詳細を見る。研究・戦略の作業をする者（設計役・実装役のエージェントを含む）は見ない。
   2. どの出力を: 承認した調査の対象の塊・時刻に限った、照合の差の詳細（価格と pip の差）。
   3. どこに保存し: 版管理の外の非公開の置き場（`data/private/quality_detail/<調査の識別子>/`）。今の `.gitignore` は `data/raw/` と `data/snapshots/` の実体だけを除外し、この置き場は除外されていないので、順 4a の実装 PR か別の実装 PR で `.gitignore` に除外を足し（D11 §9 の順 4a。改訂依頼 6-18）、`git check-ignore` で除外を確かめるまで詳細な差を作らない。版管理には、調査の識別子・承認の日時・対象・完全な記録のハッシュだけを置く。
   4. 研究者に何を返すか: 原因の区分（配信元の値の差・時刻のずれ・原因不明など）と件数だけ。差の大きさは返さない。
   5. 調査の閲覧も第4項の閲覧の記録に残す（出力の種類は「照合の差の詳細（非公開）」）。
   6. その情報を戦略の調整へ流さない（L-21 の原文）。
   7. **【決定】この調査の読み取りの経路と第3項の条件 1 との関係**（PR #80 の仮置き 16）: 詳細な差（価格と pip の差）を出すので、第3項の条件 1 をそのままでは満たさない。そこで、この調査の読み取りも関所の品質確認の許可を通し（許可の定義の出力の種類に「照合の差の詳細（非公開）」を書き、人間が PR の merge で承認する。ADR-0036 第4項）、出力は上の 3 の非公開の置き場にだけ書き、人間だけが見る。この出力は研究者への出力ではないので、条件 1 の例外（ADR-0036 第10項の保護された生成物と同じ扱い）とする。上の 1〜6 を満たさない調査は戦略選定の閲覧として扱う。品質確認の閲覧なので封印の状態を変えない。
