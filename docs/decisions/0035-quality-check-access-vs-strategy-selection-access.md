## 文脈

順 6 の計画書 D15（2026-10-28 承認）で、人間は次を決めた（原文は D15 §0.1.2）。

- 決定 2': 2024 年以降のデータを、旧基盤での閲覧の有無に関係なく、最終検証用の封印期間（`SEALED`）として使う。研究と同じ OANDA MT5 の 1 分足を新たに取得し、関所（`holdout_gate`）の下に封印として取り込む。誰も開かない。
- 決定 2'': 前向きの封印を残す。
- D15-17 (a): 封印の取り込みでは、受入れの検査（時刻・件数・欠落の区間・価格 4 値の整合の合否・負のスプレッドの件数）を品質確認専用の許可の下で行い、出力は件数・時刻・区間・ハッシュ・合否だけにする。閲覧の記録を残し、封印の状態は変えない。

封印の取り込みの受入れは、snapshot を作るために封印のデータの価格を解析する（D15-14 (a)）。品質確認の閲覧を封印期間の使用に数えると、取り込みのたびに封印が使用済みになる。区別が無いまま数えないと、品質確認を名目にした戦略選定の閲覧を止められない。

長期評価の設計 D11 §5.1 の確認（2026-10-09）の時点の事実:

- 品質確認の閲覧と戦略選定の閲覧の区別は、どの文書（ADR-0014・D03・D09）にも無かった。
- ADR-0014 の記録の仕組み（`access_log.jsonl`）は snapshot の partition の読み取りだけを対象にする。原ファイル（原 CSV・1 分足）の閲覧は記録の外にある。
- 監査（PR #76 `docs/data/audit_usdjpy_2026-10.md`）は、2024 年以降の USDJPY の原 CSV と 1 分足、他の 9 銘柄の原 CSV 18 本の**時刻と件数**を数えた。価格の列は解析・表示・保存していない（同 §0・§8 の 6）。この閲覧は記録の仕組みの外で行われた。

本 ADR は PR #80 の案（2026-10-14〜15）を出発点にした。PR #80 は旧データ（HistData・Dukascopy の補充）の経路を前提に書かれ、2026-10-15 に人間の指示で保留になった。その後、研究用データは OANDA MT5 API の 1 分足に変わった（D12-129）。本 ADR は、今の経路で要る部分（閲覧の区別、記録、封印を消費しない条件、違反の扱い）を残し、旧データの補充の照合の手順は「当面使わない」として外した（D15 §3.1 の (a)）。PR #80 からの変更点は末尾の表にある。

## 決定

### 0. 適用範囲と区分の呼び方

1. 本 ADR の「閲覧」は、本基盤の経路での読み取り（`data/raw/` 配下の原ファイルの読み取りと、snapshot の partition の読み取り）を指す。MT5 の端末の気配値の表示と、研究の外での相場の閲覧の扱いは、制約の改定文の決定記録（D15 §2.2 の S2a。D15-13 (a)）が定める。（【決定】PR #107 の仮置き S1-6）
2. **【決定】取得の道具の出力**（PR #107 の要決定 S1-3）: 取得の道具（AWS の Windows の MT5）が取得の時に出す件数・時刻の範囲・ハッシュは、取得の一部として制約の改定文の決定記録（S2a）の下で扱い、本 ADR の閲覧に数えない。その記録は取り込みの記録（`docs/data/sealed/`。D15 の仮置き 11）に置く。取得の道具が何をどこまで扱ってよいかは改定文（S2a）が定める（人間の指示 D15 §0.1.2 の §4「取得の道具は 2024-01-01 以降の価格を**ファイルに書くだけ**にし」）。取得の道具が書いた原ファイルを本基盤で読む処理（受入れを含む）は、本 ADR の閲覧であり、ADR-0036 の品質確認の許可を通す。
3. 本 ADR は区分を名前で書く。**封印の区分**は、封印の状態（`HoldoutState`。`SEALED` / `CONSUMED`）を持つ区分すべてを指す（今は ADR-0014 の `LEGACY_HOLDOUT`。ADR-0014 を置き換える決定記録（S2a）が、2024-01-01 以降の封印の区分と前向きの封印の区分を定める）。**隔離の区分**は `QUARANTINED_UNASSIGNED` を指す。**2024 年以降の区分**は、封印の区分と隔離の区分の総称である。どの期間がどの区分に入るかは、ADR-0014 とそれを置き換える決定記録が定め、本 ADR は定めない（【決定】PR #107 の仮置き S1-2・S1-3）。

### 1. 区別の規則を置く場所

人間の決定 L-12（2026-10-09、原文は D11 §7.5）: 「1: 新しい ADR（推奨）」。本 ADR がその ADR である。

### 2. 品質確認の閲覧と戦略選定の閲覧の区別（D11 §5.2 の表。人間の決定 K-38）

人間の決定 K-38（2026-10-11、原文は D11 §7.10）: 「このまま + P1-3 の条件を反映（推奨）」。D11 §5.2 の表を次のとおり写す。

| | 品質確認の閲覧 | 戦略選定の閲覧 |
|---|---|---|
| 目的 | 出所・時刻・休場・欠落の追跡（D11 第2・3節）。封印の取り込みの受入れの検査（D15-17 (a)） | 戦略・パラメータ・評価基準を選ぶ・調整する・判断する |
| 出力してよいもの | 件数、時刻、区間、ハッシュ、合否、照合の一致・不一致の件数、根拠の資料 | 制限なし（区分が許す範囲で） |
| 出力しないもの | 価格の値・収益率・価格の図・指標の値・戦略の判断や損益 | — |
| 例 | 受入れの完全性検査、欠落一覧、区間台帳の作成、カレンダーの宣言と公表記録の照合 | run、探索の実験、評価のレポート |
| 記録 | 品質確認の閲覧の記録（本 ADR の第4項）に、日時・道具と版・対象の区分と期間・出力の種類を残す。消費の記録とは別（P1-3） | 封印の区分なら ADR-0014 の許可判定と消費の記録。研究履歴なら試行台帳 |

### 3. 品質確認だけで封印を消費しない条件（人間の決定 L-13・K-39・P1-3）

L-13 の原文（2026-10-09、D11 §7.5）の該当部分:

> 品質確認だけで封印を消費しないための条件も、先ほど決めた新しい閲覧ルールで明文化します。

K-39 の原文（2026-10-11、D11 §7.10）: 「3 つ + P1-3 の条件（推奨）」。

P1-3 の原文（2026-10-11、D11 §7.9）:

> 既存の読み取り関所（holdout_gate）を通し、品質確認専用の許可を追加します。
> ただし、最終評価用の許可に目的名だけを追加する設計では不十分です。
> - 品質確認の許可は、承認された道具・版・設定・対象期間に限定する。通常の戦略実行へ転用できないようにする。
> - 原CSV・1分足も対象に含め、関所を迂回する読み取り経路を作らない。
> - 閲覧記録と消費記録を明確に区別する。品質確認の記録を追加しても、封印状態を消費済みにしない。消費済みを封印へ戻すこともない。
> - 許可確認や必須記録に失敗したら、読み取りを開始しない。
> - 2026年分は品質確認の許可があっても隔離を維持する。
> - 価格を出力しないだけでなく、内部で戦略成績を計算して判断に使う経路も禁止する。
> 依存規則の設計（D01）、期間アクセス分類の決定記録（ADR-0014）、市場データ設計（D03）、品質確認用の新しい決定記録を整合させてから実装する方針です。

これらにより、次の**すべて**を満たす閲覧だけを品質確認の閲覧とする。1 つでも満たさない閲覧は戦略選定の閲覧として扱う（D11 §5.2 の K-39 の反映）。

1. 第2項の表の「出力しないもの」を出さない。【決定】受入れが保護の区分を引き継いで書く partition（保護された生成物）は、ここでいう出力に当たらない（条件は ADR-0036 の第10項。PR #80 の仮置き 12）。
2. 第4項の閲覧の記録がある。
3. 戦略・パラメータ・評価基準の判断に使わない。
4. 読み取りの関所（`holdout_gate`）の品質確認専用の許可を通る（ADR-0036）。
5. 閲覧の記録は消費の記録と別であり、品質確認の記録で封印の状態を消費済み（`CONSUMED`）にしない。消費済みを封印（`SEALED`）へ戻さない。
6. 内部で戦略の成績を計算して判断に使わない。

品質確認の閲覧は封印期間の使用に数えない。したがって、品質確認の閲覧は `HoldoutState` を変えない（ADR-0014 の注記）。

**【決定】条件を満たしていなかったと後から分かったとき**（PR #80 の仮置き 15）: 許可と閲覧の記録は通ったが、後から条件 1・3・6 のどれか（価格を出した、判断に使った、内部で戦略の成績を計算した）を満たしていなかったと分かった閲覧は、その時点で戦略選定の閲覧として扱う。人間が判定し、判定の事実を品質確認の閲覧の記録に**判定の行**（第4項の 6 の開始の行・終了の行とは別の第 3 の種別。閲覧の識別子・違反した条件・判定の日時と判定者を持ち、1 つの閲覧の識別子に 0 行か 1 行）として追記する。対象に封印の区分の partition が含まれていれば、その partition の状態（`SEALED` か `CONSUMED` か）によらず、既にあるすべての snapshot の同じ系列・重なる期間の `SEALED` の partition に、消費の記録を追記して `CONSUMED` にする（同じ期間の価格を見たことは snapshot にも対象の状態にもよらないため。対象が partition と原ファイルの両方を含むときは、この規則と下の原ファイルの規則の両方を当てる。下の原ファイルだけの閲覧の扱い（仮置き 21）と揃える）（不可逆。ADR-0014 の消費の記録の手順に従い、origin への push まで行う）。（【決定】PR #107 の仮置き S1-2）PR #80 の案と決定の原文の「`LEGACY_HOLDOUT`」「旧封印期間（2024〜2025）」は、封印の区分（第0項の 3。S2a で定める 2024-01-01 以降の封印の区分と前向きの封印の区分を含む）と読む。

**【決定】書き手と経路**（PR #80 の仮置き 20）: 最終評価の許可は D09 の後続版（D15 の R2・R4）まで実装しないので、この消費の記録は関所の最終評価の手順では書けない。関所の品質確認の許可を実装する PR（D15 §2.2 の S3。PR #80 の時点の呼び名は D11 §9 の順 4a。（【決定】PR #107 の仮置き S1-1））で、人間だけが使う管理コマンド（`app.cli`。判定の行の追記と、`HoldoutAccessLog` を通した消費の記録の追記・コミット・origin への push を、この順で fail-closed に行う）を足し、それで書く。消費の記録の行の種別は ADR-0014 の `CONSUMED` の行のまま（理由として閲覧の識別子と判定の行を指す）。**【決定】途中で失敗したときのやり直し**（PR #107 の要決定 S1-2。PR #80 の未決定「順 4a で決める事項 1」）: 管理コマンドが判定の行を書いた後に消費の記録の追記・push で失敗したときは、やり直しで、同じ閲覧の識別子の判定の行が既にあれば判定の行の追記を飛ばし、消費の記録の追記と push だけをやり直す（判定の行の重複で第4項の 6 の読込が止まらないようにする）。

**【決定】原ファイルだけを対象にした閲覧の違反判定**（PR #80 の仮置き 21）: 違反と判定した閲覧の対象に原ファイル（原 CSV・1 分足）が含まれるとき（partition を含まないときも）、その原ファイルの期間と重なる封印の区分の `SEALED` の partition を、既にあるすべての snapshot についてすべて使用済み（`CONSUMED`）にする（決定の原文の「旧封印期間（2024〜2025）」の読みは上の（【決定】PR #107 の仮置き S1-2））。原ファイルの期間は、閲覧の記録の対象（原ファイルの置き場とハッシュ）と、データ源の設定のファイルの期間から決める。期間が分からなければ、封印の区分の全体と重なるとみなす（fail-closed）。書き手と経路は上の仮置き 20 の管理コマンドである。

**【決定】違反と判定した後に受け入れる snapshot**（PR #107 の要決定 S1-1。PR #80 の未決定の仮置き 22）: 判定の後に受け入れる新しい snapshot の封印の区分の partition は、受入れが品質確認の閲覧の記録の判定の行を読み、同じ系列・重なる期間（原ファイルだけの閲覧の判定は、その原ファイルの期間。期間が分からなければ封印の区分の全体）に違反の判定があれば、使用済み（`CONSUMED`）で始める。判定の行が無ければ、初期状態の規則（ADR-0014 と、それを置き換える決定記録（S2a））のまま。記録が読めない・構造の誤りがあるときは受入れを始めない（第4項の 6 と同じ fail-closed）。

**【決定】管理コマンドの実装の PR**（PR #110 の要決定 S3-A。2026-10-29「(a) R4 で足す（推奨）」）: 上の「書き手と経路」の「S3 で…管理コマンドを足し」の文は変えず、管理コマンドは R4（関所の最終評価の許可の実装 PR）で足す。R4 が S5a より後になるなら、S5a の前に単独の PR で足す（D15 §2.2 の R4 の行の注記）。根拠: 消費の記録の行の項目と行の鍵は D09 の後続版（R2）が決め、消費の記録のポート `HoldoutAccessLog` と git の commit・push の仕組みは R4 で作る。封印の partition は S5a まで 0 件である。判定の行の型・読込・判定の後に受け入れる partition の初期状態（PR #107 の要決定 S1-1）は S3（PR #110）で実装した。

**【決定】原ファイルだけの閲覧の違反の範囲**（PR #110 の仮置き S3-7。2026-10-29「このまま（推奨）」）: 上の「原ファイルだけを対象にした閲覧の違反判定」と「違反と判定した後に受け入れる snapshot」の範囲は、その原ファイルの銘柄のすべての系列（銘柄が分からなければすべての銘柄）の、封印の区分の全体とする（原ファイルの期間を決めるデータ源の設定のファイルの期間の項目がまだ無いので、「期間が分からなければ全体」を当てる）。

### 4. 2024 年以降の品質確認の閲覧の記録（人間の決定 L-20・L-27）

L-20 の原文（2026-10-09、D11 §7.5）: 「1: 必須（日時・道具と版・区分と期間・出力の種類）（推奨）」。

L-27 の原文（2026-10-09、D11 §7.6）: 「1: 記録に残す（L-20 の対象に原ファイルの閲覧を含め、今回の監査の閲覧も後から記録）（推奨）」。

1. 2024 年以降の区分（封印の区分と隔離の区分）の品質確認の閲覧を、**必ず**記録する。項目は少なくとも、日時・道具と版・区分と期間・出力の種類の 4 つ。
2. 記録の対象は、snapshot の partition の読み取りだけでなく、**原ファイル（原 CSV・1 分足）の閲覧を含む**。
3. 記録は ADR-0014 の消費の記録（`data/snapshots/<snapshot_id>/access_log.jsonl`）とは**別の記録**にする（P1-3 の「閲覧記録と消費記録を明確に区別する」）。
4. 記録の追記に失敗したら読み取りを始めない（P1-3。手順は ADR-0036）。
5. **【決定】記録の置き場と「記録に成功した」の意味**（PR #80 の仮置き 2）: リポジトリの根の `research/quality_access_log.jsonl`（版管理・追記専用・1 行 1 JSON）に 1 本で置く。既存の行を書き換えない・消さない・並べ替えない。追記した行がファイルに書き込まれ、読み直して一致したことをもって「記録に成功した」とし、その後にだけ読み取りを始める。追記の後のコミットと origin への push は人間が行う（試行台帳 `research/trial_ledger.jsonl` と同じ運用。D01 §10.4）。記録を失わないための規則（試行台帳の D09 v0.3 §10.12.1・§10.12.5 に揃える）:
   1. 追記は 1 回ごとに作って消すロック `research/quality_access_log.lock`（版管理しない）の下で行う。ロックを取れなければ記録に失敗したとして読み取りを始めない。
   2. 品質確認の記録を伸ばす作業木は同時に 1 つだけとし、足した行を `main` に取り込んで push してから別の作業木で伸ばす。
   3. 合流で衝突したときは両方の行を残す（行を消さない）。
   4. 足した行を origin へ push するまで、その作業木を消さない。
   5. 記録のファイルは追記で作らない。関所の品質確認の許可を実装する PR（S3）が空のファイルを版管理で最初に置き、無ければ記録に失敗したとして読み取りを始めない（試行台帳の D09 v0.3 §10.12.1 の W2・§10.12.2 の L0 と同じ）。
   6. 末尾に改行で終わらない断片（前の追記が途中で止まった跡）があれば、試行台帳の W3 と同じ規則で扱い、断片につなげて追記しない。断片を扱えなければ記録に失敗したとして読み取りを始めない。
   ロックの除外（`.gitignore`）は S3 か別の実装 PR で足す。ただし、品質確認の閲覧の記録を追記する前に入れる。理由: 原ファイルの閲覧は snapshot に属さないので snapshot ごとのファイルに置けない。`research/` は既に版管理の対象である。品質確認の記録は封印の状態を変えないので、消費の記録のような origin への push による排他（ADR-0014「消費遷移の直列化」）は要らない。
6. **【決定】行の項目**（PR #80 の仮置き 3）: 決定の 4 項目に、次を足す。許可の識別子（ADR-0036）、対象（partition の識別子、または原ファイルの置き場とハッシュ）、品質確認の種類（受入れ・欠落一覧・区間台帳・照合など）、結果（完了・途中で停止）、記録の種別（その場の記録か、後から記録したものか）。既存の行を書き換えないので、1 回の閲覧は 2 行で記録する: 読み取りの前に書く**開始の行**（決定の 4 項目・許可の識別子・対象・品質確認の種類・記録の種別。これが「必須の記録」）と、読み取りの後に書く**終了の行**（結果・記録の種別）。記録の種別は両方の行に持たせ、同じ閲覧の 2 行で同じ値にする（違えば読込で構造の誤り）。各行は自分の行の識別子（行の鍵）を持つ。1 回の閲覧の 2 行を結ぶのは**閲覧の識別子だけ**であり、開始の行が閲覧の識別子を決め、終了の行は同じ閲覧の識別子を持つ（終了の行は開始の行の行の識別子を持たない）。1 つの閲覧の識別子に開始の行は 1 行、終了の行は 0 行か 1 行とする。読込は次をすべて構造の誤りとして止まる（試行台帳の読込の検査 D09 §10.12.2 の主キーの重複 L6・開始の行の無い結末の行 L8 と同じ考え方）: 同じ閲覧の識別子の開始の行が 2 行以上、終了の行が 2 行以上、開始の行の無い終了の行（第3項の判定の行も同じく、開始の行が無ければ誤り）、同じ閲覧の識別子の判定の行が 2 行以上、行の識別子の重複。構造の誤りがある間は、記録に失敗したとみなして新しい品質確認の読み取りを始めない（P1-3 の「必須記録に失敗したら、読み取りを開始しない」）。直すのは人間で、行を消さずに直す方法（合流の取り違えなら落ちた行を戻す）を取る。終了の行が無い開始の行は「結果不明」として扱い、閲覧が無かったことにはしない。【決定】読み取りの後に終了の行を書けなかったときは、道具は品質確認の結果（件数・合否など）を出さずに失敗として終わる（成功を報告しない）。開始の行は「結果不明」として残る（PR #80 の仮置き 13）。
