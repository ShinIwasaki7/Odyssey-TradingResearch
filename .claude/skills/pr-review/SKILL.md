# PR Review

このリポジトリの PR レビューのレーン。方針の正本は
[docs/pr_review_policy.md](../../../docs/pr_review_policy.md)、
Codex 応答の取得は [tools/ops/codex_review_poll.py](../../../tools/ops/codex_review_poll.py)。

## When to use

- PR を作る / PR 完了報告を作るとき。
- Codex の独立レビューを依頼し、その応答を待って修正するとき。
- レビュー指摘を分類し、merge 可否の判断材料を人間へ渡すとき。

## 手順

1. **PR 種別を判定する**（設計文書のみ / 骨格・ツール / 実装）。
   Codex review の要否は方針文書の §2 の表による。実装 PR と骨格・ツール PR は必須。
2. **PR を作る**。`gh pr create --base main`。本文には成果物一覧・検証結果・
   仮置きした事項（何が未定義か / 現在の実装 / 選択肢を1件ずつ番号付きで。方針文書 §6）を書く。
3. **検証を通す**。`uv sync` → `uv run ruff check .` → `uv run ruff format --check .`
   → `uv run mypy` → `uv run lint-imports` → `uv run pytest`。CI と同じ並び。
4. **Codex にレビューを依頼する**。`gh pr comment <PR#> --body "@codex review"` を投稿し、
   その投稿時刻（UTC, ISO8601）を控える。
   **レビュー対象範囲を依頼本文に添える**。範囲の正本は方針文書 §3.1 の表で選ぶ。
   §1.2 の境界表を持つ設計文書ならその §1.2、**§1.2 を持たない文書（決定記録・D01〜D03・全体計画書・
   本スキル・無人運転プロトコルなど）なら PR 本文に置いた範囲表**、実装なら PR 本文に挙げた設計文書の節である。
   `@codex review` の後ろに、選んだ正本を指す1文（例:「対象範囲は §1.2 の表。表の外は対象外」）を入れる。
   §1.2 を持たない文書の PR では、**PR 本文の範囲表に「決めること」と「決めないこと」の両方を書く**。
   **1つの PR が複数に当たる場合は、該当する正本をすべて併合する**（広い方に合わせる）。
   とくに**実装を含む PR は、同じ PR に設計文書の改訂が入っていても必ず設計文書の節を範囲に含める**。
5. **応答を待つ**。

   ```
   uv run python tools/ops/codex_review_poll.py \
       --pr <PR#> --since <投稿時刻> --interval 240 --timeout 1200
   ```

   exit 0 = 応答あり（JSON）、1 = gh の失敗（報告して停止）、
   2 = 20分無応答（「Codex 未応答（GitHub App 未設定の可能性）」として報告し、待たない）。
   動作確認だけしたいときは `--once`。
6. **指摘を分類する**。まず**対象内 / 対象外（後続文書へ）/ 不採用（人間の決定・設計と衝突）**の
   3つに分け、対象内のものに P0 / P1 / P2 を付ける（定義は方針文書 §3・§3.1）。
   poller は本文中の P0/P1/P2 タグを `priority` として返すが、タグがない指摘は
   自分で分類し、**3分類とも PR コメントに残す**。対象外は担当の文書・段階を、
   不採用は衝突の理由を書く。
7. **対象内の P0 / P1 を修正して push し、再度 `@codex review` を投稿する**。
   **終了条件は巡数ではなく指摘の残数**で、対象内の P0 が0件かつ P1 が0件の巡が出たら終了する。方針文書 §4.1。
   **0件の判定は、その巡が見たコミットに対するもの**である。**0件の巡の後に何かを push したら
   （P2 の修正、手順 9 の設計適合レビューの修正、手順 10 の仮置きの決定の反映を含む）、
   最終 head に対して 4 からやり直す**。再依頼を増やしたくないなら P2 は直さず、
   見送る理由を PR に記録する（方針文書 §3）。
   **2巡目以降は毎巡、直前までの指摘の傾向を1行で PR コメントに書いてから修正に入る**。
   同種の指摘が繰り返しているときは、個別の修正より先に**根本対処**（同じ種類の指摘が
   次の巡で再発しないようにする文書上・実装上の手当て）を入れる。方針文書 §4.2。
   **指摘に合わせて承認済みの設計や人間の決定を曲げない**。衝突するものは「不採用」とし、
   設計を変える価値があるなら要決定として人間に上げる。方針文書 §4.3。
8. **安全弁**。6巡で収束しなければ止め、**指摘の傾向と収束しない理由の仮説**を添えて人間に報告する
   （続行 / 対象範囲の明記し直し / 別工程への切り替えを人間が選ぶ）。方針文書 §4.4。
   このとき**報告の見出しは「要決定」で、merge の可否は問わない**（方針文書 §7）。
   人間の選択に従って収束させ、終了条件に達してから改めて merge を問う。
   Codex が利用上限で応答した巡は巡数に数えず、30分待って再投稿する（最大8回）。
   **8回を使い切っても利用上限のままなら止め、「要決定」として報告する**（merge は問わない）。
   残っている P0 / P1 の件数と最後の利用上限応答の時刻を書き、進捗ファイルの「人間待ち」に1行残す。
   人間が利用枠の回復後の再開を指示する。
9. **設計適合レビュー**（方針文書 §5）を別レーンとして行う。Codex が clean でも省略しない。
   実装 PR では Codex が終了条件に達した後、**別セッション（既定では Sonnet）が read-only** で行い、
   P0 / P1 / P2 で報告する。修正は実装したセッションが行う。
10. **仮置きを閉じる**。PR 本文に列挙した仮置き事項を、merge 前に人間が1件ずつ選択式で決める。
    決定は**設計文書の改訂として同じ PR に含める**（方針文書 §6）。
11. **報告する**。実施した巡数と各巡の件数、残った P2、仮置きした事項、**終了条件を満たした head** を書く。
    手順 9・10 で PR を変えたなら、その最終 head で 4〜7 をもう一巡してから報告する。

## 規律

- 4 の依頼から 7 の再依頼までのループは、**巡数によらず、承認停止なしで自走する**。
  止めて確認を取るのは **merge の前だけ**（CLAUDE.md）。8 の安全弁に当たったときは、
  merge ではなく「要決定」として報告する。
- **merge はしない**。merge 可否は人間が判断する。
- 3チャネル（review / inline comment / issue comment）の照会は poller が正本。
  `gh` を手で叩いて再実装しない。
- 承認外の設計判断が必要になったら、その場で決めずに実装を止め、設計文書へ差し戻す。
